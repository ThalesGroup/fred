# fred-capability-ppt-filler

Fred agent capability that fills an uploaded PowerPoint template from chat.

An author uploads a `.pptx` whose slides carry `{key}` or `{{key}}` placeholders and whose
slide notes describe each key (a `{key}:` or `{{key}}:` header plus prose, optional
`- type: image` / `- folder: ...` metadata for picture keys). The capability
parses and validates the template, then gives the agent a fill tool that
substitutes the keys - honoring inline Markdown (`**bold**` / `*italic*`) in the
substituted values - and produces a downloadable, filled deck.

This package holds the pure, offline core: the template parser/validator, the
shared text-frame traversal (list + replace), the image-anchor geometry seam, and
the folder-resolution / image-location validation layer.

## Template markers

Single and double braces identify the same case-sensitive key. Mix either form
between slides and notes, including multi-key headers such as `{first}, {{last}}:`
and image markers. Leading/trailing key whitespace is ignored. The single-brace
form requires at least one character and no braces inside the key. Double-brace recognition retains its legacy rule: the key is everything
up to the first closing brace, followed by two closing braces. No extra syntax
validation is introduced for existing templates.

Markers split across runs in one paragraph are supported in text boxes, table
text, and grouped shapes. Images use the containing shape's placement box;
table cells remain invalid image locations. Chart text and SmartArt are unsupported.

## `ppt_builder` (same package)

A second capability, `ppt_builder` (`fred_capability_ppt_filler/builder/`),
generates a deck from a chat plan on an _unannotated_ corporate template, or
on the built-in Fred template (`builder/assets/fred_template.pptx`, analysis
stored beside it and regenerated by `make builtin-inventory`) when the agent
has none.

- **Save** stores the template and returns at once; a background job
  (`analysis_job.py`) analyses it (layouts, example slides, slots, capacities)
  and, unless "Use a vision model" is off, labels each example slide with a
  vision model (`labelling.py`). The result lives in the owned table
  `cap_ppt_builder_analysis`; the agent stays unavailable until it succeeds.
- **Chat**: the model sends content per slide, `assign.py` picks the template
  slide under deck rules (cover once first, closing last, no three identical
  in a row), and a slide that fits nothing returns `needs_revision` instead of
  a wrong deck. `render.py` duplicates and fills; `checks.py` removes leftover
  example text. Delivery reuses the filler's preview part and pane.

- **Charts** (`charts.py`): the model sends data only (`chart {type,
  categories, series, title, unit, show}`, `show` saying whether a pie's labels
  hold percentages, values or both); the code draws a native python-pptx chart
  in a chart zone (a chart placeholder, or an example slide's chart frames),
  else in a free large content placeholder, in the theme's accent colours and
  body font. When an example slide's own chart already shows the type asked,
  it is kept instead (copied with its workbook, data replaced): the designer's
  colours and fonts stay, only legend, labels and number format follow the
  data. Eleven types: column, bar, line, pie, doughnut, stacked column and
  bar, area, radar on categories; scatter and bubble on numeric points
  (`series [{name, points [{x, y, size, label}]}]`, `x_title`/`y_title`
  required, one unit per axis, point names shown up to 12 points). The type
  mapping, chart data, legend rule and length check are adapted from
  `fred-capability-pptx-generator` (PR #3058, by Shuigami). An example slide
  may hold up to four charts, each at least 1/20 of the slide: a plan slide
  sends `charts [chart, …]` (each titled) and only goes to a slide with exactly
  that many frames, filled in reading order; a free text box right above a
  frame shows that chart's title.

- **Storytelling** (`story.py`, `notes.py`): the working rules ask for a
  `takeaway` per content slide (the first line of the speaker notes, never on
  the slide) and a `source` for content from the user's documents or data; the builder enforces only that a
  chart holds one measure (two written units refused) and writes the notes.
  The `validate_plan` setting turns a conversation's first build into an
  outline the user answers first.

- **Intents** (meaning, never style): `chart.highlight` / `sort` /
  `stacked_as`, `table.total_row` (the table style's own total row, else bold)
  / `highlight_row` / `highlight_column` (bold and a tint of the style's
  accent; `table_intents.py` lists PowerPoint's predefined styles), and
  `items[].trend` (an arrow before the figure, in its own font). A template
  zone named or read as the key message (`takeaway`, `key message`, `à
  retenir`…) shows the slide's takeaway only when the user asks for the key
  messages on the slides (`show_takeaways`). An intent the slide cannot show
  never blocks: the agent is told and "What was built" says so.

Optional annotation channels: a shape name from the Selection pane (`title`,
`body`, `number`, `keep`…), and `kind:` / `label:` lines in a slide's notes.
Spec: `openspec/specs/ppt-builder/spec.md`.

### Evaluation (opt-in)

`make eval` runs prompts x templates through the real analysis, the real
`build_presentation` tool and a real LLM acting as the agent, and writes one
JSON per run, `summary.md` and, with `--contact-sheets`, PNG sheets. It reads
only the API keys from `apps/fred-agents/config/.env` and the profile from
`models_catalog.yaml` (default `chat.mistral.small`). Templates are never
committed: pass them by path. LibreOffice is required.

```bash
make eval EVAL_ARGS="--template corporate=/path/to/template.pptx --out target/eval"
# or PPT_EVAL_TEMPLATES=a.pptx,b.pptx; --modes vision,rules; --prompts pitch_4,kickoff
```

## Registration

Installing this package _is_ the registration: the fred-agents pod auto-discovers
the capability at boot via the `fred.capabilities` entry point declared in
`pyproject.toml` (`ppt_filler = "fred_capability_ppt_filler.capability:PptFillerCapability"`).

## Validation memory and admission

Selection and save each independently open the deck once. One marker walk supplies
field discovery and table-cell image checks, without allocating image anchors or
computing coordinates. Generation retains its geometry path. Only the schema survives
into asynchronous folder lookup; worker cleanup collects cyclic presentation objects
after validation and generation,
including failed processing. Collection runs in the worker but can pause other Python
threads while holding the GIL. The existing per-pod limit remains four heavy jobs with
fail-fast busy feedback. This count is not a memory budget: four large decks can still
exceed a deployment's limit, and cancelling an awaiting request can release its slot
before its worker stops.

Save transport failures distinguish an unreachable runtime (503), operation timeout
(504), and interrupted communication (502). The form translates their stable codes;
transport logs include exception type and duration with the current request context,
without service URLs or raw exception messages. A dropped connection does not identify
an OOM kill or require Kubernetes access.
