# Validate or kill the `operation` concept

**Date:** 2026-08-12

**Scope:** `libs/fred-runtime`, `libs/fred-sdk`, `apps/fred-agents`, `apps/control-plane-backend`, `apps/frontend` (model-routing surfaces)

**Status:** investigation and decision brief — no code changed, no docs renamed or removed

**Tracking:** blocks the model-routing simplification (`capability + operation -> model profile`); no GitHub issue filed for the simplification itself yet

---

## 1. Verdict

**(A) Keep `operation` as a rule criterion — but redefine what it means, close one real gap, and change the UI.** The mechanism itself is sound and already proven in production: Graph agents (`mindmap`, `comparison`) explicitly declare distinct, self-descriptive operation labels at real call sites today, and those labels already flow through the same resolver ReAct uses. A fully shipped control-plane/frontend rule editor exists for this (`TEAM-05`, #2118), has been bug-fixed once in production (#2237), and a second product surface is currently being requested to reuse the same pattern (#2325, open, filed 2026-08-11). Killing the concept now would mean reversing live, working, wanted infrastructure. But four things are broken or dishonest about the concept *as currently presented*, and the verdict is conditioned on fixing them, not on leaving them as-is: (1) `routing`/`planning` are ReAct/Deep-specific heuristic labels wearing a platform-wide name, colliding with the feature's own name and with Deep Agents' native "planning" vocabulary; (2) Deep Agents silently ignores `operation` for model selection despite computing the same label for tracing — a real bug, not a design choice; (3) there is no shared cross-agent vocabulary — Graph agents already use entirely different, non-overlapping operation strings, so a "planning" rule can never affect them, and nothing documents this; (4) the UI is free text with zero validation, which has already produced at least one class of silently-dead configuration in production and is about to be repeated by design in #2325's proposed dropdown of invented operation names. Section 6 spells out what this means concretely for the backend contract and for Odelia's UI work.

## 2. Q1 findings — where the strings are produced and consumed

### 2.1 ReAct: heuristic inference, not a decision

`infer_react_model_operation_from_messages` — `libs/fred-runtime/fred_runtime/react/react_model_adapter.py:151-173`:

```python
for message in reversed(messages):
    if message.__class__.__name__ == "ToolMessage":
        return REACT_MODEL_OPERATION_PLANNING
    if isinstance(message, HumanMessage):
        return REACT_MODEL_OPERATION_ROUTING
return REACT_MODEL_OPERATION_ROUTING
```

`REACT_MODEL_OPERATION_ROUTING = "routing"`, `REACT_MODEL_OPERATION_PLANNING = "planning"` (same file, lines 59-60). **This is inferred from a heuristic over state, not derived from an explicit decision.** It walks message history in reverse and returns on the *first* `ToolMessage` or `HumanMessage` found — not on `messages[-1]`'s type, not on a count of tool calls, not on anything the agent author declared. The module's own comment (lines 48-58) is explicit about original intent: **"Model-operation labels are Fred tracing metadata, not agent-facing concepts."** It was designed for tracing and is now also used as a policy-routing criterion — a repurposing the code comment itself doesn't anticipate.

Wired into `ReActRuntime.build_executor` via `ModelRoutingMiddleware` (`libs/fred-runtime/fred_runtime/react/middleware/model_routing.py:32-96`), constructed in `libs/fred-runtime/fred_runtime/react/react_runtime.py:892` and placed second in the fixed platform middleware frame (`build_react_platform_middleware_frame`, `libs/fred-runtime/fred_runtime/react/middleware/frame.py:78-113`; the frame is `CheckpointHygieneMiddleware -> ModelRoutingMiddleware -> DynamicPromptMiddleware -> capability middleware -> TracingKpiMiddleware -> ToolObservabilityMiddleware -> FredHitlMiddleware -> [ToolCallLimitMiddleware]`, corroborated by `docs/swift/reviews/2026-08-05-langchain-langgraph-middleware-modernization.md:36-43`).

`ModelRoutingMiddleware.awrap_model_call` (`model_routing.py:64-96`) calls the heuristic on every model call, resolves and caches one `BaseChatModel` per operation string for the lifetime of the compiled agent (`self._models_by_operation`, line 62), and calls `chat_model_factory.build_for_operation(definition=..., binding=..., purpose="chat", operation=operation)`.

### 2.2 Resolver and factory — the deterministic core

`ModelRoutingResolver.resolve()` (`libs/fred-runtime/fred_runtime/model_routing/resolver.py:118-185`) is a pure function: filter rules by `capability`, keep those whose `match` fields all match the request, highest-specificity-then-declaration-order wins, else fall through to `_default_selection` (capability default, `resolver.py:187-203`).

`RoutedChatModelFactory` (`libs/fred-runtime/fred_runtime/model_routing/provider.py:83-296`) is the only production implementation of `ChatModelFactoryPort` (`libs/fred-sdk/fred_sdk/contracts/runtime.py:392-426`). `build()` → `build_for_chat(operation=None)`; `build_for_operation()` → `build_for_chat(operation=operation)`. `build_for_chat()` (`provider.py:162-296`) builds a `ModelSelectionRequest(capability, purpose="chat", agent_id, team_id, user_id, operation)` (lines 341-348), calls `self._resolver.resolve(request)` (line 349), enforces the ReBAC `usable_model_ids` fail-closed check, then only **after** the static resolver falls through to `ModelSelectionSource.DEFAULT` does it call `resolve_team_override(...)` (`provider.py:350-362`, `resolver.py:221-280`) — the per-team override in control-plane never overrides a static `models_catalog.yaml` rule; it only fills the gap when no static rule matched.

`RoutedChatModelFactory` is wired globally at pod boot: `_build_chat_model_factory` (`libs/fred-runtime/fred_runtime/app/context.py` / `agent_app.py:364-401`) constructs it and threads it into the process-global `RuntimeContext.chat_model_factory` (`agent_app.py:4649, 4665`), reaching every `RuntimeServices`. **Note:** `provider.py:18-19`'s module docstring ("intentionally not wired by default into Fred runtime creation... a safe integration seam to trial centralized model routing") is stale and contradicts this — it is wired by default today. Flagged, not corrected (read-only task).

### 2.3 Graph v2 — explicit, author-declared, opt-in

`on_activate()` builds one fixed model with **no** operation (`self._model = ...factory.build(self.definition, binding)`, `libs/fred-runtime/fred_runtime/graph/graph_runtime.py:1926-1930`). Per-operation routing is opt-in: `_model_for_operation(self, operation)` (`graph_runtime.py:1132-1148`) calls `factory.build_for_operation(..., operation=operation)`, threaded into every node's execution context as `model_resolver=self._model_for_operation` (lines 1258, 1470). The call site an agent author actually touches is `GraphNodeContext.invoke_model(messages, *, operation: str = "default")` / `invoke_structured_model(...)` (`libs/fred-sdk/fred_sdk/graph/runtime.py:213-228`, implemented at `graph_runtime.py:432-461,562+`): `resolved_model = self.model_resolver(operation) if self.model_resolver is not None else self.model`. **Graph never calls `infer_operation_from_messages`.** If a node author doesn't pass `operation=`, the literal string `"default"` is used, which matches no `routing`/`planning` rule and silently falls through to the capability default.

Real, shipped, non-probe production call sites (all registered agents, `apps/fred-agents/fred_agents/registry.py`):

| Agent | File:line | Operation label | What it does |
|---|---|---|---|
| Mindmap | `mindmap/graph_steps.py:1045` | `mindmap_summarize_document_page` | per-page transcript-segment summarization |
| Mindmap | `mindmap/graph_steps.py:1163` | `mindmap_analyze_request` | normalize request + detect language |
| Mindmap | `mindmap/graph_steps.py:1403` | `mindmap_build_fallback_digest` | condense evidence when no page summaries exist |

None of these use `"routing"` or `"planning"`. **This is the single most important Q1 finding**: the only real, shipped, non-diagnostic operation labels in this codebase today are agent-namespaced and task-specific, not phase-generic.

The `routing_probe` Graph agent (`apps/fred-agents/fred_agents/routing_probe/graph_agent.py`, `graph_steps.py`, built for issue #2267) is a real SDK-native diagnostic tool, tagged `("test", "graph", "routing", "dev")`, registered but **not enabled in any deployed `agents_catalog.yaml`** — dormant. It hardcodes three phase nodes at `graph_steps.py:98-100`: `operation="routing"`, `operation="planning"`, and, notably, a **third label, `operation="execution"`**, that doesn't exist anywhere in ReAct — proof that even Fred's own diagnostic tooling already treats the two-value ReAct taxonomy as insufficient once you leave ReAct.

### 2.4 Deep Agents — the label is computed but never used to route

`DeepAgentRuntime(ReActRuntime)` (`libs/fred-runtime/fred_runtime/deep/deep_runtime.py:84`) inherits `ReActRuntime.on_activate` unchanged — one fixed model via `.build()`, no operation. It overrides `build_executor` to call `create_deep_agent(model=self._model, ..., middleware=_build_deepagent_runtime_middleware(...))` (`deep_runtime.py:143-154,171,179-197`; `deepagents>=0.6.12` is a **hard**, not optional, dependency — `libs/fred-runtime/pyproject.toml:13`, despite a stale "optional dependency" comment at `deep_runtime.py:170`). `_build_deepagent_runtime_middleware` (`deep_runtime.py:245-303`) wires only `TracingKpiMiddleware` and `ToolObservabilityMiddleware` — **`ModelRoutingMiddleware` is never constructed anywhere in this file.** `infer_react_model_operation_from_messages` **is** passed into `TracingKpiMiddleware` (line 284-285), so the `routing`/`planning` label is still computed and still lands in spans/KPI — but nothing downstream ever calls `build_for_operation` with it. **Every Deep Agents turn runs on one fixed model for its entire lifetime, regardless of phase, despite computing a phase label that looks identical to ReAct's.** This is an unadvertised asymmetry, not a documented design decision — `RUNTIME-EXECUTION-CONTRACT.md` §8.17 (lines 1198-1229) covers only the observability-parity fix that added `TracingKpiMiddleware`/`ToolObservabilityMiddleware` to Deep; it says nothing about `ModelRoutingMiddleware`, consistent with the code.

### 2.5 Bypass paths — model construction outside operation-aware routing

- `libs/fred-sdk/fred_sdk/authoring/authored_tool_runtime.py:113` — the authored-tool `ToolContext.model` property calls `.build()` with no operation. Goes through the resolver, but never benefits from per-operation routing.
- `libs/fred-sdk/fred_sdk/authoring/api.py:260-296` — `ctx.extract_structured()`, a ReAct capability-authoring primitive, reuses `self._runtime.model` (whatever the turn's already-resolved routing/planning model is) directly, with **no operation parameter at all**. Shipped SDK code; zero current callers.
- `apps/knowledge-flow-backend` — an entirely separate app with its own static, config-driven `get_model()` (`libs/fred-core/fred_core/model/factory.py:271`), no `purpose`/`operation`/`capability` concept whatsoever. `application_context.py:632-638` (`get_utility_model()`, `get_vision_model()`) feeds document summarization (`core/processors/output/summarizer/{llm_summarizer,smart_llm_summarizer}.py`, plus the live `POST /documents/{id}/summarize` endpoint) and image/vision description (`core/processors/input/common/image_describer.py`, used by 6 ingestion processors). These are real, shipped, high-traffic LLM call sites, but structurally outside fred-runtime's routing system — a different app boundary, not a gap in `operation`.
- No hardcoded provider-SDK construction (`ChatOpenAI(`, `ChatAnthropic(`, etc.) was found anywhere in `libs/fred-runtime`, `libs/fred-sdk`, or `apps/fred-agents` outside the resolver's own `FredCoreModelProvider.build_model` (`provider.py:69,80`) — every in-scope chat-model acquisition funnels through `ChatModelFactoryPort`.
- `libs/fred-core/fred_core/model/factory.py:822-850`'s `get_structured_chain()` is exported but has zero callers anywhere — dead code, not a live bypass.

## 3. Q2 findings — do `routing`/`planning` carve the space correctly?

**No, not as a platform-wide pair — but the underlying idea (a call-site-declared label) is sound, and Graph already does it correctly.**

**The `routing` collision is real and already visible in the live UI.** The shipped team-settings panel is titled "Model routing" (`apps/frontend/src/locales/en/translation.json:1956,1960`, `TeamSettingsRouting.tsx:99,194`), and inside it a free-text field literally labeled "Operation" lets an admin type the value `routing` (`translation.json:1970`, example text at line 1969: *"Override the default model for a specific runtime operation (e.g. planning)"*). An admin configuring "Model routing" who sets "Operation: routing" is reading a sentence that means two unrelated things with the same word, in the same screen. Not a crash, but a real, demonstrated confusion surface — not a hypothetical one.

**The `planning` collision is currently latent but real for the near future.** Fred does not use Deep Agents' native `write_todos`/planning-tool pattern today (confirmed: zero hits for `write_todos`, `SubAgent`, `SummarizationMiddleware` anywhere in the repo outside the `deepagents` package itself) — so there is no in-repo clash *yet*. But `deepagents>=0.6.12` is already a hard dependency, and Deep Agents' own vocabulary for todo-decomposition is "planning." Naming Fred's tool-followup phase `planning` now forecloses that name for when Fred does adopt native planning, which is a real, foreseeable, not merely theoretical cost.

**Is the boundary between the two phases stable?** No — and it's coarser than the docs imply. A turn with N tool-call round trips emits the model-call operation exactly once as `routing` (the very first call) and then `planning` for **every subsequent call**, indiscriminately — the 2nd tool follow-up and the 8th are labeled identically. There is no notion of "early planning" vs. "converging" vs. "self-check." The heuristic is a strict binary (last message was a `ToolMessage`, yes/no), not a graduated pipeline.

**This directly contradicts the aspirational vocabulary already circulating in this repo.** `docs/swift/platform/LLM_ROUTING_FRED.md` and `LLM_ROUTING_PRIMER.md` (both compact platform docs, not RFCs) describe a five-phase pipeline — `routing -> planning -> analysis -> generate_draft -> self_check` (`LLM_ROUTING_FRED.md:81-152`) — as if it were Fred's actual convention. It is not: `analysis`, `generate_draft`, `self_check`, and `corrective_queries` appear **nowhere** in production code (verified: zero matches across the entire repo outside these two doc files). `json_validation_fc` appears only in a resolver docstring example and one unit test (`resolver.py` module docstring, `libs/fred-runtime/tests/test_model_routing.py:442`) — never emitted by real code. These docs describe a hypothesis as if it were shipped, and issue #2325 (open, filed 2026-08-11 — see §5) proposes hard-coding exactly this fictional list into a UI dropdown. This is precisely the mistake the task brief warns against repeating from `purpose`.

**Naming proposal.** For the two ReAct/Deep values specifically, adopt `tool_selection` / `tool_followup` (the suggested candidate) over `routing`/`planning`: it removes both collisions, and it's a more accurate description of the actual mechanical trigger (last message is/isn't a `ToolMessage`) than "planning," which implies deliberate multi-step reasoning the heuristic doesn't actually detect. **But renaming alone doesn't fix the deeper issue**: `operation` should stop being documented as one shared five-phase taxonomy. It is, and should be presented as, a **call-site label the executing runtime or agent author chooses to declare** — ReAct/Deep mechanically contribute exactly two values (`tool_selection`/`tool_followup`); each Graph agent defines its own (as `mindmap_*`/`comparison_*` already do, correctly). A rule keyed on `tool_followup` will never match a Graph node, and vice versa, unless a Graph author deliberately reuses that literal string.

**Other call sites that plausibly deserve their own operation, and whether they exist today:**

| Candidate | Exists today? | Verdict |
|---|---|---|
| Conversation/session title generation | **No** — `title` is a plain nullable column (`control_plane_backend/models/session_metadata_models.py:33`), set verbatim from user input or defaulted client-side to `"New conversation"` (`useManagedChat.ts:436`); no LLM involved anywhere | Do not propose an operation for it |
| ReAct conversation-history summarization | **No** — no truncation-then-recap mechanism exists anywhere in the ReAct runtime or control-plane | Do not propose an operation for it |
| Document summarization (knowledge-flow-backend) | **Yes**, shipped (`llm_summarizer.py`, `smart_llm_summarizer.py`, live `POST /documents/{id}/summarize` endpoint) | Exists, but in a different app that doesn't use `ChatModelFactoryPort` at all — not a candidate for Fred's `operation` taxonomy without first bringing that app onto the shared resolver, which is a separate, larger question |
| Image/vision description (knowledge-flow-backend ingestion) | **Yes**, shipped, used by 6 processors | Same as above — different app, different model-resolution mechanism |
| Mindmap/comparison structured extraction and judging | **Yes**, shipped (§2.3 table) | Already has operations — this is the working example, not a gap |
| `ctx.extract_structured()` (ReAct capability authoring) | **Yes**, shipped SDK primitive, zero callers | A real gap in the *mechanism*: it deliberately reuses the turn's already-resolved model with no operation tag, so a capability author cannot ask for a different model for a structured-extraction sub-call within a ReAct turn today. Worth a small follow-up if a real capability needs it — not urgent, no live caller yet |

## 4. Q3 findings — does the concept generalise across the three runtime shapes?

| # | Criterion | 1. ReAct | 2. Deep Agents | 3. Arbitrary LangGraph graphs |
|---|---|---|---|---|
| C1 | Emission point exists | **Yes.** `ModelRoutingMiddleware.awrap_model_call` calls the heuristic on every model call (`model_routing.py:64-96`). | **Partial/No for routing purposes.** The label is computed (`TracingKpiMiddleware`, via the same heuristic) but `ModelRoutingMiddleware` is never wired into `_build_deepagent_runtime_middleware` (`deep_runtime.py:245-303`) — there is no point where the computed label actually changes which model is used. | **Only if the author opts in.** `GraphNodeContext.invoke_model(operation=...)` exists and is real (`graph_runtime.py:432-461`), but nothing forces a node to pass it; unset, it's the literal `"default"`. |
| C2 | Deterministic | **Yes**, technically — same message-history input always yields the same output; but it's a *heuristic over state*, not an explicit decision (§2.1). | N/A for model selection today (nothing consumes it); would inherit ReAct's C2 if wired. | **Yes**, trivially — it's a hardcoded string literal at the call site, chosen once by the author. |
| C3 | Refactor-stable | **Mostly yes**, with a caveat: the check is `message.__class__.__name__ == "ToolMessage"` (string comparison on class name, not `isinstance`) — brittle if that class is ever renamed or subclassed oddly, though stable across ordinary agent-code refactors since it depends on LangChain's message types, not Fred's own node/function names. | N/A today. | **Yes** — it's a named parameter distinct from node/function identity, so renaming a node doesn't change the operation (unlike relying on node names implicitly, which the task brief correctly warns against). |
| C4 | Same meaning across agents | **Yes, but narrowly** — every ReAct agent gets exactly the same two-phase mechanical split (first turn vs. post-tool-call), so `tool_followup` means the same structural thing for agent A and agent B. It says nothing about the agent's actual reasoning content. | N/A today (not consumed). | **No — this is the decisive failure.** The only real production Graph operation labels (`mindmap_summarize_document_page`, `comparison_judge_pair`, …) are agent-namespaced and mutually exclusive by construction; nothing enforces or even suggests a shared vocabulary. A team-wide rule for `"planning"` will never match any Graph node in a real Fred capability today. |
| C5 | Actionable — would an operator plausibly route differently here | **Plausible** — a cheap model for the initial routing decision, a stronger one for tool-driven follow-up is the stated rationale in `LLM_ROUTING_FRED.md` and matches the exact ask in the currently open #2325. | **Plausible in principle**, moot until C1 is fixed. | **Yes, demonstrated** — mindmap already has a natural case (cheap model for per-page summarization at `mindmap_summarize_document_page`, stronger model for final structured extraction at `mindmap_extract_mindmap`), even though no rule currently exercises it (§5). |

**Reading the table:** ReAct passes all five criteria, weakly on C2/C3. Deep Agents fails C1 for routing purposes today — a fixable bug, not an inherent limitation (the label already exists; it's simply not wired to a consequence). Arbitrary/team-authored graphs pass C1/C2/C3/C5 **only when the author explicitly declares an operation**, and fail C4 outright as things stand — there is no cross-agent shared vocabulary, and the repo's only real multi-agent evidence (mindmap vs. comparison) shows agents independently inventing disjoint namespaces, which is actually the *correct* engineering choice for them (self-documenting, collision-free) but incompatible with treating `operation` as one flat enum a platform admin can reason about across agents.

**On the stated invariant.** The task brief's framing — "the agent author declares no provider, no model name, not even a capability" — does not exist verbatim anywhere in this repo. The actual documented invariants (`LLM_ROUTING_FRED.md:76,236-237,340`) are narrower: "agents never reference providers or model identifiers directly." That same doc's own three-dimension table (lines 44-50) lists `capability` (`chat`, `language`) as a legitimate, agent-declared routing input — so "not even a capability" is not accurate against Fred's own docs; every `ModelSelectionRequest` does carry a capability (`libs/fred-runtime/fred_runtime/model_routing/contracts.py:438-451`), always. If the report needs the "not even a capability" framing, source it explicitly as the requester's own phrasing, not a documented Fred invariant — see §7.

**Does declaring an operation violate the actual (narrower) invariant?** No. `operation` is an opaque label, not a provider, model name, or capability — declaring `mindmap_extract_mindmap` tells the policy layer nothing about *how* to run the model, only *which call site* this is. This is consistent with the real invariant as documented.

**Per-subagent Deep Agents model config vs. `operation`.** Fred does not use Deep Agents' subagent feature today (zero hits for `SubAgent`/subagent config anywhere in the repo) — there is no live tension to resolve, only a latent one. The repo's own architecture review (`docs/swift/reviews/2026-08-05-langchain-langgraph-middleware-modernization.md`, boundary table lines 171-190, and the `ModelRoutingMiddleware` row: "Keep custom: FRED owns model/operation policy") already states the team's position that model/operation routing must stay FRED-owned, not delegated to LangChain/LangGraph/deepagents mechanisms. If Deep Agents' subagent-level model config is ever adopted, it should be treated as a competing mechanism to reconcile against that stated position, not silently allowed to coexist — but that is a decision for whenever it's actually adopted, not now.

## 5. Evidence of demand

**Static YAML `rules:` — zero real instances anywhere.** The only real deployment catalog, `apps/fred-agents/config/models_catalog.yaml:311`, has `rules: []`. The same content is duplicated in `deploy/charts/fred/values.yaml` (Helm default, `rules: []`) and `deploy/local/k3d/values-local.yaml` (`rules: []`). The one exception, `deploy/local/k3d/values-bench.yaml`, has exactly 2 rules, both `agent_id`-only — neither sets `operation:`. **No shipped configuration anywhere differentiates behavior by operation today.**

**But the broader `operation` mechanism has real, current, non-hypothetical demand:**

- **A fully shipped product surface already exists.** `TeamRoutingPolicy`/`TeamOperationRouteRule` is a real, Postgres-persisted (`alembic/versions/bc06439e4cf9_add_team_routing_policy.py`), versioned, API-driven feature (`GET`/`PATCH /control-plane/v1/teams/{team_id}/routing-policy`) with a live frontend panel (`TeamSettingsRouting.tsx`, route `/team/{teamId}/settings/routing`). Root issue #2118 (closed 2026-07-27, milestone `swift ga`), authored by the requester of this investigation.
- **It has already been used and already broke in production.** Issue #2237 (closed 2026-08-09): *"Operation overrides cannot be saved — `rule_id` is always empty"* — a real 422 that made "Add rule" dead until fixed, meaning real users were actively trying to configure per-operation overrides through the UI and hitting a defect. The same issue's "Deferred" section independently confirms **`purpose` is entirely dead in production** ("the runtime only ever emits `purpose='chat'`... any purpose value is either non-matching or matches everything") — the exact `purpose`-mistake precedent this investigation was asked to avoid repeating, now independently verified from a second source.
- **A fresh, currently open request extends the same pattern.** Issue #2325 (**OPEN**, filed 2026-08-11, "Must have"): *"Evaluation run creation: let the user configure agent model overrides per operation"* — reusing `TeamOperationRouteRule`'s exact shape for per-run overrides, motivated by a concrete, named case: *"a stronger model for `planning`, the default for everything else."* This is real, current demand for operation-differentiated routing — not a hypothesis. Its design section, however, proposes *"a known-operations dropdown, e.g. `routing`, `planning`, `analysis`, `generate_draft`, `self_check`"* — lifted straight from the aspirational vocabulary in `LLM_ROUTING_FRED.md`, three of which (`analysis`, `generate_draft`, `self_check`) are emitted by **zero lines of production code** anywhere in this repo. Left as designed, this would ship a second UI surface offering users a menu of operations that mostly don't exist — repeating, in a new location, exactly the silently-dead-rule problem #2237 already surfaced once.
- **The `operation` label is computed on every production ReAct/Deep turn today**, whether or not any rule consumes it (§2.1, §2.4) — the plumbing is live, not aspirational, even though no deployment currently branches on it.

**Reading this evidence honestly:** there is zero demonstrated need for the *specific* `routing`/`planning` ReAct split (no team has ever configured a rule that uses it). There is real, current, twice-independently-sourced demand for the *general capability* of per-call-site model overrides — proven by a shipped feature, a production bug fix, and a fresh open issue asking to extend the same pattern to a second surface. Recommending (C), drop `operation` entirely, would mean reversing that shipped and actively-requested capability. Recommending (B), observability-only, is defensible on the narrow ReAct-pair evidence alone but does not fit the Graph-layer reality, where the mechanism already works and is already used for real, distinct call sites — it would mean disabling something that already functions correctly for Graph in order to protect against a naming problem that's specific to ReAct/Deep.

## 6. Consequences of the verdict

**Backend contract:**

- Keep `operation: str | None` as a `ModelRouteMatch`/`TeamOperationRouteRule` criterion (`contracts.py:158-201`, `CONTROL-PLANE-PRODUCT-CONTRACT.md` §37) — no removal.
- Rename the two ReAct/Deep-emitted constants from `REACT_MODEL_OPERATION_ROUTING`/`REACT_MODEL_OPERATION_PLANNING` (`"routing"`/`"planning"`) to `"tool_selection"`/`"tool_followup"` (or an equivalent pair without the naming collisions identified in §3). This is a breaking rename for any stored `TeamOperationRouteRule` currently using the old values — but §5 confirms **zero real deployment currently has such a rule** (only 2 agent-scoped, operation-wildcard rules exist in the bench config), so the migration cost is close to zero right now and will only grow.
- Fix the Deep Agents gap: either wire `ModelRoutingMiddleware` into `_build_deepagent_runtime_middleware` (`deep_runtime.py:245-303`) so the label it already computes actually drives model selection, or explicitly document that Deep Agents does not support per-operation routing yet and remove the misleading appearance of parity (today it silently computes a label that looks identical to ReAct's but does nothing).
- Document, in the compact design doc (not another RFC — this is a mechanical clarification, not an open question), that `operation` has no shared cross-agent vocabulary: ReAct/Deep contribute exactly two literal values; Graph agents each declare their own. `LLM_ROUTING_FRED.md`/`LLM_ROUTING_PRIMER.md` should be corrected to stop presenting the five-phase `routing -> planning -> analysis -> generate_draft -> self_check` pipeline as Fred's actual convention — it isn't, and isn't in scope to become one without new call sites that don't exist yet (§3).

**What Odelia should build (and should not):**

- Should: replace the free-text "Operation" input in `TeamSettingsRouting.tsx` (and any equivalent field proposed for #2325's evaluation-run overrides) with a dropdown **sourced from the actually-declared operation labels of the selected agent/template**, not a fixed platform-wide list. This is buildable today for Graph agents (their operation strings are static literals at known call sites, enumerable per agent) and for ReAct/Deep (exactly two values, post-rename). This directly fixes the dead-rule defect class already observed once in production (#2237) and prevents #2325 from repeating it with the aspirational five-value list currently in its design section.
- Should not: build #2325's UI against the `routing`/`planning`/`analysis`/`generate_draft`/`self_check` list as currently drafted — three of those five values are not emitted by any code in this repository and would silently never match anything, exactly repeating the `purpose` mistake this investigation was commissioned to avoid.
- Should not: assume a "planning" or "tool_followup" rule set for one team affects any Graph-based capability that team uses — Graph agents (mindmap, comparison, and anything future) use their own operation strings entirely, and the UI/docs should say so plainly rather than implying one universal set of phases governs every agent.
