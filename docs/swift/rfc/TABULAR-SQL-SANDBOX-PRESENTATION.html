Executing agent SQL over
tabular data, safely

The agent writes arbitrary SQL. It runs in DuckDB, in our pod, over Parquet the user is allowed to read. Where does the security boundary sit?

Florian Muller · August 2026
Full design: docs/swift/rfc/TABULAR-SQL-SANDBOX-RFC.md · trigger: #2364 (GCS signBlob outage)

The problem

Arbitrary SQL, authored by an LLM, run in our pod

  • The tabular feature lets an agent answer questions over CSV/Excel by writing read-only SQL, executed by DuckDB against the ingested Parquet.
  • The SQL text is attacker-controlled in the worst case (prompt injection through an ingested document).
  • ReBAC already decides which datasets the user may read. The question is enforcing that — and nothing more — at execution.

Four requirements

  • R1 — never read a dataset the user can't see
  • R2 — never read anything else in the pod: local files, other buckets, internal HTTP, the metadata server
  • R3 — the boundary must not be a hand-written SQL parser: a parser gap must not be a breach
  • R4 (goal) — read big Parquet without downloading the whole file

Today R1/R2 rest on an AST-walking SQL validator. R3 says: that's exactly what we don't want to depend on.

Why R3 matters

What one gap in the SQL parser costs

DuckDB is powerful by design. If a crafted query slips past the validator, plain SQL functions reach far beyond the dataset:

-- read any file the pod can read
SELECT * FROM read_text('/app/.env');

-- SSRF → the cloud metadata server →
-- the pod's service-account token
SELECT * FROM read_csv(
  'http://169.254.169.254/computeMetadata/...');

-- reach another team's bucket with
-- the pod's own store credentials
SELECT * FROM read_parquet(
  's3://fred-data/other-team/secret.parquet');
  • The validator is a recursive AST walk (joins, CTEs, subqueries, table functions). It works today — but it is a hand-written allowlist.
  • One missed node shape = full reach of the pod's filesystem, network, and credentials.
  • A boundary that fails closed — and lives outside the SQL stream — is worth more than a cleverer parser.

This is the lens for judging every option that follows.

Two survive the R1–R3 filter: A (download + sandbox) and B (STS + httpfs).

The two survivors

Same job, opposite strategy

A · Local materialization + sandbox

Bring the data to a locked-down DuckDB.

  • Backend downloads only the authorized files into a per-job directory
  • DuckDB runs with external access off, pinned to that directory, config locked
  • Boundary = physical absence — there is nothing else to reach
  • No credential in DuckDB's hands, no network

Cost: full-file download (weak on R4). Verified workable on DuckDB 1.5.4.

B · STS-scoped credential + httpfs

Give DuckDB a key that only opens the right doors.

  • Backend mints a short-lived credential scoped to exactly those object keys
  • DuckDB reads s3:///https:// directly, with range reads
  • Boundary = the credential, enforced at the object store's IAM layer
  • A foreign key → 403 from the store, outside the SQL stream

Meets R4. But httpfs stays on → needs a network layer (next).

Solution A · in depth

Download, sandbox, delete

→

Sandboxexternal access off · pinned to dir · locked

Run & deletequery, then drop the whole dir

The lock (verified on 1.5.4)

SET allowed_directories = ['<job dir>'];
SET enable_external_access = false;
SET lock_configuration   = true;
-- httpfs never loaded · no s3 · no http
-- agent SQL cannot leave the dir or re-SET

The job dir contains only authorized artifacts, so "which files are present" is the boundary — not the parser.

Efficiency — a pnpm-style cache

  • Shared pod-local cache; each job dir gets hardlinks to what it may read (symlinks are correctly refused by the sandbox)
  • Invalidation = the store's own etag / generation (one HEAD per mount) — catches re-ingestion and out-of-band writes
  • Eviction is safe: a running job's hardlink keeps the file alive
  • Local mode: copy instead, no cache — the local file is the store of record
Solution B · in depth

Mint a scoped key — in a pod that can only reach the store

Per query: ReBAC picks the datasets, KF mints a token scoped to those keys only, and hands it to a locked-down executor.

The catch: httpfs can't be locked down like A — external access must stay on, so SSRF is closed at the pod's network edge, not in DuckDB. That edge can't live on KF (it needs the metadata server) → a separate minimal pod.

Both solutions · a fair question

"So do we delete the parser?" — No, we demote it

Today — the parser is the wall

A row cap forces the SQL into one wrapped SELECT; the AST allowlist is what keeps it safe.

# the query is wrapped to force a cap
SELECT * FROM (
    <agent sql>          # must be ONE SELECT
) AS fred_result
LIMIT 200;
  • Security = the recursive AST allowlist
  • Wrapper is injectable if a gap admits a 2nd statement
  • No multi-statement, no temp-table staging

With the sandbox — the parser steps back

The sandbox (A) or the scoped credential (B) is the wall. The cap becomes a Python fetch.

# no wrapper — cap is a streaming fetch
cur = con.execute(agent_sql)   # any script
rows = cur.fetchmany(max_rows + 1)
  • Security = sandbox / credential — not the parser
  • Parser kept only for clean 400s + mount-narrowing
  • Multi-statement + CREATE TEMP TABLE now allowed

The agent gets more SQL power, not less — the sandbox is what makes that safe.

Current state · PR #2444

The GCS outage is fixed — the boundary isn't moved yet

#2364 removed the presigned URL: GCS reads now download server-side via ADC (plain storage.objects.get, no signBlob). Good. But the DuckDB sandbox flags aren't on, so even with the download in place, the agent's SQL can still:

Reach any URL

httpfs is still loadable → read_csv('http://169.254.169.254/…') — SSRF to the SA token.

Read any file in the pod

External access is on → read_text('/app/.env'), any path the process can reach.

Change its own config

No lock_configuration → a query can SET its way around limits.

The parser is still the only wall. Solution A is half-built: the expensive half.

The gap to full Solution A

One small change moves the boundary off the parser

GapWhat's neededSize
G1Sandbox flags on the local-file path: allowed_directories + enable_external_access=false + lock_configuration. The strategy is already known at connection-open.small — the one that matters
G2Non-GCS remote stores (MinIO/SeaweedFS) still use presigned URL + httpfs → decide: extend download model, or hold for Bdecision + medium
G3Local filesystem store hands direct paths into object_root (all docs) → copy authorized artifacts into the job dirsmall

With G1 alone, the GCS path — the one in production trouble — stops depending on the parser.

The decision for this room

Do we go A, or B?

A wins if…

artifacts stay within a disk budget · we want no new infrastructure · we want the boundary that fails closed with zero credential and zero network. Meets R1–R3 today via G1.

B wins if…

big-Parquet analysis (R4) becomes real · we accept running a tabular-executor service + egress policy · and S3NS actually exposes STS.

  • Open question, gating B: does S3NS (sovereign GCP) expose STS / Credential Access Boundaries at all? Same class of gap as the signBlob denial that started this.
  • Not exclusive: A now (uniform, small), B later behind the executor when R4 arrives — the parser is demoted either way.
