# Agent sandbox: k3d browser evidence

These captures show real Fred conversations on `k3d-fred-secondary` on 24-25 October 2026. The test agent had only `code_sandbox` enabled. The guest used gVisor, SIG Agent Sandbox with a zero-replica WarmPool, and read-only rclone CSI mounts. The corpus and attachment files are synthetic. The retained captures were refreshed on 25 October in the French UI with the Bash-only tool contract and the new trace styling; the group count reads `commande` or `commandes`. The tool now asks for a short intent comment before every execution. When supplied, that comment appears alone beside the command count in the group heading. Each expanded command row has a small terminal icon after its status dot, then shows the comment in ordinary text and the submitted command in a monospace code surface. Multiline code, including heredocs, is flattened onto one visually truncated row. Each detail capture shows the complete Bash script and result. A nonzero exit code marks a command as failed in the trace.

The cluster was deleted and rebuilt with the factory `make k3d-wipe`, `make k3d-up`, `make k3d-sandbox-smoke`, `make k3d-sandbox-files-demo` and `make k3d-app` targets. The smoke passed Bash, Python, gVisor, zero warm replicas and a read-only CSI file read. No Kubernetes resource name or persistent volume was edited by hand.

The guest's `/skills` directory contained `compare-options`, `grounded-research`, `meeting-minutes`, `mermaid`, `summarize-document`, `tabular-evidence` and `verify-answer`, matching the Fred runtime source used by the `/` skill catalog. Its script `tabular-evidence/analyze.py` ran against a mounted CSV and returned operations 75, research 120 and support 40. A new source skill appeared in an existing guest after the CSI directory cache refreshed, without a guest restart. The runtime's `/` catalog currently snapshots skills at startup and needs an agent Pod restart to discover a newly published skill.

An early browser run exposed a race when parallel `execute_code` calls opened the same file view: one request failed on a duplicate primary key and appeared as "The sandbox is unavailable." The view creation now uses a conflict-safe insert and a locked ownership check. The four-call skill rerun above had no such failure. This was a reliability defect, not a write escape.

Earlier exploratory runs covered DOCX, PPTX, PDF, CSV, DuckDB and a Large 4 isolation probe. The probe found no service-account token, `kubectl`, Docker socket or other conversation's attachment; writes to `/inputs` and `/skills` were denied, and tested network destinations were unreachable. These observations do not prove production isolation. The target cluster still needs its own CNI, gVisor or Kata, CSI, process-limit and load validation. Small 4 often chose short Bash or Python scripts; Medium 3.5 used pandas more readily and got the weighted Excel calculation right on its first try. Those were individual runs, not a statistical model comparison.
