# Reference: document journey trace and inspection

Technical companion to [Priya's document journey](02.2-document-journey.md), for
Fred developers and coding assistants. It maps the visible steps to source code,
durable state and read-only inspection commands. This is a replay guide, not a
record of an observed live run. The scenario uses Priya in TSN's fredlab team,
folder `ArxivAi`, file `paper.pdf` and processing profile `fast`.

## Establish the scenario

Use an installation with manager original storage, processing, its dispatcher,
Temporal and the KF workers configured according to the
[activation guide](../swift/ops/migrations/rust-control-plane.md#optional-document-processing).
For the OpenSearch checkpoints, the KF `manager_processing.vector_store` must
select OpenSearch and its dedicated index. Another configured vector backend
does not write these chunks to OpenSearch.

Priya's authenticated subject, current CGU acceptance, unique TSN attachment and
fredlab `can_write` permission are prerequisites. Admin alone does not grant
content write access. The repository's
[demo provisioning fixture](../../apps/control-plane/tests/fixtures/import_export/demo_provisioning/organizations.json)
places Priya in **Demo**, and its fredlab team also belongs to Demo. Do not mistake
that fixture for this TSN scenario or give Priya a second organization to reproduce
it. Confirm the actual identity and placement before beginning; see
[one person, one organization](04-organizations.md#one-person-one-organization).

Record the API/worker revisions, effective configuration, PDF byte count and
SHA-256, selected profile and these identifiers once, then reuse them at every
checkpoint. Names alone are insufficient to join stores.

| Symbol | Meaning and source |
| --- | --- |
| `U` | Priya's OIDC subject, not her display name |
| `O`, `S` | TSN organization UUID and fredlab team-space UUID; API identities, SQL `space`, OpenFGA placement |
| `F` | ArxivAi folder UUID returned by creation |
| `K` | Upload `Idempotency-Key`, generated by the browser |
| `D` | Published document UUID; also the internal `document_upload.id` |
| `I` | Installation UUID, `document_storage.namespace` |
| `P` | Processing attempt UUID, `document_processing.id` |
| `W`, `R` | Temporal workflow ID and run ID, recorded in `document_processing` |
| `G` | Published generation UUID, `document_processing.manifest.generation` |

API paths below are relative to the deployment's manager API base. The browser
uses the `/control-plane/v1` proxy; worker configuration can use a different mounted
base. Capture the actual network requests rather than substituting a KF URL.

## Follow the document

The steps below describe stage boundaries; retries can add intermediate commits. S3, OpenSearch,
PostgreSQL and Temporal do not share one transaction. SQL publication determines
which staged result is visible.

### 1. Create ArxivAi

The existing creation dialog sends `POST /folders` with `space_id=S`,
`parent_id=null`, `name="ArxivAi"`. Manager returns `201` with `F` and path `/<F>/`.
There is one new `folder` row, no document, no S3 object and no vector.
OpenFGA evaluates authority on `space:S`; no `folder:F` tuple is created.
The organization's technical guard revision changes on a successful mutation.

Read [create_folder and authorized_write](../../apps/control-plane/src/spaces.rs)
and the [HTTP handler](../../apps/control-plane/src/api.rs).

### 2. Transfer and store the original

Priya opens ArxivAi and selects the PDF. Preflight checks current name conflicts
and quota without reserving either. The actual multipart upload carries `K` and
`profile=fast`. Manager first spools the complete file and measures its bytes and
SHA-256. A guarded transaction reserves `paper.pdf` and its bytes in
`document_upload(status='pending')`; fredlab is the quota owner in this scenario.

Manager writes and reads back the original object in the [document layout](A9-documents.md#physical-object-layout). A second guarded
transaction inserts `document(id=D, space_id=S, folder_id=F)`, marks the receipt
`stored`, and creates `document_processing(id=P, status='pending', stage='queued')`.
These three changes commit together. An omitted profile creates no processing
attempt. `stored` means the original is durable, not that extraction is finished.
The dispatcher can advance processing before the upload response is received.

Read [upload, reserve and publish](../../apps/control-plane/src/documents/upload.rs)
and [processing admission](../../apps/control-plane/src/processing/store.rs).

### 3. Deliver the existing worker contract

The dispatcher, a background task of `control-plane serve`, is woken by the
commit's notification, leases the SQL intent and starts `ProcessPush` in the
configured Temporal namespace and base queue. Its periodic poll delivers an intent
whose notification was missed. `W` is
`manager-document-<I>-<P>`; `R` identifies its execution. The input remains one
`PipelineDefinition` containing one `FileToProcess`: `document_uid=D`,
`source_tag=manager:<I>:<P>`, the selected profile and the exported KF policy.
Files and credentials are absent from Temporal input.

The workflow and registered activities retain their existing contracts. The KF
activity implementation recognizes the source reference and selects the manager
persistence adapter. This requires a KF worker with that adapter; it does not mean
an older, unmodified worker understands manager storage. The adapter's authenticated
HTTP callbacks are a separate contract from the unchanged Temporal input.

Read [submission](../../apps/control-plane/src/processing/worker_contract.rs),
[dispatch](../../apps/control-plane/src/processing/dispatch.rs) and
[manager adapter](../../apps/knowledge-flow-backend/knowledge_flow_backend/features/manager_processing/service.py).

### 4. Extract, chunk and index

The worker authenticates to manager using its workload identity. Manager binds
each stage claim to this work and a generation. Preparation persists `policy.json`.
Extraction obtains the original through manager, checks its size/hash and runs the
existing configured PDF processor. Output processing reuses the configured
splitter, embedding model and vector store implementation.

Each stage writes under its own derived generation prefix. For a nonempty text
PDF, the published artifact set contains `metadata.json`, `output.md` and
`chunks.jsonl`, plus carried policy and processor-specific assets when produced.
The manifest, not a hard-coded list, is the inventory. An input PDF's File preview
uses the original; a derived `native.pdf` is not required for this PDF journey.

Each vector ID is `UUIDv5(generation UUID, decimal ordinal string)`. The worker
journals planned IDs before writes and reads back persisted chunks before creating
`chunks.jsonl`. Chunk metadata uses the existing Swift fields, including
`document_uid=D` and `chunk_uid`; there are no manager-specific metadata fields.
The OpenSearch adapter and mapping are unchanged. The current adapter receives
`folder_id` and `folder_path` in its descriptor but does not copy them into chunk
metadata. Join `D` back to SQL to establish ArxivAi placement. Filter the index by
`metadata.document_uid`, then match chunk IDs to the published `chunks.jsonl`.
A document filter alone can also return staged generations.

The separate `document-vectors` index prevents legacy retrieval from exposing
staged manager chunks or applying legacy ACLs to manager documents. Generation
UUID-based IDs fence stale writes without changing the Swift chunk schema.

Read [scoped pipeline and vectors](../../apps/knowledge-flow-backend/knowledge_flow_backend/features/manager_processing/persistence.py),
[artifact persistence](../../apps/knowledge-flow-backend/knowledge_flow_backend/features/manager_processing/artifacts.py)
and the [OpenSearch mapping](../../apps/knowledge-flow-backend/knowledge_flow_backend/core/stores/vector/opensearch_vector_store.py).

### 5. Publish and read the result

Manager verifies the final artifact bytes against the submitted manifest, then
rechecks Priya's current write authority and CGU before committing `succeeded`,
`done`, the published manifest and counts. Existing File/Raw previews and download
perform current read checks. Reload recovers progress from SQL.

Temporal completion alone is not processing success. Conversely, staged S3
objects or vectors can exist before SQL publication. Manager outputs remain
separate from the legacy KF catalog and search/chat retrieval. No new per-document
OpenFGA grant, legacy tag, legacy metadata-catalog row or legacy task is created.

Read [publication](../../apps/control-plane/src/processing/publication.rs) and
[preview](../../apps/control-plane/src/processing/preview.rs). The exact bucket/key
comparison with `swift` is in [physical object layout](A9-documents.md#physical-object-layout).

## Observe the same identities in every store

Use read-only credentials and the effective deployment endpoints. The following
queries inspect state; ingestion itself is driven through the existing UI.
Take a fresh snapshot at each checkpoint: keeping one SQL transaction open
through the upload would hide later commits.

### PostgreSQL: placement, receipts and publication

In `psql`, set `subject`, `space_id`, `folder_id` and `request_key` to the captured
values (`\set variable value`). Inspect the manager database, not KF's catalog.
After publication, the same query also gives `D`, `P`, `W`, `R` and `G`.

```sql
BEGIN READ ONLY;
SELECT id, kind, name, personal_owner, deletion_id
FROM space WHERE id = :'space_id'::uuid;
SELECT id, space_id, parent_id, name, path
FROM folder WHERE id = :'folder_id'::uuid;
SELECT namespace, endpoint, bucket, prefix,
       derived_endpoint, derived_bucket, derived_prefix
FROM document_storage WHERE singleton;
SELECT u.id AS upload_id, u.request_key, u.actor, u.organization_id,
       u.status AS upload_status, u.processing_profile,
       u.document_id, u.size, u.sha256, u.object_key, u.quota_owner,
       d.space_id, d.folder_id, d.name,
       p.id AS processing_id, p.status AS processing_status, p.stage,
       p.workflow_id, p.run_id, p.error_code, p.chunks, p.vectors,
       p.manifest, p.generations
FROM document_upload u
LEFT JOIN document d ON d.id = u.document_id
LEFT JOIN document_processing p ON p.document_id = d.id
WHERE u.actor = :'subject' AND u.request_key = :'request_key'::uuid
ORDER BY p.created_at, p.id;
COMMIT;
```

Before storage finishes, `document_id` is null. After an explicit processing retry,
the join returns multiple attempts for the same original. The `space` table has
no parent/organization column: establish TSN/fredlab placement in OpenFGA.

### OpenFGA: existing authority, no document grants

Read `active_store` and `model_id` from the manager's `authorization_store` row;
do not assume the configured seed store is the active store. Use these values
with the existing OpenFGA inspection client or HTTP API:

| Read-only request | Body / expected result for this scenario |
| --- | --- |
| `POST /stores/<active_store>/read` | `{"tuple_key":{"object":"space:<S>"}}`; fredlab's `parent` is `space:<O>`; inspect its direct roles |
| `POST /stores/<active_store>/read` | `{"tuple_key":{"object":"space:<O>"}}`; inspect Priya's organization role |
| `POST /stores/<active_store>/check` | `{"authorization_model_id":"<model_id>","tuple_key":{"user":"user:<U>","relation":"can_write","object":"space:<S>"},"consistency":"HIGHER_CONSISTENCY"}`; `allowed=true` |
| `POST /stores/<active_store>/read` | `{"tuple_key":{"object":"guard:<O>","relation":"version"}}`; technical revision changes across successful writes |

Follow every nonempty `continuation_token` when reading tuples. For the simple
direct-role setup, Priya has `member` on TSN and `editor` on fredlab. An inherited
editor grant is also valid; use Check to establish effective authority. The
[model](../../apps/control-plane/openfga/model.fga) has no folder/document types.
Content mutations change guard versions, not the number of content-role tuples.

### S3: original bytes and published artifacts

Use the bucket and **exact** `object_key` from SQL. With an already configured
AWS CLI profile, `S3_ENDPOINT`, `ORIGINAL_BUCKET` and `OBJECT_KEY` from that row:

```sh
aws --endpoint-url "$S3_ENDPOINT" s3api head-object \
  --bucket "$ORIGINAL_BUCKET" --key "$OBJECT_KEY"
aws --endpoint-url "$S3_ENDPOINT" s3api get-object \
  --bucket "$ORIGINAL_BUCKET" --key "$OBJECT_KEY" /tmp/journey-original.pdf
sha256sum /tmp/journey-original.pdf
```

Compare byte count and SHA-256 with the selected PDF and SQL; an ETag is not a
SHA-256 proof. Use the derived endpoint/bucket from SQL and the
[prefix formula](A9-documents.md#physical-object-layout) with `I/O/S/D/P/G`.
List that prefix (follow pagination), then fetch each relative path in the
published manifest and compare its size/hash. Read `output.md`, `metadata.json`
and every record of `chunks.jsonl`. Do not expect an `ArxivAi/` S3 directory.
Earlier stage/attempt objects may remain until cleanup; only the published
manifest identifies the visible result.

### OpenSearch and Temporal: inspect the processing result

In OpenSearch Dev Tools, substitute the configured manager index and `D`:

```text
GET <manager-index>/_search
{
  "size": 10,
  "track_total_hits": true,
  "_source": ["text", "metadata"],
  "query": {"term": {"metadata.document_uid": "<D>"}}
}
```

This is a sample, and its total can include obsolete generations awaiting cleanup.
For a complete comparison, use `_mget` in bounded batches with all IDs from the
published `chunks.jsonl`. Verify each `_id`, text and metadata against that file,
and inspect a vector's `vector_field` dimension
against the configured embedding model. The published record/ID count agrees with
the SQL manifest's `chunks`, `vectors` and `vector_ordinals` for this text PDF.
Check the legacy index separately: this ingestion adds no legacy document there.

In the configured Temporal namespace, open `W` and `R`. Verify `ProcessPush`, the
single-file input, the base/profile queues and activity attempts. Correlate their
outcomes with `document_processing`; read its `submission` for the exact frozen
input and `profile_settings` for the resolved processor policy.

## Replay checkpoints and evidence

| Stop | Expected observation |
| --- | --- |
| Before import | Correct Priya/TSN/fredlab authority; `F` exists; no `paper.pdf` in this folder |
| Upload response | `stored` original, identical size/hash, one processing intent; processing may already be running |
| During processing | Durable stage/generation changes; temporary S3/vector effects can precede publication |
| Success | SQL `succeeded/done`, manifest `G`, matching artifacts/chunks/vectors; File/Raw previews and original download work |
| Reload | Same `D`, original key and published result |
| Failure, if exercised | Original remains; SQL records a safe stage/error; an explicit processing retry creates a new `P`, linked by `retry_of`, without uploading again |

For a live session, record timestamp, identifiers, expected result, observed result
and evidence at each stop in the session notes or issue. Mark a transient state
that was too brief to capture as unobserved; a later terminal row does not prove
that the intermediate state was inspected. Do not mark the whole journey passed
from the UI badge alone.

The [quality chapter](09-quality.md#processing-request-costs-and-evidence) describes
automated evidence and its limits. The disposable real-worker journey exercises
Temporal and object storage with **PGVector**, local identity/model fixtures and
no KF HTTP server. It is not an OpenSearch ingestion observation or a live run of
this named Priya/TSN scenario.
