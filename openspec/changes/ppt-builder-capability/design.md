## Context

`ppt_builder` lives beside `ppt_filler` in `libs/capabilities/fred-capability-ppt-filler/` and reuses its bounded python-pptx work (`concurrency.py`), run-merging traversal (`traversal.py`), image placement (`fill.py`, `folder_resolution.py`), `text_metrics.py`, LibreOffice conversion (`fred_core.convert_office_bytes_to_pdf`), the `ppt_preview` chat part and side pane. The first iteration (pattern inventory + model-chosen pattern ids + composition layer) failed end to end; see proposal. This design replaces it; the acquired rendering pieces stay.

Facts that constrain the design (verified in code):

- `validate_config` receives `SaveContext(identity, services)` (`fred_sdk/contracts/capability/context.py:79`). The save path builds a full `BoundRuntimeContext` but only injects `workspace_fs`, `agent_assets`, `document_folders` (`fred_runtime/app/agent_app.py` `_build_capability_save_services`, ~3676). There is **no model port** on the save path or in capability routes; `ChatModelFactoryPort.build(definition, binding)` (`fred_sdk/contracts/runtime.py:556`) is turn-shaped. The process-wide factory is `get_runtime_context().config.chat_model_factory` (`RoutedChatModelFactory`, `fred_runtime/model_routing/provider.py:104`, enforcing `binding.usable_model_ids`). `ModelProfile` (`model_routing/contracts.py:145`) has no vision flag; `models_catalog.yaml` profiles are all `capability: chat`, default `chat.mistral.small`.
- A capability can change its stored config **only** through `validate_config`'s return value; nothing writes it back later. `agent_assets` is bound to the saving user's token, which may expire after the request.
- fred-agents runs several replicas. In-process helpers exist (`fred_runtime/common/background_tasks.spawn`, in-memory). Temporal workers run in knowledge-flow, control-plane and knowledge-base pods, not in fred-agents. `fred_core.tasks` (`cp_task_run`) has a closed task-kind union owned by control-plane. Capabilities may own tables (`cap_<id>_*`, own Alembic tree, `migrations_location()`); `fred-capability-writable-document/store.py` is the pattern (overridable module-level store provider, router authorises on the row).
- The analysis takes ~50 s, beyond what a synchronous save should hold.
- The feature is not on `swift`: stored configs exist only on local dev agents, so the config shape may change without `upgrade_config`.

## Goals / Non-Goals

**Goals:** the template's own slides, chosen right, every time or an explicit error; analysis that understands real corporate slides; a save that never waits on analysis; one code path for customer and built-in templates; measurable deck quality.

**Non-Goals:** drawing shapes the template does not hold (composition is parked, not abandoned); charts/SmartArt as generated content, and tables beyond filling one the template holds (D14); swapping a template's icons; vision checks of the rendered output (text checks only); in-place editing of a generated deck (D23 edits the plan and re-renders the whole deck).

## Decisions

### D1. Park composition, delete the generated theme

The composition layer moves to branch `parked/ppt-builder-composition` with the `ppt-builder-composition` change. `Box`, `ZoneRole`, `TEXT_ROLES` move from `design_system.py` into `models.py`. `theme.py` is deleted (dependents: `capability.py` middleware, `validate_config`, the `/theme` routes and the registration warm-up; tests `test_builder_capability.py` and the parked composition tests; frontend `usePatternsPreview.ts` via `/theme/preview.pdf`). Alternative — keep composition behind a switch — rejected: it is the code path that replaced good template slides, and keeping it doubles every test surface.

### D2. Analysis: deterministic structure, vision meaning

1. **Deterministic pass (kept, amended).** Layouts are classified from typed placeholders as today. On example slides **every text-bearing shape is a slot by default**; excluded only when its text repeats on ≥ 2 slides, or it is a date/footer/slide-number field (`a:fld` type or footer/date/sldNum placeholder). Repeat groups, exclusion of chart/table/icon-bank slides (a data table is a table zone since D14) and the annotation channels stay. **Capacity** is measured once per slot at analysis time from its geometry, padding, line spacing and font (`text_metrics`) and stored on the slot as `chars_per_line × max_lines`. When the slot holds the designer's own sample text and that text does not fit by our ruler (the substitute font is wider than the designer's), the width estimate is **calibrated** on it: a binary search raises `chars_per_line`, bounded to 1/0.75 of the measured value, until the sample fits its box (after ppt-master's `text_measure.py calibrate`). The fit check, the renderer and the tool description all read these stored numbers, so they agree. Copyable relationships drop slide-to-slide hyperlinks from the blockers (they are not copied, D6). The sample-text lexicon no longer decides fillability.
   - **An example slide that copies its layout replaces it** (same role-bearing placeholders, nothing else drawn, not excluded): the slide is the pattern (duplicate + fill) and the layout pattern leaves the inventory, so one design is one catalogue entry and it carries the slide's sample text (calibration), notes `kind:`/`label:` lines, shape names and position. A later copy of the same layout is dropped; an excluded copy leaves the layout. Rejected: merging the slide's signals into the layout pattern (two sources per pattern, and instantiating the layout loses the sample's paragraph formatting). Slide 1 with a title-capable slot and no body content is a `cover` unless the template states another kind. An `OBJECT` placeholder named as an image is an image slot; a title-less `quote` takes its quote in the top body (role `title`) and its attribution in the next (`subtitle`). Measuring a slide placeholder, its padding and wrap come from its layout's and master's `bodyPr` when its own is empty, and inherited font and spacing from the layout placeholder of the same idx first (the first of the same type matched the wrong one).
   - **Rows of same-size text shapes are a repeat group**, like grouped shapes: non-grouped text shapes (placeholders or boxes, never title/subtitle) of near-equal size (±10 %), same font size and weight, on one band without overlap. One row is a group from 3 shapes; 2 shapes need a second row aligned under them (number above label, step title above body), and the chained rows give each item its fields; further aligned rows of the same class make a grid. A shape wider than 35 % or taller than 40 % of the slide is a column body, never an item, so two/three-column bodies stay columns. These items are filled, counted (`items max N`), removed and recentred like grouped ones; a non-grouped item is removed shape by shape.
2. **Vision pass (new, `labelling.py`).** Example slides are rendered once (patterns deck → LibreOffice PDF → per-page PNG via `pypdfium2`), each slot's box is overlaid with its number (set-of-mark), and a vision model returns, per slide, a typed JSON: `kind`, `label`, per-slot `purpose`, `max_items`, `reusable`. Calls run with bounded concurrency. Layouts are not sent (placeholders already say what they are).
3. **Merge.** Vision decides `kind`, `reusable` and slot purposes; geometry and capacity stay deterministic. A vision `kind` is accepted only when the slide's detected slots can carry it, otherwise the heuristic kind stays (the vision label, purposes and reusable flag are still taken), the rejection is logged, counted and added to the pattern's warnings. Compatibility: `cover`, `section`, `quote` need a title-capable slot (title or heading); `bullets` a body slot (body or caption); `image_text` an image slot and a text slot besides the title; `two_columns`, `comparison` two body slots; `cards`, `process`, `timeline`, `agenda`, `team` a repeat group of ≥ 2 items; `figures` a repeat group with a number slot; `closing`, `other` anything. A slide whose vision answer is missing or invalid keeps its heuristic label and `labelled_by="heuristic"`, shown in the review panel — analysis never fails because the model did. A kind the template declares — a `kind:` note, or a shape name stating a kind (`Roadmap`, `Agenda`…) — is never replaced by the vision kind; a `label:` note keeps its label.

**One closed vocabulary**, `SlideKind`: `cover, agenda, section, bullets, two_columns, comparison, cards, figures, process, timeline, team, quote, image_text, table, closing, other` (`table` added by D14). It replaces `Intent` in the inventory, the overrides and the plan.

### D3. Model access outside a turn

Add a turn-free port to the SDK: `CapabilityModelPort` (optional field appended to `RuntimeServices`), `async ainvoke(messages, *, profile_id: str | None, require_vision: bool) -> AIMessage`, implemented in fred-runtime over `RoutedChatModelFactory.select`/`build_for_chat` (`model_routing/provider.py`), which resolves **the model the agent uses by default**: platform binding, then `resolve_effective_chat_profile` (`fred_sdk/contracts/context.py` ~600: agent override → team `chat_default_profile_id` → catalogue default), checked against `usable_model_ids`.

Gap found: the save binding (`_build_capability_save_services`) has no team routing policy, no `usable_model_ids` and no platform binding; control-plane sends those only at prepare-execution. So the validate-config call gains the same routing fields control-plane already computes for prepare-execution (WP10), the save binding carries them, and the background job keeps that binding. No agent-tuning model field exists; routing is keyed by `agent_id`, so the port uses the saved agent's id.

Override: optional `PptBuilderConfig.labelling_model` (profile id), rendered as a selector inside the capability's own form widget (`ppt_builder_template`, no stock widget id), fed by the existing `GET /teams/{team_id}/routing-policy/available-models`; save checks only that the profile is known; usability and vision are enforced by the port. Unset → agent default.

**Vision toggle.** `PptBuilderConfig.use_vision: bool = True`. Off → the job makes no model call and labels by rules only. The selector shows only while the toggle is on and lists only vision-capable profiles. The form knows whether vision is possible from the existing `available-models` endpoint plus `effective-chat-model`, both extended with `supports_vision` (WP10). If neither the agent's resolved model nor any selectable profile has vision, the toggle is shown disabled and forced off, with "No vision-capable model is available for this agent; slides are labelled by rules". The job applies the same rule when the port is absent or refuses. `ModelProfile` gains optional `supports_vision`; capable profiles are flagged in `models_catalog.yaml`; the port fails closed when the resolved profile lacks it (→ heuristic labels, D2.3). Images go as LangChain `image_url` content parts. This touches the frozen runtime contract: dated entry in `RUNTIME-EXECUTION-CONTRACT.md` §8, and ships as its own PR (consolidation scope rule). Alternative — the capability reading the process-global runtime context directly — rejected: it bypasses the `RuntimeServices` boundary every capability is held to.

### D4. Background analysis with an owned table

- **Save** (`validate_config`): read the upload with python-pptx (an unreadable or oversized file still fails the save), after an archive pre-check that refuses a zip bomb before anything is inflated (`pptx_archive.open_presentation`: total uncompressed ≤ 512 MB, one member ≤ 256 MB, a member over 10 MB inflating > 100×; python-pptx inflates every member up front and the 50 MB limit bounds only the compressed size; every `.pptx` either capability opens from bytes goes through it), store the bytes via `agent_assets`, compute `template_sha256`, upsert a `pending` row, `spawn` the job with the bytes in memory and the save's `CapabilityModelPort`, return at once. Re-uploading the same file (same sha and labelling key) keeps a succeeded, current analysis instead of resetting it to pending; rebuilding a lost row from the stored asset returns that file's sha, not the client's. The stored config holds `template_sha256`, `use_vision`, `labelling_model` and the overrides — the inventory and `patterns_path` leave the config.
- **Store** `cap_ppt_builder_analysis`, one row per agent instance (replaced by the next save that needs a new analysis) matched on `(template_sha256, labelling_key)`, where `labelling_key` is `rules` or `vision:<profile id or agent-default>`, so toggling vision or changing the model re-runs the analysis: `status` (`pending|running|succeeded|failed`), `job_id` (a superseded job's writes match nothing), `attempts`, `lease_until`, `template_pptx` (so a re-run needs no user token), `inventory_json`, `patterns_pdf` (thumbnails), `error`, `team_id`, `saved_by`, timestamps. The job heartbeats the lease and writes the result in one transaction; it needs no Knowledge Flow token after the request.
- **Reads:** the middleware loads the row by `(instance, sha)`; a `succeeded` row is immutable, so a per-process cache keyed by the hash is replica-safe and costs one DB read per template per pod. The build renders the template bytes **from the row**, filtered on the config's sha, never the asset: a save stores the new asset before its config commits, so a turn on the old config would otherwise render bytes its inventory was not made from (it refuses instead). Template bytes are cached per pod by sha (4 entries; immutable, replica-safe). `GET /analysis/{instance_id}` (status + summary + inventory) and `GET /analysis/{instance_id}/patterns.pdf` serve the form; authorised for users who can **edit** the agent: there is no `agent_instance` FGA type; control-plane checks `TeamPermission.CAN_UPDATE_AGENTS` (`team.can_update_agents: team_editor`, `schema.fga`) on the instance's team (`product/api.py`). Capability routers are mounted with authentication only (`agent_app.py` ~4741), so the router checks the same permission on the row's `team_id` through the pod's `rebac_engine` (`runtime_context.py`, used as `check_user_permission_or_raise` in `agent_app.py`), exposed to capabilities as a small dependency (WP1).
- **Recovery:** a row whose lease expired is `interrupted`; the next readiness check, save or turn on any replica claims it atomically and re-runs it from the row's template, at most 3 attempts, then it is failed. The form shows "analysis interrupted" and that saving the agent re-runs it. Only a save carries the model port (the pod remembers it per process, so it is gone after a restart or on another replica): a readiness check or turn does not recover a vision-labelled row without it, which stays interrupted until a save re-runs it with vision (owner decision 2026-10-15, after re-runs from a restarted pod silently came back labelled by rules). A job that still runs without the port for a vision key logs a WARNING and records the labelling it really used (`rules`). A `rules` row serves a vision config (readiness and turns accept it), and the next save that carries a model port re-runs it with vision; a save without one leaves it.
- **Re-analysis on rule change (refresh):** a `succeeded` row older than `ANALYSIS_VERSION` stays in use (the agent is never blocked by a rule change) and is refreshed in place: the first readiness check, turn (an outdated inventory is cached per pod and re-read every 60 s, since its refresh may land on another pod or never; a refresh finishing on this pod drops the instance's entries) or save that sees it claims the row atomically (`claim_refresh`: still succeeded and outdated, lease expired, attempts left), which sets a new `job_id` and a lease but keeps `status`, inventory and thumbnails; the job runs from the row's template as any re-run, its heartbeats keep the row `succeeded`, and its `finish` writes the new inventory with the current version. A failed refresh keeps the old result, records the error and spends every attempt, so it is not retried automatically; an interrupted one is claimed again while attempts remain. A save forces a new refresh (attempts reset) unless one holds the lease. While a refresh holds the lease, `GET /analysis` reports `current: true`, so the form offers no re-run over it. `refresh_outdated(store, record)` is the shared helper (a platform-default template can reuse it). A vision-labelled analysis (labelling key not `rules`) is refreshed automatically only on a replica holding the model port its last save remembered: elsewhere the re-run would label by rules, so the old analysis keeps serving (developer decision, 2026-10-07), `current` stays false and the form says that saving the agent re-reads it with its vision model. A save forces the refresh with the port it carries (vision kept). There is no separate re-run route: it had no save context, so after a restart it re-ran vision analyses by rules.
- **Copy to another scope** (AUTHORING "Scope-private settings"): `template_key` is an `AssetKey` of the `template` slot, set only while `template_sha256` is (a validator derives it), so a copy re-submits an uploaded template to `validate_config` in the target, which stores it and starts a fresh analysis for the new instance; the built-in template has no file to copy. `labelling_model` and `PatternOverride.pattern_id` are `Public`: a catalogue profile the target team may not use falls back to rules, and pattern ids travel with the template. No analysis is reused across instances by hash.

- **Background CPU bound:** background python-pptx work holds at most 2 of the pod's 4 heavy-job slots, so a burst of refreshes (an `ANALYSIS_VERSION` bump) never leaves the turns' builds busy; a cancelled job (timeout, superseded) keeps its slot until its worker thread really ends.
- **Known gaps (deferred):** analysis rows are never deleted when an instance is deleted or the capability disabled (the SDK has no delete hook), so a deleted agent's row and template bytes stay in the table; the analysis routes answer 404 for an unknown instance before checking the caller's permission.

Alternatives: JSON result in the asset store (needs a valid user token when the job ends and a KF fetch per turn); Temporal worker in fred-agents (new worker deployment for a one-minute job); `fred_core.tasks` (closed union in a control-plane hotspot). The table is the smallest durable, replica-safe option that follows an existing capability pattern.

### D5. Agent unavailable until analysis succeeds

The agent itself is unavailable while its analysis is `pending`, `running`, `failed` or `stale`, reusing the existing suspension machinery: `AgentInstanceRow.suspension_reason` (`control_plane_backend/models/agent_instance_models.py`), closed enum `SuspensionReason` (`agent_instances/suspension.py`). Every guard already treats a non-null reason as unavailable: run → 409 (`product/service.py` ~3243), locked toggle (`AgentCard.tsx`), hidden from non-managers (`TeamAgentsPage.tsx`), chat picker / recents / search filter on `!suspension_reason`.

- Add `SuspensionReason.CAPABILITY_PENDING` (same column, no schema change) and an optional `suspension_detail` text so a failure can carry its message (`config_invalid` carries none today).
- Add one optional, generic SDK hook `AgentCapability.readiness(stored) -> Ready | Pending | Failed(message)` (`fred_sdk/contracts/capability/base.py`), served by the pod. Control-plane reads it after a save and in `run_capability_reconciliation_sweep` beside `reconcile_instance_config_health`, setting/clearing `capability_pending` / `capability_config_invalid`. No ppt-specific code in control-plane.
- ppt_builder's `readiness` reads its analysis row: pending/running/stale → Pending, failed → Failed(error), succeeded → Ready, including a succeeded row made by older rules, which it refreshes in the background (D4). Becoming available therefore waits for the next sweep or for the form's status poll, which asks control-plane to re-check the instance (WP10 picks one; no extra save needed).
- The reconciliation sweep has no production host, so listing a team's agents also re-checks its `capability_pending` instances (caller's token, ≤ 10 concurrently, 2 s bound, on the shared runtime HTTP client; no answer changes nothing); with the form's re-check poll, an agent becomes available on the next listing after its analysis completes. A failed preparation (`suspension_detail` set) is not re-checked there: it only changes on a save or the form's re-check. Over 10, a random subset is checked (stateless, any replica). The hook therefore runs on listings: it must return quickly, starting background work (the outdated refresh, interrupted recovery) without waiting for it.
- Only readiness verdicts set or clear `capability_pending`. A save, enrol or copy that validated its capability slices ends in one suspension write: none when the pod answers ready (the save resolves any earlier reason), else `capability_pending`; no answer after such a save fails closed to `capability_pending` without detail, lifted by the next answer. An older pod without the route (404) reads as ready. Every readiness write is compare-and-set on the reason read before the pod call, so a slow check never clears a suspension written meanwhile. A capability whose hook raised is reported `pending`, never omitted (omitted reads as ready).
- A copy goes through `copy-config`, which re-runs the capability's save in the destination: control-plane sends the destination team's routing parameters there and asks readiness once the copy exists.
- The pod's capability routes check the team the request names before building team-scoped services (the model port grants that team's models): `CAN_UPDATE_AGENTS` for validate-config and for both teams of copy-config, `CAN_USE_TEAM_AGENTS` for readiness (the listing's permission), with the route authorizer's rules (personal space, ReBAC off, security off). The model port re-reads the team's usable models every 30 s, since background jobs keep it.
- Failed or interrupted keeps the agent unavailable; the form shows the error and that saving the agent re-runs the analysis (the save carries the labelling model). `build_presentation` still refuses unless succeeded (defence in depth).

Control-plane, SDK-hook and frontend-gating parts ship as their own work package (WP10).

### D6. Rendering (kept, fixed)

Duplicate + fill stays the only way an example slide reaches the deck; layouts are instantiated as today. Fixes: `_duplicate_slide` copies only image/media/external-hyperlink relationships (slide-to-slide links dropped, their `a:hlinkClick` removed), copies `p:clrMapOvr` and the notes slide; the template's sections (`p14:sectionLst`) are dropped with its slides, since they list only removed slides and none of the copies (PowerPoint offers a repair otherwise) and their names mean nothing in a generated deck; `_write_lines` reuses the template paragraph's `a:pPr` of the same level for every level. A subtitle on a slide with no subtitle zone leads the body as an unbulleted line (as a column heading without its zone does), and step numbers 1, 2, 3… need no number zone (the order shows them): neither is lost content. Fill by slot, overflow (`fontScale` floor then word-boundary cut, reported), repeat-group item removal and recentring, image zones, lost-content reporting — unchanged.

**After-render check (`checks.py`):** any original non-shared slide text still present on a duplicated slide is removed and reported; overflow and lost content are reported. The tool fails closed: a slide that ends with no filled slot is an error (D8), never a silent sample slide.

### D7. The code chooses the slide

The plan per slide: `title`, `subtitle`, `bullets`, `columns`, `items`, `image(s)`, `notes`, then `kind` — last, optional. `pattern` and pattern ids leave the schema; the catalogue in the tool description lists the kinds the template offers with, per variant, the measured capacity of each zone (`≈C chars × L lines`, `items max N`), never ids, so the model writes to size on the first call. The plan coercion in `plan.py` stays.

`assign.py` maps the whole deck at once. A slide's candidate kinds, cheapest first: the requested `kind`, then the kinds inferred from its content shape, then every other kind; a candidate pattern must pass the **fit check** (every non-empty field has a slot, item count ≤ capacity, text within the stored capacity at the shrink floor). **Soft fallback:** a requested kind the template does not offer, or cannot fill with this content, or that the position forbids (`cover` not first, `closing` not last), is not an error: the slide goes to the best fitting pattern of a close kind (D21), and the success message names each substitution. Example slides outrank layouts of the same kind. A pass over the slides minimises misfit cost plus a variety penalty (deck-wide since D12) under **deck rules**: the cover only at position 1 (a default for a kind-less title slide there, never forced: D35); closing at most once and only last; never three identical archetypes in a row when an alternative fits (otherwise allowed and reported). `DEGRADATION`, `resolve()`'s last-resort fallback and the id loose-matching are deleted.

### D8. No silent fallback: actionable repair

If a slide fits no pattern of any kind (or a slide is empty), the tool builds nothing and returns `needs_revision`. Per slide it names the exact field and element that does not fit and the measured limit, measured against the closest pattern: "bullets[2] is 214 chars; this zone holds ≈40 chars × 3 lines", "items: 9 given, max 6", "subtitle: no place on this slide", with concrete options (shorten `bullets[2]` to ≈120 chars, trim to 6 items, split over two slides, a kind that holds the content). The tool remembers the previous `needs_revision` of the same call sequence: a slide with the same problem again is flagged as resent unchanged, or as changed with the problem still there, never repeated word for word. The success message no longer says "do not call again"; it lists substitutions and what the after-render check removed or truncated. The prompt fragment tells the model to fix and call again, with only the changes since D23.

### D9. Built-in Fred template

`builder/assets/fred_template.pptx` — a real deck designed by the developer, with example slides for every `SlideKind` except `team`/`other` — ships as package data with `fred_template.inventory.json` (the analysis plus the deck's sha256), regenerated by `make builtin-inventory`; a test fails when the stored JSON differs from what the pipeline now produces for the shipped deck (deck edited, `ANALYSIS_VERSION` bumped, heuristic changed). The stored analysis is rules only: regeneration stays deterministic and needs no model, and every example slide stands for its layout (D2.1), so vision would label all of them. No template configured → this pair is used through the exact customer render path. The `/theme` routes are replaced by `/builtin` (inventory) and `/builtin/patterns.pdf`; `theme.py` is deleted.

### D10. Review panel and overrides

Thumbnail + label + kind per pattern, example slides and layouts in separate sections (D13); the author may change label or kind and exclude/include. `PatternOverride` keeps `label`, `kind`, `included`; zone-role overrides and the zone-outline detail dialog are deleted. A kind change also sets `reusable` from the new kind: the author's choice wins over the analysis's one-off verdict (an `other` slide, or vision's `reusable: false`), as a `kind:` note does; re-kinding to `other` makes the slide unused, and an override repeating the analysed kind changes nothing. Nothing is mandatory. The form shows the D4 status while pending.

### D11. Evaluation harness

`eval/` in the package, run by an opt-in `make eval` (never in `make test`): N prompts × templates through the real analysis, the real `build_presentation` tool and the configured LLM in a minimal ReAct loop with in-memory ports. Metrics per deck: first-call success, distinct archetypes / slides, cover exactly once at 1, closing at most once at the end, no three in a row, leftover sample text, overflow, lost content, repairs. Templates: the local "PPT Corporate" agent's `config/ppt_builder_template.pptx` (path given by env var, never committed) and the built-in one. Results go into `verification.md`.

### D12. Deck-wide variety: each template slide once where possible

Found on the "Paintress" template (48 patterns, 12-slide deck alternating two `bullets` slides): the assigner only prices adjacency (`_REPEAT`, `_TRIPLE`, `assign.py:65-66`, `_viterbi` 454-457), so A B A B is free; the icon cards (`slide:272`, `slide:273`) lose because (1) every cards slide of that template has one text field per item, so the natural `heading` + `text` item fits none of them (`_unused_item_fields`, `render.py:797`) and falls to `process`; (2) an empty item image zone costs nothing (`assign.py:290-292` reads top-level zones only), so `slide:266` ties `slide:272` at 0 and wins by order, then renders with its pictures removed; (3) the catalogue quotes 4 variants per kind (`_MAX_VARIANTS`, `tools.py:129`), hiding `slide:273`; (4) layouts 10/11 stay beside the slides that copy them (D13), doubling identical designs. `Pattern.preferred` is computed (`analysis.py:690`, `labelling.py:301`) and read nowhere.

- **Reuse cost.** A pattern already used k times in the deck costs `_REUSE × k` more (anywhere, not only adjacent); it outweighs `_LAYOUT` and the fit costs, and stays below `_KIND_STEP` for the first reuse, so an unused pattern of the same kind tier wins, a second kind tier wins only from the second reuse. Deck rules stay hard. The second-order Viterbi is replaced by a beam search whose state carries the use counts and the last two choices (decks ≤ ~30 slides, bounded beam): same rules, global term.
- **Honest fit costs.** An empty item image zone costs `_IMAGE_HOLE` like a top-level one.
- **Item heading without a heading zone** leads the item's single text zone in bold (as a subtitle leads the body, D6), counted against its capacity; lost only when it does not fit.
- **Catalogue:** every distinct variant per kind, each with its label (`cards: Three icon cards: items max 3 [text ≈12 × 2] | …`), no cap; the description asks to vary content shapes (items, columns, figures) rather than bullets everywhere.
- **Variety note:** when a pattern is used ≥ 3 times, the success message names the slides and the unused variants with their sizes, so a correction pass can recast one.
- **Icons** stay the template's decoration (group members or small pictures, never slots); never swapped. A decoration that overlaps a removed item is removed with it.
- `Pattern.preferred` is deleted (consolidation: dead field).

Alternative — a hard "never reuse" rule — rejected: small templates must still build a long deck; the cost keeps reuse possible and reported.

### D13. Review dialog: example slides first, layouts apart

An example slide that **holds every slot of its layout** stands for it even when it also draws decoration (D2.1 required "nothing else drawn"): picture placeholders count as slots, not as drawn extras (`_copies_layout`, `analysis.py:1096`, made `layout:10/11` survive beside `slide:266/267`). On Paintress this removes 6 of 10 layouts. A slide whose placeholders share an `idx` (`slide:267`: two `ph:16`) gets distinct zone keys and a pattern warning.

The dialog shows three sections: **slides of the deck** (included example slides), **layouts** (collapsed, "used only when no slide of the deck fits"), **excluded**. CSS fixes: `.cardHeader` uses `minmax(0, 1fr) auto` (its `1fr` took the native input's min-content and pushed the switch out of the card), the label `TextInput` is `compact` (its empty hint row made the gap above the kind `Select`), the switch is `small`, the thumbnail page is sized to its box.

### D14. Tables: fill a table the template holds

Paintress slide 5 (`slide:300`) holds one `a:tbl`: 12 rows × 5 equal columns (173 pt), `firstRow="1" bandRow="1"`, table style "Medium Style 2 – Accent 2", empty cells (only `a:endParaRPr lang`), no merges, no cell fills, text 18 pt (presentation default); it is excluded `table` (`analysis.py:1054`). Slide 24 (`slide:278`, "Timeline 1 an") is a 6 × 13 Gantt grid whose bars are per-cell `solidFill`: a drawing, not data.

- **Analysis.** A table covering the slide's main area is a **table zone** (role `table`) when it is a data table: ≥ 2 columns, no `gridSpan`/`rowSpan`/`hMerge`/`vMerge`, body cells empty or sample text, no per-cell fill that varies across body cells. Otherwise the slide stays excluded (`table`). The zone stores the header flag (`firstRow`), per-column `chars_per_line` (column width − cell margins, cell font: run → `endParaRPr` → presentation `defaultTextStyle`), the line height and `max_lines` = the lines the template's rows show (here 11 body lines). Kind `table`; vision compatibility: a table zone.
- **Plan.** `table: {header: [str], rows: [[str]]}` on a slide; ragged rows are padded (coercion); `infer_kinds` → `table` first. Fewer columns than the template: trailing columns removed, the others widened to the same total width; more → misfit. A table on a template with no table slide is a misfit (D8), never turned into bullets.
- **Fit.** Each row takes the wrapped line count of its tallest cell; the body's lines must fit `max_lines` at full size or at the shrink floor (one font scale for the whole table). Cells are never cut: `table: 18 rows need ≈22 lines; this table holds ≈11 (≈14 at the smallest size); longest cell rows[3][2] 120 chars, its column holds ≈17 chars per line`.
- **Render.** Header and cells written with the cell's `endParaRPr` attributes, colours left to the table style, `**bold**` allowed; rows grown by cloning the last body row (cleared, fresh `a16:rowId`) or removed from the bottom; columns removed with their `gridCol`; frame height set to the rows' sum; shrink sets one `sz` on every run.
- **Checks / preview / eval.** No template cell text left; the frame stays on the slide; shrink reported. The patterns PDF shows the table (LibreOffice's rendering of built-in table styles to be checked). Eval prompts with tabular content (offers × criteria, a schedule); metrics: table used when given, shape kept, no overflow.

### D15. No dropped text; variety asked once, on the first deck

Found in a real session (`mistral-small`, Paintress): four slides sent `"columns": {"bullets": [...], "heading": "Espagne", "heading2": "Italie"}`. The column coercion read `heading`/`bullets` and dropped `heading2` without a word, the deck showed one column, and the only signal was the passive note "Slides 4, 7, 10, 13 all use the template slide '2 colonnes de texte'" (the plan repeated section → two_columns → table, the columns restating the table). The eval's `lost` metric read the renderer's report, which never saw the key.

- **No silent loss.** The plan coercion keeps every key it cannot map as an ignored field, on slides, columns and items alike (`heading2 'Italie'`); a field given twice (`bullets` and `text`) is merged, not first-wins; a bullet written as `{heading, text}` keeps both. The assigner turns ignored fields into a `needs_revision` problem naming the slide and the field, and so does an unbalanced group: in `columns` or `items`, when one entry has both a heading and a body, an entry with a heading and no body (or a body and no heading) is a problem (`columns[1] has heading 'Italie' but no bullets`); an item's `number` counts as its heading and its `text` as its body, and a number with its label is a whole entry, so figures and agendas (headings only) stay whole lists. The renderer's ignored-field warning is deleted (unreachable). The eval's `lost` counts every text string of the raw tool arguments absent from the delivered deck.
- **Variety as a revision, first deck only.** When the assignment uses a non-structural template slide (not `cover`, `section`, `agenda`, `closing`) three times or more and the template has an unused variant of its kind or an unused slide of another non-structural kind, the tool returns `needs_revision` once, naming the repeated slides and the alternatives with what each suits (figures for short numeric items, timeline for dated items, cards for parallel items…). It says a resend of the same plan is built as is, and the next call is accepted whatever it holds (one ask per tool instance, i.e. per turn). It applies only while the conversation has no deck yet, read from the conversation history: the middleware keeps the messages of the turn's last model call, and an earlier `build_presentation` tool message whose text is a delivery (`Delivered: '…'`, or `The presentation '…' … is ready` without a preview) means a deck was delivered, so a later turn, where the user may ask for specific slides, keeps the passive note. A `needs_revision` or an error delivers nothing, so a history holding only those is still a first deck. The history is read only when a revision would otherwise be returned (no added work on the usual call). Earlier turns' tool messages reach the model through the runtime's transcript, but the platform's checkpoint hygiene clears every message `name` before any capability middleware sees the model request (WP35, found live: the ask came back on turn 3), so a result is recognised by the `tool_call_id` of the `AIMessage` call that named `build_presentation` (or its own name when present), its text read from a string or from text blocks; a history trimmed before the delivered deck makes the next `slides` deck count as a first one again (at most one more ask, a resend is built); a `changes` call is never asked, since its stored base is a delivered deck (WP38: a trimmed history re-asked variety on slides the user never touched). This replaced listing the session's outputs folder (`workspace_fs.ls`), retired when the SDK `WorkspaceFsPort` became write-only upstream; with no listing the ask never fired in production. Rejected: a new per-session store (the history already records it).
- **Choice guide.** The tool description replaces its "vary the content shapes" sentence with a short guide built from the offered kinds: numbers → figures, dates → timeline, parallel items → cards, ordered steps → process, a comparison → table (not restated as columns before it); each slide should look different.

### D16. Variety by kind, with alternatives read from the content

Found in a real session (`mistral-medium-3.5`, reasoning off, Paintress, first deck, one call, no ask, no note): kinds `[cover, agenda, bullets, two_columns, bullets, two_columns, bullets, table, bullets, bullets, closing]`. The five `bullets` slides landed on five different template slides ('Message clé', 'Texte', 'Vide', '1_Blank', 'Titre et contenu'), so the D15 trigger (one template slide 3+ times) never fired, though the deck showed five near-identical lists. A template slide used 3+ times is still one (it is a kind used 3+ times). Everything else of D15 stays: asked once, first deck only, resend built, structural kinds exempt. The passive note on later decks names the kind repetition too ("Slides 3, 5, 7, 9, 10 are all 'bullets' slides").

Rejected: a hard cap on `bullets` in the assigner (the content is bullets as sent; recasting it is the model's job); an LLM call to classify the content (cost and latency per call for what a few patterns catch).

### D17. Variety asked on the first call only, with what each suggestion holds

Found by the WP17 eval (`mistral-small`, 78 like-for-like runs): the kind-level ask fired on most first decks (59 asks against 9), success fell 73 → 63, first-call 21 → 7, tool calls +39 %. 13 of the 15 failures had an ask, and in most the recast deck then failed the fit check: items sent to figures/process slides with no label or number zone, four columns on a two-column slide. The ask said which kind to use, not what that kind's slide holds, and it came after a fit repair, costing a round of its own.

- **Timing.** The ask is evaluated on the first `build_presentation` call of a turn whose plan is evaluated only (first deck of the conversation, D15); a call refused before evaluation (unreadable, empty, bad changes) does not use it up (WP38). When that call also has fit problems, the ask is **merged** into the same `needs_revision` (the problems, then the variety block): the model fixes and recasts in one round, so the ask never costs a round of its own, and a recast that brings new fit problems gets them back on the second call, as any repair. A later call of the turn is never asked, whatever it holds: no ask after a fit repair, and a resend is built (D15). The assigner therefore also computes repeats when some slides fit nothing. A slide with a fit problem counts on the template slide it would take once fixed: its closest fit (the pattern its problem names, `closest fit, a '<kind>' slide`) or a variant of that kind with no other problem, under the same caps, structural and revisable rules; so slides that repeat while each has a fit problem are asked in the same round (live Paintress call, `variety_max_uses` 1: a `label` on the items of two cards slides hid their repeat, and the repaired deck broke the max). An option or suggestion offered for such a slide never names a template slide that has the same fit problem. A slide with no closest fit (no slide takes its position, a table on a template without one) or whose text would be dropped is left out of the count. Rejected: asking only on a clean first call (a first call with a fit problem is the usual case on a weak model, so most decks would never be asked, and the ones asked would still pay a round); asking after the fit repair (the WP17 behaviour this replaces).
- **Fit hints.** Each content-based suggestion states what the suggested slide holds, read from the inventory: for a kind with items, `up to N items [number ≈C chars, text ≈C chars × L lines]` with the plan's item field names (so a figures slide says `number` and `label`, not `text`); for `two_columns`/`comparison`, `exactly 2 columns [heading ≈C chars, bullets ≈C chars × L lines]`. The variant quoted is the one the assigner would favour for that content: it holds the entries and the longest entry (a misfit is no candidate, an empty picture only a cost), then has no item picture to leave empty, is an example slide rather than a layout, then has the most room per entry; a field the analysis could not measure adds no room. When the slide's longest entry is longer than that room, the hint adds `shorten each entry to ≈N chars`. A kind no variant can hold (too few items, not exactly two body zones for two groups) is not suggested (D16). The hint reuses the catalogue's zone wording (`zone_summary`), so the description, the problems and the ask quote the same sizes.

### D18. Variety check as a setting; suggestions capped by the template

Found in two live sessions on Paintress (WP18 code). `mistral-small` (reasoning on): the first call had 2 `bullets` slides, yet got a merged ask for `slides [2, 4, 7]`, slide 2 being the agenda (asked `agenda`, too long for the agenda slide, built on a bullets slide by the soft fallback, so counted as `bullets`). The ask had no `suggested` line, only the generic options, `figures` first; the model recast slides 2, 4 and 7 to `figures` beside the two figures slides already there: 4 slides on Paintress's single figures slide (`Four KPI figures`), the agenda rendered by fallback, and, the ask being first-call-only, that deck was delivered. `mistral-medium` (reasoning off) ignored the ask and resent: its deck was the most varied (5 bullets of 16).

- **Structural slides are never in a repeat.** A slide is structural when its requested kind (or, with none, its first inferred kind) or its template slide's kind is `cover`, `section`, `agenda` or `closing`. It is grouped apart (by template slide, never revisable), so it neither counts towards a content repeat nor is named in an ask. The small-model plan above then has 2 bullets slides and no ask.
- **Caps.** Each kind gets a budget: its distinct variants in the catalogue minus the deck's slides already of that kind (a slide with a fit problem counts by its closest fit's kind, D17). A content suggestion (`suggested`) and an option of another kind (`options`) are given only while that kind's budget is above zero, each suggestion using one, shared across the repeats of one answer; Paintress `figures` (1 variant) beside 2 figures slides is never offered. Each slide gets one suggested kind: among those its content suits, the one suggested least so far (spread across kinds), so `two_columns or cards` alternatives go.
- **Setting `variety_check`** on `PptBuilderConfig`, values `template_slide` (default: ask when one non-structural template slide is used 3+ times, the D15 trigger), `kind` (ask when one non-structural kind is on 3+ slides, D16), `off` (no ask). Timing (first call of the turn, merged with fit problems, first deck only: D15/D17), caps and structural exclusion apply to both asking modes. The passive note stays in every mode, grouped as the mode groups (`off` groups by kind). A generic `FieldSpec` (`type="select"`, `enum`), rendered by the agent form's `TuningFieldRenderer` beside the plugin widget, option labels under `capability.ppt_builder.fields.variety_check.options.*`. Not in `labelling_key`: read per turn by the tool, no re-analysis; a stored config without it validates to the default.

Rejected: changing the default to `kind` now (the head-to-head eval decides; the developer chooses); a per-turn chat control (an author's choice, not a user's).

### D19. Max uses as a setting; one variety row in the widget

The WP19 eval showed `template_slide` nearly inert (the fixed "3+ uses" trigger rarely fires, since D12 already spreads template slides) and `kind` effective but tied to the same threshold. The developer approved an author-set maximum.

- **Setting `variety_max_uses`** (int 1..5, default 2) on `PptBuilderConfig`. 2 is the D15–D18 threshold (asked from the 3rd use); 1 means every content slide unique. With `variety_check: off` it does nothing (switch off = no enforcement). Not in `labelling_key`; a stored config without it validates to 2.
- **Realistic cap.** The max never applies below what the whole deck forces: one deck-wide cap per mode, `max(max_uses, ceil(n / v))` for every template slide, `n` the non-structural slides that fit (a slide with a fit problem counted on its closest fit, D17), `v` the non-structural template slides of the pool; in `kind` mode the kind cap is `max(max_uses, ceil(n / k))`, `k` the distinct non-structural kinds of the pool. Computed once per `assign` (`_caps`), before the beam, and reused by the ask, so the cost and the ask agree. Structural slides (D18) are exempt everywhere. Not per kind: a cap raised to a kind's own slides over its own variants (five bullets slides on a template with one bullets variant → five) would silence the very ask that recasts those slides into other kinds; reuse is forced only once the deck has more content slides than the template has content slides (or kinds). (An earlier draft of this paragraph described the per-kind cap; the code was always deck-wide, benchmarked in WP20–WP22, and is kept.)
- **Assigner.** The D12 `_REUSE × k` cost stays; when the check is on, each content use of a template slide beyond its cap adds `_OVER_MAX` (100), above `_KIND_STEP` and the fit costs, below `_TRIPLE`: another variant of the same tier wins while one fits; a requested kind is still its slide's only tier (D7), so the cost never switches it. The assigner prices template slides in both modes (the one thing it chooses); `kind` mode counts kinds for the ask.
- **Ask threshold.** A group (template slide or kind, per mode) is a repeat when its slides exceed its cap; timing, merge with fit problems, first deck only, resend built and suggestion caps (D15–D18) unchanged. Each variety entry carries `at_most` (the cap), so the model knows how many slides to recast. `off` keeps the passive note at 3+ slides of one kind.
- **Choice guide.** The "each slide should look different, at most 2 bullets slides" sentence goes; when the check is on: max 1 → "Each slide of the deck must look different."; otherwise "Use any variant below at most N times per deck" (`template_slide`) or "Use any kind below on at most N slides per deck, cover, agenda, section and closing aside" (`kind`). The bullets cap goes (the max covers it).
- **UI.** Both fields carry `ui=UIHints(widget="ppt_builder_template")`: the plugin widget renders one row, "Enforce variety [By slide name ▾] at most [2 ▾] times each", switch at the end (the vision row's pattern; a `div`, not a `label`, so the selects never toggle it). Switch off writes `variety_check: "off"` and disables the selects (stable layout); switch on restores the last mode seen while the form is open (default `template_slide`). The generic select field and its option labels are deleted.

Rejected: a per-kind max (one number is what an author can reason about); hiding the selects when off (the row would jump).

### D20. Limits where the model writes, build directly, no empty picture frame

Found by the WP20 eval and a live deck. Fit problems are the first cause of failed first calls: in WP20 cell 2 (`mistral-small`, `template_slide` max 1), 5 cover subtitles over the cover's ≈32 chars and 5 figure labels over ≈12 chars; the sizes were only in the description's catalogue, far from the fields. `mistral-medium` answered 2 of 14 first requests with a plan and a question (`no_tool_call`), as the fragment told it to "settle the outline" when the request looked vague. On Paintress, 'Nos quatre priorités stratégiques' (3 items heading + text, `kind: cards`, no images) landed on `slide:266` "3 colonnes d'image + texte": its three picture placeholders were removed, but its layout draws a full-width grey `Rectangle 2` behind them (y 25–49 % of the slide), which no slide can remove, so a grey band stayed between the title and the texts. `_IMAGE_HOLE` could not prevent it: a requested kind is the only tier (D7), and `slide:266` was the only `cards` variant holding that text.

- **Field limits in the schema.** Each text field of the tool schema (`title`, `subtitle`, `bullets`, `columns[].heading`, `columns[].bullets`, `items[].number|heading|text|label`) carries the template's room in its JSON-schema `description`, from the same zone mapping and measurement as the catalogue (`zone_summary`). Per kind, the room is the largest of its variants' (each variant quoting its tightest zone for that field, as the catalogue does), so a text within it always has a slide of that kind; the hint states the most common room across the kinds and lists the kinds that differ: `Room: ≈71 chars; cover ≈32 chars × 2 lines, figures ≈12 chars`. The cover is one fixed slide, so its room is exact. An item heading written atop the text (no heading zone) shares the text's room. Descriptive only, never `maxLength`: a schema violation would make the provider reject the call instead of the tool returning `needs_revision`. The schema stays cached, keyed by the offered kinds and the hints (identical inventories share it).
- **Build directly.** The fragment tells the agent to write the plan and call the tool in the same answer, asking to validate an outline only when the user asked for it or the request does not say what the presentation is about.
- **A picture zone framed by its layout needs a picture.** The analysis flags an image zone `framed` when a shape of the layout or master that no slide can remove (not a placeholder, no text, under half the slide's area, so never a background) covers at least half of it. The fit check treats a framed picture left empty (no slide image for a slide zone, no item image for a used item) as a misfit; the build tool fetches the plan's pictures before assigning and counts only those that open as an image (an invalid id is dropped and reported), so the slide goes to another variant or kind (soft fallback, D7) and only a plan with pictures gets that slide; the catalogue quotes such pictures as `image (required)` / `images×N (required)`. Unused items' pictures are removed with their items as before. On Paintress (and corporate) this flags `slide:266` and `slide:267` (layout bands behind their picture rows) and no other picture zone; on the built-in deck, "Pairing text with a visual" (its layout draws a panel exactly under the picture). `ANALYSIS_VERSION` 11 (stored analyses are refreshed in the background when first seen, the agent staying available; a vision-labelled one only where its model port is, otherwise at the next save, D4). Rejected: raising `_IMAGE_HOLE` (a requested kind is the only tier, so the cost never switches it); hiding the layout's shapes on the slide (`showMasterSp="0"` also hides the logo and footer); removing slide-level decoration over an emptied picture (no such case in the three templates: not added).
- **Eval agent prompt.** `eval/run_eval.py --agent-prompt <file>` replaces the short stand-in agent prompt with an author's prompt; `eval/agent_prompts/agent_prompt_fr.txt` holds a candidate prompt for agent authors, measured against the stand-in: no gain on the measured path, not suggested as is (verification.md, WP21). A short prompt (`agent_prompt_short_fr.txt`: stand-in + no invented figures + one- or two-sentence answer) was measured next (WP22): replies get short, but mistral-small then rebuilds the deck after delivery on most turns and neither model stops inventing figures without documents; not suggested either. No author prompt is suggested; the eval keeps the stand-in.
- **Variety default kept.** `template_slide`, `variety_max_uses` 2 (the code default). Max 1 scored slightly better in the WP20–WP21 benchmark; the developer validated max 2 in real sessions with mistral-small and mistral-medium and keeps it (2026-10-07).

### D21. Fallback only to a close kind; every message actionable

Found live (Paintress, `mistral-small`): an `agenda` slide with 9 items, where the agenda slide (SOMMAIRE) holds 8 [number, heading ≈19 chars × 2 lines]. The D7 fallback went on to the content-inferred kinds and built it on a `team` slide (15–22 items); the note said only "built as 'team' instead of 'agenda' (no 'agenda' slide holds this content)". The model resent the same 9 items three times.

- **Close kinds.** A requested kind falls back only to the kinds of `CLOSE_KINDS` (`assign.py`), in preference order (a list over the kind's largest slide first continues on a second slide of the same kind, D24; the close kinds come after); the inferred and "any kind" tiers apply only when no kind is requested (or `other`):

  | Requested | Close kinds, in order |
  |---|---|
  | cover | section |
  | agenda | bullets, process, timeline |
  | section | quote |
  | bullets | two_columns, cards, image_text |
  | two_columns | comparison, table |
  | comparison | two_columns, table |
  | table | comparison, two_columns |
  | cards | bullets, two_columns, comparison, process |
  | figures | cards, bullets |
  | process | timeline, bullets |
  | timeline | process, bullets |
  | team | cards |
  | quote | section, bullets |
  | image_text | bullets, two_columns |
  | closing | section, bullets |

  A list stays a list (agenda, process, timeline, bullets); grouped content stays grouped (two_columns, comparison, table); title slides stay title slides (cover, section, quote, closing). `quote → bullets` and `closing → bullets` keep the same structure (a title and one text block), so a statement or contact lines still build. `cards → process`: the same item shape (heading + text blocks), the mildest shift on offer (numbering suggests an order); without it, a cards slide whose only variant frames empty pictures (D20) fails instead of building. Item kinds cannot take bullets or columns and the reverse: such a close kind is never a candidate for that content, only an option in the revision. Never: agenda → team/figures/cards, or any kind to an unrelated one.
- **No absurd substitution.** When neither the requested kind nor a close kind fits, the slide is a `needs_revision` problem measured on the requested kind's closest slide (when that kind is absent or forbidden at this position, on the closest close kind's, led by `<why>; closest close kind, a '<kind>' slide: …`; otherwise `closest fit, a '<kind>' slide: …`; a first slide forced onto the cover takes only the cover prefix, never the close-kind lead). The item count names that kind's largest slide, not the template's: `items: 9 given; the largest 'agenda' slide holds 8`, options `trim to 8 items`, `split the items over two slides`, what the slide takes, then up to three close kinds with what each takes. It is counted for variety on its closest fit and merged with the first call's ask (D17): never a round of its own. A kind with neither its own slides nor a close kind in the template: "leave `kind` out".
- **Substitution note.** What, why, how to get the requested kind: `Slide 2: built as 'process' instead of 'agenda': the 'agenda' slide does not fit (items: 9 given, max 8). To get the 'agenda' slide, call again and trim to 8 items or split them over two slides; otherwise nothing to do.` A kind unavailable there: `…: this template has no 'timeline' slide. Nothing to do.`
- **Message rule.** Every text `build_presentation` and `list_images_in_folder` return states what happened, why, and one concrete remedy, or "nothing to do". Results that build nothing start "No deck was built"; a render error says whether to resend the plan or have the owner save the template again (it changed since its analysis); review notes give a remedy per element (`not placed: subtitle (move it to a field this slide shows, or drop it)`); misfit options name an edit that fits (`give the bullets as items (at most 8)` on an items-only slide, not `drop bullets`; a fixed slide: `send only the title '<label>'`); in `changes` mode a `drop <field>` option for a whole slide field carries the exact change that does it (`drop bullets: {"op": "edit", "slide": 10, "field": "bullets", "value": []}`, WP39), a refused `slides` call keeping the words. Kept: the `Delivered: '` / `The presentation '` prefixes (`deck_delivered`); `Ignored:` went with the argument-keyed duplicate guard (D26). **Renderer findings** the after-check report does not carry go to `DeckReport.notes` and join the review notes, phrased by the same rule: the agenda gap (`Slide 2: the agenda announces 6 parts but only 2 slide(s) follow it. Add the missing slides or remove those parts from the agenda; otherwise nothing to do.`), a one-line heading or label running into the text below (shorten to under N characters), an items slide given no items (give that content as `items`), content sent to a fixed slide, a table the render cannot fit (its measured cause and remedy, instead of `not placed: table`). The last three are defensive (the fit check stops them first). The render reports through `DeckReport` only: truncations, removed example text, dropped items, lost content, unusable images and a table off the slide are in its per-slide report, skipped entries in the tool's notes (WP38 deleted `RenderResult.warnings`, a log-only copy).

Rejected: keeping the inferred tier after the close kinds (that is where `team` came from); refusing every substitution (loses the D7 first-call gain on templates that lack a kind); converting items to bullets for a bullets fallback (a renderer change; the revision option asks the model instead).

### D22. Limits phrased in words

Found by the WP21 eval: with the figure-label room in the schema ("figures ≈12 chars"), `mistral-small` still wrote 18–40-char labels (6 too-long labels in cell A, first-call success 3/14). Small models do not count characters; they follow a word count.

- **One rule, every template.** Wherever the model reads a room (catalogue, schema hints, `needs_revision` reasons and options, the kind advice), `capacity_text` quotes a word budget first, then the measured characters: `≤4 words (≈32 chars)`, `≤20 words (≈71 chars × 2 lines)`, `1 word (≈12 chars)`. Words per line = `floor((chars per line + 1) / 7)` (the last word needs no space), times the lines, since a word never spans two lines; at least one, "1 short word" under 6 chars per line. Nothing is tuned per template: the only input is the room the analysis already measures.
- **Ratio 7 chars per word, space included.** French prose averages about 5 letters per word (6 with the space), business vocabulary runs longer ("stratégique", "déploiement"): 7 errs on the short side, so the budget never promises more room than the characters allow on typical text. The characters stay quoted next to it.
- **Unchanged.** The rooms, the fit check (characters), the targets of the options (the same `per_line × lines`), the schema (no `maxLength`) and the reason's leading `<field> is N chars` measure.
- **No example from the template's sample text.** Considered (`label: 1 word, like 'Clients'`) and dropped: on Paintress every sample that fits its zone and is not placeholder text is either a slide name describing the layout ("3 colonnes d'image + texte", "Planche à puces") or a number ("01", "2022"); the label samples are "KPI #1", "Nom", "Changer ce texte". An example would be template-dependent, mostly absent, and misleading where present.

Rejected: per-kind or per-template ratios (template-dependent); words only, without chars (the fit check counts chars, and the model needs the target it is judged by).

### D23. Changes against the previous plan, whole deck re-rendered

Two needs, one mechanism. (a) A `needs_revision` naming two slides of twelve made the model resend all twelve, and weak models reworded or dropped slides they were not asked to touch. (b) A later-turn request ("add a key-figures slide per country", "put this phone number on the last slide") had the same cost and risk. Developer constraint: render quality must not change, so a change never patches the generated file — the tool applies the changes to the stored plan and the **whole resulting plan** goes through the normal path (assignment, fit check, variety rules, render), exactly as a full `slides` call.

- **Schema.** `build_presentation` takes `slides` (the whole deck, unchanged) **or** `changes`, a list of operations whose slide numbers are the **previous plan's** (1-based, never shifted by earlier operations of the same list):
  - `{op: "replace", slide: N, slides: [slide, …]}` — slide N becomes these slides;
  - `{op: "insert", after: N, slides: [slide, …]}` — after slide N, `0` = at the start;
  - `{op: "remove", slide: N}`;
  - `{op: "edit", slide: N, field: "items[2].label", value: …}` — one field of slide N: a slide field (`title`, `bullets`…), an element (`bullets[1]`, `columns[0].heading`, `items[2].text`, `table.rows[3][1]`); indexes from 0 as in the tool's messages; `value` null removes a list element, an index equal to the list's length appends one; a whole field set to `[]` (a list) or null (a text, a table) is cleared. The edited slide is re-coerced as any slide.
  Operations are applied all at once on the base: untouched slides are the base's own objects (byte-identical in the plan); inserts after the same N keep their order. `file_name` left out keeps the base's. A `replace`/`insert` whose slide fields sit in the change itself (`{op, slide, title, items}`, no `slides`) is read as that one new slide (WP35, seen live); slide fields beside a non-empty `slides`, or on an `edit`/`remove`, are refused with what, why and the remedy (put them inside that slide's entry of `slides`; for an edit, write `field` and `value`).
- **Actionable errors, nothing built**, all bad operations listed at once (`changes[2] (remove): slide 14 does not exist; the previous deck has 12 slides. Use a number from 1 to 12.`): unknown `op` (the four listed), a number out of range, `insert` without `after`, `replace`/`insert` without slides, `edit` without `field` or with a path the slide does not have (`items has 3 entries, items[0] to items[2]`) or a field that is not a slide field, two operations replacing/removing the same slide, an edit on a replaced or removed slide, `slides` and `changes` both non-empty. **No base plan** → `No deck was built: there is no previous deck in this conversation to change. Send the whole deck in slides.`
- **Base plan = the last deck delivered** in this conversation and agent, **as delivered** (D24: a split list's parts are slides of their own, entries that were not slides are gone), so a delivered deck's numbers are its file's. Within a turn, the tool instance keeps in memory the last plan it evaluated, so a fix after `needs_revision` (fit problems or a variety ask) applies to the refused plan; that plan is never stored (WP38, found in review: a refused plan became the next turn's base, so the user's next change applied to a deck they never got). An error before evaluation (unreadable or empty plan, bad changes) or after it (busy, template load, render or upload failure) does not replace the base, so a retry of the same call applies to the same base. Pictures that did not load are dropped from the delivered deck, as from the evaluated plan.
- **Where it lives.** A capability-owned table `cap_ppt_builder_deck_plan` (same Alembic tree as the analysis), primary key `(session_id, agent_instance_id)`, holding `plan_json` and `updated_at`: one small upsert per delivered deck, read only when a call sends `changes` and the tool instance has not already evaluated a plan this turn (the turn's own last plan is kept in memory). Replica-safe (any pod reads it) and independent of history trimming. No session id (a test or eval context without one) → memory only. A failed write is logged, never fatal: the deck is still delivered; the next turn's base is then the previous stored plan (the risk is a stale base only after a database failure). Rejected: rebuilding the base from the conversation history (tool-call arguments are trimmed with history, and a `changes` call would require replaying every earlier call); patching the generated `.pptx` (a second render path, and the assignment and variety rules could no longer see the whole deck).
- **Corrected resend.** Found by the eval (`mistral-small`): after a refused `insert`, the model resent the corrected `insert`, never a `replace` of the refused slide, and each call inserted one more copy into the refused plan. So when a `changes` call has the same **shape** (per change: `op`, `slide`, `after`, `field`, content aside) as the call of this turn that produced the base, it is applied to that call's own base, not on top of it: a corrected or identical resend replaces the refused changes, never adds them twice; this also keeps "send the same call again: it will be built as is" (variety ask, D15) true. A fix numbered on the refused plan (`replace` of the listed slide) has another shape and applies to the refused plan. The parent is kept in memory for the turn (resends happen within it), and only until a delivery: the same changes sent after a delivered deck are a new change to it (WP38: two inserts of one shape in one turn replaced each other). The `needs_revision` of a `changes` call therefore asks for "the same `changes`, corrected (all of them: they apply to the deck before them)"; a refused `slides` call asks for `changes` on the listed numbers. Limit: a resend that drops some of the earlier changes while keeping an insert has another shape and stacks.
- **Schema cost.** Change slides are plain objects in the schema (`written as in slides`), validated as slides in code: typed as the slide model, LangChain inlined the whole slide schema under `changes` and the tool schema went from ≈5 k to ≈10 k chars on every model call (+33 % input tokens in the eval). `slides: null` beside `changes` and one change sent as an object are read, not refused by validation.
- **Everything else unchanged on the resulting plan**: first call of the turn (D17), `deck_delivered` from history (D15), misfit closest-fit counting (D17), the repeated-problem flag (D8, by the new plan's slide numbers), success prefixes. Messages use the resulting plan's numbering; `needs_revision` ends "call build_presentation again with only `changes` for these slides (numbers as listed), or the whole deck in `slides`"; a delivery says to change it later with `changes`.
- **Description and working rules.** Both modes in a few lines: a new deck → `slides`; a fix after `needs_revision` or a change the user asks for → `changes`, which keeps the other slides exactly as they are. The fragment's "regenerate the whole deck" goes. Text inside a slide changes with `edit` (the slide keeps its design); `replace` is for a different slide.
- **Design kept (WP35).** Found live: a `replace` of the closing slide meant only to change its text moved it to another closing template slide (its envelope icon lost). Each slide of a delivered deck stores the template slide it was built on (`built_on`, hidden from the schema). A slide carrying one keeps that template slide alone while it is among the fits of the best-ranked kind (the requested kind, or its close kinds when the requested kind fits nowhere: a timeline built on a process slide stays there, WP38); otherwise it is assigned as any slide. `built_on`, `asked_design` and `asked_from` are never read from the model's call: every sent slide drops them, only delivery and `like` set them (WP38). A `replace` gives its first new slide the replaced slide's `built_on`, an `edit` keeps it, a corrected resend applies to the same base, so all three keep the design; an untouched slide keeps its own the same way. Rejected: matching a replacement to the old slide by content (fragile); keeping the template slide whatever the content (a slide that no longer fits would be cut).
- **Same design as another slide (WP36).** Found live: the user asked for slide 7 "with the same layout as slide 5" (two bullets slides the variety rules had spread over two template slides); the model could only resend slide 7's kind and bullets, the pin kept its template slide and the tool answered "Delivered". `{op: "edit", slide: N, field: "like", value: M}` (also read as `{op: "edit", slide: N, like: M}`) gives slide N the template slide slide M has **in the base plan** (`built_on`, the delivered file's design), even when the same call edits, replaces or removes slide M: the user points at what they see. On a replaced slide it applies to the first new slide. Unless the same call sets slide N's kind, its kind is cleared so the design decides. The request is carried on the slide as two hidden fields (`asked_design`, `asked_from`) until the deck is delivered, then becomes the slide's `built_on` like any pin. The assigner offers that template slide alone, at its fit cost: it is an explicit user choice, so variety neither prices it out nor groups it in an ask. If the slide does not fit it, its kind differs from the asked kind, or it is a cover/closing out of place, `needs_revision` names slide M's design and gives the misfit options plus "drop the `like`". Bad references (not a number, out of range, the slide itself, a removed target, two `like` on one slide, a slide with no `built_on` yet) are change errors. Rejected: letting `kind` edits move a slide to another variant (the kind is the same; the variant is what the user named); a model-facing `template_slide` field (internal template ids in the model's vocabulary).
- **Designs named in the delivery (WP37).** Same session: the model read "same layout" as "same kind", saw two bullets slides and answered "already the same" without a call; it never learned which template slide each slide was on. Both success texts add one line, `Designs: 1 'Title Slide' · 2 'Process' · 3 'Process' · … · 7 'Free text'`, numbered on the file's slides (a split list's parts included), with the template slide's label the user sees in the review and the summary dialog (cut past 28 chars), then "slides with different names look different; to give slide N the design of slide M, send" the `like` edit. Included template slides sharing a shown label (after the cut, WP38) are suffixed `#2`, `#3`… in inventory order (stable across builds), so two different designs never read as one; the review and the summary still show the bare label. Rejected: pattern ids (internal vocabulary, D12/WP36); one line per slide (token cost on every later turn).
- **Nothing changed (WP36).** Same session: the no-op changes rebuilt an identical file and the "Delivered" text let the model claim the change. Against a delivered base (`delivered`, a hidden flag set on the stored deck at delivery; a plan stored by `needs_revision` never has it, so a resend after an ask is still built), a call whose resulting plan shows the same content on the same template slides (a kind left out read as its template slide's kind) and keeps the file name builds and stores nothing and returns an error: `No deck was built: nothing changed…`, why, "do not tell the user it was changed", and the remedies (`edit` with new text, `like` for another slide's design). An error, like every non-delivery, so it never starts with a success prefix.
- **A kind edit reshapes the slide (WP39).** Found live: a delivered `bullets` slide edited to `two_columns` (kind, title and columns sent, bullets left) kept its bullets; no `two_columns` slide shows bullets beside columns, the revision said `drop bullets`, and the model, not knowing how to drop a field, resent nearly the same call twelve times until the turn's tool-call cap (`MAX_TOOL_CALLS_PER_TURN = 12`) blocked the thirteenth, which the runtime reported as a generic failure. An edit that changes a slide's kind now clears the fields (title, subtitle, bullets, columns, items, image, images, table; notes always stay) that no template slide of the new kind has a place for beside the rest of its content (the fit check's own "no place" reasons, on every slide of that kind), unless the same call sets them; nothing is cleared when the template has no slide of that kind (the soft fallback decides) or for a `like`. The delivery's review notes, or the `needs_revision` lead, say it: `Slide 2: bullets cleared, as kind 'two_columns' has no place for it beside the rest (to keep that text, put it in a field this kind shows).` Rejected: a static kind → fields table (a `two_columns` slide holds bullets without columns; the template decides).
- **An identical refused call (WP39).** Same session: calls 2 to 12 were mostly byte-identical. A call identical (canonical JSON of its arguments) to one refused with fit problems earlier in the turn, on the same base plan (a `changes` call's effective base, so a resend that would apply elsewhere is evaluated), is not evaluated again: `No deck was built: this call is identical to one already refused in this answer, so it is refused again (slide 10: …). Do not resend it: apply one of the options given then, or send each listed slide whole with {"op": "replace", …} in changes (numbers as listed), or drop the change that causes it` (`leave that slide out` for a `slides` call). It changes no turn state (base, repeated-problem flags, variety ask). A delivery forgets the refused calls; a variety ask is never one (its resend is built as is). Rejected: counting resends and stopping after N (the cap already does that, and the first identical resend already proves the loop).
- **Known gap.** Rows are never deleted (no session-deletion hook reaches a capability); one row per conversation with this agent, a few KB. Per-instance data cleanup is tracked by issue #2990.

### D24. A list too long for its kind continues on a slide of the same kind

Found live (D21's case): an agenda of 9 entries on a template whose agenda slide holds 8. D21 stopped the absurd `team` fallback, but the remaining remedies (a close kind that looks less like an agenda, or `needs_revision` asking the model to trim or split) both cost the deck or a round. The developer approved continuing the list on a second slide of the same kind.

- **What splits.** Only a list counted in entries: `items` (agenda, cards, figures, process, timeline, team…) and `table.rows` (the header repeated on each part; a table without a header is split by rows only). A slide is split only when its own kind holds it in no slide as one piece and its entry count is the cause: more items than the kind's largest slide holds, or a table whose only problem on every table slide of the kind is its height. Bullets, columns and any single field never split: a bullets overflow is measured in text room, not in entries, and cutting prose or sub-bullets between two slides can separate a point from its sub-points; text too long stays a fit problem with its word-budget remedy (D22).
- **Which kind.** The requested kind; with none, the first content-inferred kind (D7) whose slides hold the parts, tried only when no inferred kind holds the slide whole. The first slide forced onto the cover never splits.
- **Preference.** Same kind split > close-kind fallback (D21) > `needs_revision`. A split is accepted only when every part fits a slide of that kind with no misfit; otherwise the D21 path runs unchanged.
- **Balance and cap.** Parts = `ceil(entries / most)`, `most` the kind's largest slide (for a table, 2 parts); entries spread evenly, the first parts one longer (9 over 8 → 5 + 4). At most **2 slides per slide sent** (`_MAX_PARTS`): a list longer than two slides hold is a document, and the model should restructure it. Beyond the cap, the close kinds are tried, then `needs_revision` on the requested kind: `items: 20 given; the largest 'agenda' slide holds 8, two slides hold 16`, options `trim to 16 items (beyond 8 they continue on a second slide)` and `or keep 8 here and move the rest to slides of your own`.
- **Titles.** Each part's title ends with ` (k/n)`: digits and a slash read the same in every language, so no word to translate. A slide with no title gets no marker. The marker counts in the title's fit check.
- **Numbering.** Items keep their place in the list: explicit numbers are kept as sent (6..9 on the second part); when the items have none and the part's slide shows a number zone, the renderer numbers the continuation on in the template's style (`06`…`09`) instead of restarting, from the entries before it (`Assignment.starts`, a delivered split included). Generated numbers are never stored, so a change to part 1's entries renumbers part 2 (WP38). A consecutive run of numbers (`6, 7, 8, 9`) now counts as order numbers like `1, 2, 3`, so a slide without a number zone does not report them lost on the continuation.
- **Template slide.** The continuation prefers the same template slide as its first part: for it, that slide carries no reuse, repeat or max-uses cost; another slide of the kind costs a kind step more.
- **Variety.** A split list counts as one slide: continuation parts are left out of the use counts, the deck-wide caps (D19), the variety groups and asks (D15–D19) and the "three in a row" note; other slides using the same template slide count as before.
- **One numbering: the file's** (WP35, replaces "the model's numbering"). Live, a split made the file 14 slides for a 13-slide stored plan, and `changes` named on the file's slides missed. After a delivery the stored base plan (D23) is the deck as delivered: each part a slide of its own, with its rendered title (` (k/n)`), its entries (with only the numbers the model sent) and its kind. Every delivery message (notes, renderer findings) names the file's slide numbers, and the delivery says later `changes` use them (`1 to N, a list continued on two slides counts two`). The delivered note: `Slide 2: its 9 items continue on a second 'agenda' slide (5 + 4, titles marked (1/2) and (2/2)): …`; a slide after the split is named by its place in the file. `needs_revision` and the variety ask build nothing; their numbers stay those of the plan they refuse, which the turn keeps in memory (D23).
- **Rebuilding a stored split.** Consecutive slides titled `X (k/n)` and `X (k+1/n)` are read again as parts of one list: never split or suffixed a second time, counted as one slide for variety (the exemption above), and the second part on the first part's template slide at no cost. A lone `(1/2)` is an ordinary slide.
- **Agenda gap.** The renderer counts the parts of one agenda as one agenda: its topics summed, the slides that follow counted after its last part.

Rejected: asking the model to split (a round, and weak models resend the same list, D21's live case); splitting bullets by line count (breaks sub-bullets from their parent); keeping the model's numbering (WP33: the file and `changes` then disagree, which the live model got wrong).

### D25. "What was built": a structured summary on the delivered part

Users see the deck and the model's reply, and the reply can paraphrase or omit what the tool reported (a list continued on a second slide, a picture left out, a text cut). Developer-approved: an info button beside the download opens a short, plain account of the deck, taken from the tool.

- **Where.** An optional `summary` on the `ppt_preview` part (`PptPreviewPart`, shared with `ppt_filler`, which never sets it). The part is persisted with the message, so history replay shows the same button; no second store, no new endpoint.
- **Shape.** A list, one entry per rendered slide, in deck order: `{number, part, parts, title, kind, template, notes}`. `number` is the slide's place in the deck (D24, WP35: each part counts), `part`/`parts` mark a split (1/1 otherwise), `title` the title as rendered (with the `(k/n)` marker, inline Markdown stripped, capped at 120 chars), `kind` the template slide's kind, `template` its label. Each note is `{code, count?, kind?}`: `text_shortened`, `content_left_out`, `items_left_out` (count), `image_unusable` (count), `table_left_out`, `table_text_smaller`, `text_overflows`, `left_empty`, `fixed_slide`, `list_continued`, `other_kind` (the requested kind). A 20-slide deck is a few KB.
- **Codes, not prose.** The agent's notes are English sentences with remedies written for the model ("call again with `changes`…"); a user needs neither the remedy nor English. Codes let the frontend translate (fr/en today) and word them for a non-technical reader, and keep the payload small. Field names (`subtitle`, `bullets`) stay out: they are the model's vocabulary, not the user's.
- **Truth.** Recorded where the render and the tool act (the same places as the agent's report, D21), per rendered slide rather than per plan number, so a split list's parts each carry their own notes. Pictures that failed to load before the assignment are noted on the slide that named them (its first part). Left out on purpose: removed example text, the agenda gap and repeat notes (hints for the model, nothing the user lost).
- **Display.** The button shows only when `summary` exists (older parts and `ppt_filler` decks have none).

Rejected: sending the agent's English notes (untranslatable, model-facing); a separate endpoint reading the stored plan (it changes with the next build or refusal).

### D26. One build per model round; a resend of the delivered deck rebuilds nothing

Found live (session 028c5af3, `mistral-small`): one deck sent as several different `build_presentation` calls in one assistant message. The cover+agenda call was delivered; the fragments were refused for not starting with the cover, and the remedy "add a cover slide before it" led to more splitting. Later in the turn the model resent the delivered deck as is: a ~14 s rebuild for nothing, one of the turn's 12 tool calls spent.

- **One build per round.** The capability middleware's `awrap_tool_call` reads, in the agent state, the assistant message that holds the call: when it asks for several `build_presentation` calls, the first in that message's order is run and the others are refused before the tool runs, naming the first by its first slide's title and pointing to ONE call with every slide, or `changes` on the delivered deck. Ordering comes from the message, not timing, so the choice is deterministic. Identical copies are refused the same way; the argument-keyed guard and its `Ignored:` answer (WP27) are deleted. Limit: only where the agent loop runs the capability middleware (ReAct; `ppt_builder` exposes its tools only through it); a tool called directly is serialised by the lock, a copy then finding the deck delivered (below).
- **A fragment after a delivered deck.** A `slides` plan whose first slide fits no cover while a deck is delivered (this turn, or in the history, D15) gets one option: add the slides with `changes` (`insert` after N, `replace`), a new deck going in one call, cover first. Without a delivered deck the options are unchanged.
- **Identical resend.** A `slides` call whose assigned deck equals the deck delivered in this turn (same file name; per slide the same content and template slide, the `changes` "nothing changed" comparison) is answered `No deck was built: unchanged, deck already delivered as '<file>'` before the template load: no render, upload, preview or store write. Same turn only: a later turn may run another template version, and its `changes` already have the "nothing changed" answer (D23).

Rejected: keying on arguments or timing (fragments differ; timing is not deterministic); a runtime change (capability-local, no contract touched).

### D27. A revision is an answer, not an error; the limit per section

Found live (session a9429766, `mistral-medium`): a 14-slide deck got a variety `needs_revision` because its Italy and Spain sections deliberately repeated one structure (figures at slides 4/8, timeline at 6/10). The revision was an `is_error` result, so the runtime counted a failed call; the model planned the fix in its reasoning, ended the turn without the call, and the runtime replaced its answer with the raw revision text and JSON.

- **Revision vs error.** `_answer` (non-error, one text block) carries every expected outcome that built nothing: fit and variety `needs_revision` (same text, `status` and payload), the identical-resend guard (D26/WP39), a later call of one model round (D26), "nothing changed" (D23) and "unchanged, deck already delivered" (D26). `_error` stays for real failures only: an unreadable plan, `slides` with `changes`, empty `changes`, no base, unappliable changes, an all-empty plan (bad calls), the base or template not loadable, busy, render, upload, analysis not ready. The loop breaker is unchanged: the identical call is still answered without a second evaluation. No frontend change: no `ppt_builder` component switches on the error flag, and the runtime shows a non-error result as a normal tool step.
- **Next call.** Each revision text ends with `Your very next message MUST be a new build_presentation call with these fixes applied, never a final answer, unless the user must decide something first.`; the working rules say the same.
- **Remedies the content can fill.** A template slide with a framed picture area (D20) is never offered, as a variety option, a suggestion or a fit close-kind option, to slides of which none holds an image: the model cannot invent a picture.
- **The limit per section** (owner decision 2026-10-14, replacing a first "same place in mirrored sections" rule). Sections start at each slide whose wanted kind is `section` (only there: agenda entries no longer start one, D39); slides before the first start are a section of their own, and a deck with fewer than two starts is one section (the earlier behaviour). The max uses (D19) count within each section, wherever the slides sit in it: a template slide (or kind, in `kind` mode) used twice in Italy and twice in Spain is within a cap of 2, three times in one section is a repeat. From one section to the next the counts reset, so a later section may reuse an earlier one's slides in any order. Structural slides stay uncounted and deck-wide. The realistic cap (D19) is computed on the largest section. The beam resets its content use counts (`_REUSE`, `_OVER_MAX`) at each section start, so a later section naturally takes the same designs. Alternatives offered for a repeat are read from the sections concerned (a variant unused there is offered even when another section uses it). With the check `off`, sections play no part.
- **No three in a row.** Three identical template slides in a row stay forbidden, within a section under its cap too: the beam's `_TRIPLE` is unchanged, and with a limit on, a run the beam could not avoid is a repeat of its own (`in_a_row`, at most 2) in the variety ask and the passive note, unless its slides are already listed as over their cap. With the check `off`, the earlier passive note stays.
- **`repeat_layout`, the user's explicit ask.** An optional per-slide boolean: "true: this slide keeps the previous slide's layout. Set it only when the user explicitly asked for identical consecutive slides; never on your own initiative." The model gives the intent, the code decides the look: the slide takes the previous slide's template slide whenever that one holds its content (`_NOT_REPEATED`, as costly as a triple, otherwise), and is left out of the per-section cap and never ends a run. Never silent: the agent's notes say "Slide N keeps slide N-1's template slide, as the user asked" or, when the content does not fit, that it was built on another and how to keep the layout; the "What was built" summary carries `layout_repeated` / `layout_not_repeated`. Reachable in `slides`, in `replace`/`insert` slides and as `{"op": "edit", "slide": N, "field": "repeat_layout", "value": true}` (or the shorthand `"repeat_layout": true`); loose names `same_layout`, `keep_layout`, `repeat_previous_layout` and loose values (`"yes"`, `"true"`, 1) are read. It stays on the delivered plan (user intent), on a split list's first part only. Distinct from `like` (D23), which names any slide's design.
- The variety ask and the choice guide state the rule: the limit counts within each section, a later section may reuse an earlier one's slides in any order, never three identical slides in a row unless the user explicitly asked for it.

Rejected: tolerating repetition only at the same place of mirrored sections (the first version of this decision: a section with one slide more, or in another order, was asked to vary); detecting parallel structure by comparing kind sequences (fragile); letting the model ask for repetition without the user (the field's description forbids it, and every use is reported).

### D28. Library slides are excluded, their icons reused later

Found live (Paintress Cyan, a Slidesgo template): the deck used the `Fonts` slide twice as a design, and `Nature icons`, `Business icons`… were offered as `section` variants. Owner decision 2026-10-14: a library slide (icon, font, palette, resources, credits or instructions sheet) is never a design; it is excluded now, and reusing its icons is a separate, later change.

- **Rules only.** A slide is a library when its title (or label) names a resource page (`lexicon.is_library_title`: icons, fonts, typography, palette, attributions, credits, graphic/alternative/editable resources, instructions for use, presentation maker, this template; English and French), or when it lays out twenty or more small (< 2 % of the slide) top-level items bearing no text that are pictures, groups or freeform (`custGeom`) glyphs. Preset dots, arrows and lines do not count, so a dotted timeline is no icon sheet; three or four icons beside text stay a design. The earlier `icon_bank` rule (twenty pictures, no text) is folded in; `icon_bank` stays readable only in analyses stored before version 13.
- **Reason `library`.** The pattern keeps `included=false` with `exclusion_reason="library"`, so a later change can list its elements. Vision never sees excluded slides; no prompt change.
- A closing "Thank you" slide asking to keep an attribution is untouched: its title is not a resource page and its body text is not read.

Rejected: asking the vision model (optional, and it never labels excluded slides); matching body text such as "attribution" (the closing slide carries it).

### D29. Section numbers and cropped pictures (owner decision 2026-10-17)

- **Section numbers.** The built-in sections draw a big "01" in a `number` zone that nothing filled, so it was removed and the title sat low under the gap. A section slide's number zone now shows the slide's ordinal among the deck's section slides (every slide built on a `section` template slide counts), computed at render from the plan order and padded like the example ("01" → two digits). A `number` the model gives (a new optional slide field, editable through `changes`) is kept. The assigner measures the zone as filled. A number elsewhere, or without a number zone, is not lost content (the order shows it, as for step numbers).
- **Cropped pictures.** A filled picture zone is centre-cropped (`a:srcRect`) to its frame at the picture's own aspect ratio, never letterboxed. An example picture is swapped in place (new image relationship, old one dropped), so its frame, its geometry inherited from the layout (an ellipse for the team photos) and its alt text stay; an empty picture placeholder uses python-pptx's own crop; any other shape gets a picture over its box, with the shape's preset geometry. The image bytes are embedded as given: never resampled, and the frame is never enlarged.
- **Team photos recentred once.** With fewer items than the group shows, a picture-only item zone was also taken as loose decoration and moved twice; each shape now moves once.

### D30. Shared picture slots and empty text boxes (owner decision 2026-10-17)

- **One key per slot.** The original Thales template's slide 12 copies a picture placeholder, so two picture slots share `idx` 16. The repeated group addressed both items' pictures as `ph:16`, the second insert hit a placeholder the first had already replaced, and the whole build failed. One rule for top-level slots (where step 2 used to rename the second one) and grouped items; the analysis version moves so stored inventories are recomputed. python-pptx's `insert_picture` also dropped a picture placeholder's own position, so the picture took the layout's slot of that idx (both Thales photos landed in the middle column); the slot's `a:xfrm` is now kept on the new picture.
- **An empty zone goes, whatever its shape.** An empty placeholder was removed, an empty text box only cleared, so a panel drawn as the box's own fill stayed on the slide, against the Help Center's "an area left empty is removed". Every text zone left empty is now removed; shapes that are not zones keep the decoration rules of WP49.

### D31. Builder fixes from the revision evals (owner decision 2026-10-17 overnight)

Thirty revision requests on the built-in and Thales templates found deterministic builder faults; each is fixed the smallest safe way.

- **A list sent as one object is refused, not guessed.** `columns: {…}` became one column: a two-column slide showed one, and two `columns` edits silently replaced each other. One object cannot tell one column meant from several, so it is a `needs_revision` problem with the list form (a hidden `single_columns` marker survives the dump the tool re-validates); a `changes` edit of a list of objects with one object is refused naming `columns[i]`, and a second edit of the same field on one slide is refused. `items`/`charts` as one object are still read as one entry (no content lost there).
- **Two columns split at a point.** Bullets on a two-column slide were cut by count, sending a point's sub-points to the other column. They now split at the top-level point nearest the middle; one point with its sub-points cannot be split, so that slide is a misfit for it.
- **`after` 0 means after the cover.** The first slide is always the cover, so slides inserted before it were refused as a cover. With a deck that opens on its cover, a non-cover insert at 0 goes after it, and the result says so.
- **Closing bullets.** The closing placement gave one bullet per text box (contact details), so a built-in closing (one body, catalogued for 7 entries) refused three bullets and fell back to a section slide numbered "01". A lone body now takes the list, and a closing on a section slide takes no section number.
- **Key figure labels.** The built-in key figures have number and heading zones only; a `label` was refused and the agent fell back to bullets. On a `figures` slide without a label zone the label is a line under the heading.
- **Preview glyphs.** LibreOffice cannot recode Wingdings 3 (it does Wingdings), so the Thales sub-bullets showed as boxes in the preview. The preview copy only draws them as `►` in Arial, like the existing no-wrap widening; the template is not changed (PowerPoint has the font).
- **What changed.** The delivery compares the new deck with the previous delivered one (content and design per slide, a sequence diff) and lists changed, added and removed slides, so the agent can describe its edit truthfully. One extra store read when the turn has no delivered deck in hand.

### D32. Agent guidance from the revision evals (owner decision 2026-10-17 overnight)

The LLM-behaviour faults of the same evals (D31 took the builder ones) are addressed in the capability's own guidance, tightening sentences rather than adding sections; size measured with cl100k on the built-in template: working rules 479 → 587 tokens, tool description 3189 → 3196, schema 4532 → 4540.

The rules now say a deck was built only when the tool delivered it in that answer, to describe only what the result lists (the D31 change list), and to say when a request needed no change; the delivery text adds "never a change, layout or source it does not show", and an identical deck says to tell the user so.

- **`changes` for targeted edits.** Most revisions resent the whole deck, with drift in slides nobody touched. The rules, the tool description and the `slides` field say `changes` for edits of some slides, the whole deck only for a new deck or a rewrite of most; a resend that touched at most two slides of a larger deck is still built (no refusal: the content is right) with one line pointing to `changes`. `after` 0 is described as it now behaves (after the cover).

- **Facts.** See `ppt-builder-storytelling` D6. Tone requests on a deck without addressing (tu/vous) fall under "say so when a request needed no change".

### D33. Revision fixes, round 3 (owner decision 2026-10-18: universal builder rules only)

Only logic that holds in every case goes into the builder; what depends on judgement or on what the user meant (made-up figures, which slide, a shorter deck) stays with the agent.

- **A refused call leaves no trace.** A refused `changes` call became the base of the next call unless that call had the same shape, so an edit sent once (items emptied) reached a later delivery that never sent it, and a refused `like` kept pinning the slide. The shape match is deleted: `changes` apply to the delivered deck, or to a refused or proposed `slides` plan (whose refusal asks for `changes` on it), never to a refused `changes` plan. Refused slides are numbered on that deck, as the resend numbers them.
- **The change list is what the file shows.** Each delivered slide keeps a hash of its XML and the charts, pictures and notes it uses (workbooks and the template's layouts by name), so an edit that renders the same is no change, and a change that reached only the notes is said to be invisible on the slide. A slide found at another place is moved, never removed and added. Within a run of differing slides, pairs follow shared words, so the removed slide is the one that went. A slide moved to another design with fewer points says so with both counts, a split list counted whole; whether it lost anything is for the agent to check.
- **A picture design without a picture.** The tool's own choice already prefers a design without an empty picture area; a `like` forces the design, so a picture area with nothing for it is now a revision, as a framed one was.
- **Slides and changes together.** The refusal names the one to send by whether a deck was delivered, in one line.
- **`move`.** `{"op": "move", "slide": N, "after": M}`; moves chain, loops are refused.
- Not done: a process step `number` is a growing zone whose only capacity is the designer's sample, so a long label there has no universal limit to refuse on; notes the agent wrote itself on a slide that also changed visibly are its own choice, not a builder placement.

### D34. Audit fixes (owner decision 2026-10-18: audit fixes)

Universal rules from the read-only audit of 2026-10-18; judgement stays with the agent.

- **Indexes mean the base.** Several edits of one slide apply so each index names the entry the agent saw: sets and appends upward, then deletes downward. Two edits where one path holds the other have no order that means both, so they are refused.
- **Numbers as written.** U+2212 is a minus; a leading `0` group before one separator is a decimal (`0,125`). A lone `3.141` stays ambiguous and keeps its thousands reading.
- **No empty picture area.** A picture zone the slide cannot fill leaves a frame or a hole, whatever the zone: it is a misfit everywhere, not only after a `like`, so a picture design is chosen only with its pictures.
- **The result owns the remedy.** After needs_revision the rules say only "as its result says"; a refused `changes` call changed nothing, so its result asks for every change again.
- **The plan gate is told.** With `validate_plan` on, the rules say the tool shows the outline and `skip_plan` is declared; off, neither.

### D36. Layouts and resends (owner decision 2026-10-18: audit fixes, lot 4)

Universal rules only: the catalogue matches the render, and a slide nobody changed keeps its design.

- **Two columns take `columns` (H1, H2, M4).** A flat list was cut over a two-column design while the catalogue says its two bodies take `columns`; the cut (`column_split`) and its one-point misfit are deleted, and flat `bullets` do not fit such a design (option: give `columns`). A design that takes `columns` and has headings but no title zone is no longer listed with a `title` it cannot show; a titled slide does not fit it, and the refusal points to another kind, never "drop title".
- **A takeaway zone is never a column (H3).** Beside another body, the takeaway zone is left out of the slide fields and of the zones content falls into: the body is quoted at its own room, and the zone shows only a takeaway the user asked to see, else it is removed. A takeaway zone that is the slide's only body still holds its bullets (the chart-and-commentary slides).
- **A resend keeps what it repeats (H4).** A whole deck resent in `slides` reset every pin. A resent slide identical to a delivered one (content and kind, hidden fields aside) gets that slide's `built_on` again; it is kept while it fits, as after an edit. A changed slide is assigned as before. A refused `changes` call no longer invites a whole-deck resend.
- **Split titles recounted (H5).** Splitting stays: it saves a round when a list outgrows the largest slide of its kind. Its ` (k/n)` titles are recounted on every build over delivered slides: adjacent parts are renumbered, a part left alone (a slide inserted between, a part moved or removed) drops its number. Titles never delivered, or counting above two (the builder splits in two at most), are the user's words and stay.
- **Variety asks only checked recasts (H14).** The `unused` variants and one-slide-per-kind `others` were never checked against the content; they are deleted. The ask carries the capacity-checked `suggested` recasts and is made only when one exists.

### D38. Look-alike designs, fallback fix, kinds' use (owner decision 2026-10-18: Paintress deck review)

From the review of a Thales v3 deck (`~/fred-tmp/deck-review-ec3df500/REVIEW.md`): four bullet slides on four nearly identical layouts read as four designs.

- **One design per look.** The analysis (version 21) sets `Pattern.design` to the first earlier pattern that looks the same once filled: same backdrop, same drawn shapes of 2 % of the slide or more (XML without ids, pictures by content) and the same zones (role, capacity, flags) within 20 ‰. Names never count. Variety caps, repeats, runs and the `Designs:` line count `design_key`; "different names look different" is then true. Thales v3: `Vide`, `Title and body`, `1_Blank`, `Titre et contenu` are one design; the built-in template has no look-alike content slide.
- **A fallback states its fix, no exit.** A kind substitution, a misplaced cover/closing, a fixed slide that dropped content and an agenda gap no longer end with "otherwise nothing to do"; a substitution also drops the "or use another kind" alternative (it already is another kind). The passive repeat note keeps its exit (variety is the author's setting).
- **Each content kind says what it is for** on its catalogue line (`- cards (parallel items, each 'heading: explanation'): …`), replacing the "Shape the content" pairs of the guide; chart forms (scatter, radar, `charts`) stay in the guide. Structural kinds carry no clause.
- **A deck field inside a slide is the deck's** (extends "accept misplaced deck keys instead of refusing", owner decision 2026-10-18). Sessions a611e51e and ec3df500 (mistral-medium) sent `file_name` inside the cover slide and the whole deck was refused with "put that text in title, subtitle…". One helper (`_hoisted`) lifts `file_name`, `audience`, `main_message` out of every `slides` and `changes` entry, with the same conflict rule (another top-level value: one-line refusal). A deck field still reaching a slide (e.g. inside an added slide) is named as a deck field to send next to `slides`, never as slide text.
- Not changed: takeaway-zone scoring (a key-message card left empty is rightly avoided while takeaways are not shown).

### D39. Sections, numbering and suggestions (owner decision 2026-10-18: deck review 50bf2432)

- **Only `section` slides start a section.** Session 50bf2432 sent a 14-entry agenda naming almost every slide; titles matched entries once their number was stripped, the deck became 6 sections, a cap of 1 per section never fired and four repeated designs went through with no note. The agenda-entry matching (`_entry`, `_NUMBERED`) and the "or agenda part" clause are deleted; a deck without section slides is one section.
- **A kind with one design says so.** A content kind whose pool holds one design (look-alikes counted once, D38) carries `; 1 look` in its catalogue clause (`- two_columns (two groups of points; 1 look): …`): a fact, so the model knows a second slide of that kind repeats; recasting stays its judgement.
- **One numbering per result.** Notes reached the model in the file's numbers (a split list counts two) while the plan proposal's outline, the variety ask and its `suggested` lines counted on the plan; session 50bf2432's model mis-mapped them. Each result now numbers everything as its own outline: a delivery on the file, a plan proposal (`Assignment.plan_notes`) and a `needs_revision` on the plan sent, `suggested` included (`Repeat.suggestions(at)`).
- **A suggestion never names a design at its cap.** Session 50bf2432's replay advised `3 cartes titrées` for the frise and two-columns repeats while that design was already on two slides: `_suggested` budgeted variants of a kind, not uses of the design it names. It now skips a template slide (a kind, in `kind` mode) whose uses in the scope reach the cap, and each suggestion counts as a use, so two slides are never sent to the same last free design.
