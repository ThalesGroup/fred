## Context

`ppt_builder` lives beside `ppt_filler` in `libs/capabilities/fred-capability-ppt-filler/` and reuses its bounded python-pptx work (`concurrency.py`), run-merging traversal (`traversal.py`), image placement (`fill.py`, `folder_resolution.py`), `text_metrics.py`, LibreOffice conversion (`fred_core.convert_office_bytes_to_pdf`), the `ppt_preview` chat part and side pane. The first iteration (pattern inventory + model-chosen pattern ids + composition layer) failed end to end; see proposal. This design replaces it; the acquired rendering pieces stay.

Facts that constrain the design (verified in code):

- `validate_config` receives `SaveContext(identity, services)` (`fred_sdk/contracts/capability/context.py:79`). The save path builds a full `BoundRuntimeContext` but only injects `workspace_fs`, `agent_assets`, `document_folders` (`fred_runtime/app/agent_app.py` `_build_capability_save_services`, ~3676). There is **no model port** on the save path or in capability routes; `ChatModelFactoryPort.build(definition, binding)` (`fred_sdk/contracts/runtime.py:556`) is turn-shaped. The process-wide factory is `get_runtime_context().config.chat_model_factory` (`RoutedChatModelFactory`, `fred_runtime/model_routing/provider.py:104`, enforcing `binding.usable_model_ids`). `ModelProfile` (`model_routing/contracts.py:145`) has no vision flag; `models_catalog.yaml` profiles are all `capability: chat`, default `chat.mistral.small`.
- A capability can change its stored config **only** through `validate_config`'s return value; nothing writes it back later. `agent_assets` is bound to the saving user's token, which may expire after the request.
- fred-agents runs several replicas. In-process helpers exist (`fred_runtime/common/background_tasks.spawn`, in-memory). Temporal workers run in knowledge-flow, control-plane and knowledge-base pods, not in fred-agents. `fred_core.tasks` (`cp_task_run`) has a closed task-kind union owned by control-plane. Capabilities may own tables (`cap_<id>_*`, own Alembic tree, `migrations_location()`); `fred-capability-writable-document/store.py` is the pattern (overridable module-level store provider, router authorises on the row).
- The analysis takes ~50 s, beyond what a synchronous save should hold.
- The feature is not on `swift`: stored configs exist only on local dev agents, so the config shape may change without `upgrade_config`.

## Goals / Non-Goals

**Goals:** the template's own slides, chosen right, every time or an explicit error; analysis that understands real corporate slides; a save that never waits on analysis; one code path for customer and built-in templates; measurable deck quality.

**Non-Goals:** drawing shapes the template does not hold (composition is parked, not abandoned); charts/SmartArt as generated content, and tables beyond filling one the template holds (D14); swapping a template's icons; vision checks of the rendered output (text checks only); in-place editing of a generated deck (D23 edits the plan and re-renders the whole deck).

## Decisions

### D1. Park composition, delete the generated theme

The composition layer moves to branch `parked/ppt-builder-composition` with the `ppt-builder-composition` change. `Box`, `ZoneRole`, `TEXT_ROLES` move from `design_system.py` into `models.py`. `theme.py` is deleted (dependents: `capability.py` middleware, `validate_config`, the `/theme` routes and the registration warm-up; tests `test_builder_capability.py` and the parked composition tests; frontend `usePatternsPreview.ts` via `/theme/preview.pdf`). Alternative — keep composition behind a switch — rejected: it is the code path that replaced good template slides, and keeping it doubles every test surface.

### D2. Analysis: deterministic structure, vision meaning

1. **Deterministic pass (kept, amended).** Layouts are classified from typed placeholders as today. On example slides **every text-bearing shape is a slot by default**; excluded only when its text repeats on ≥ 2 slides, or it is a date/footer/slide-number field (`a:fld` type or footer/date/sldNum placeholder). Repeat groups, exclusion of chart/table/icon-bank slides (a data table is a table zone since D14) and the annotation channels stay. **Capacity** is measured once per slot at analysis time from its geometry, padding, line spacing and font (`text_metrics`) and stored on the slot as `chars_per_line × max_lines`. When the slot holds the designer's own sample text and that text does not fit by our ruler (the substitute font is wider than the designer's), the width estimate is **calibrated** on it: a binary search raises `chars_per_line`, bounded to 1/0.75 of the measured value, until the sample fits its box (after ppt-master's `text_measure.py calibrate`). The fit check, the renderer and the tool description all read these stored numbers, so they agree. Copyable relationships drop slide-to-slide hyperlinks from the blockers (they are not copied, D6). The sample-text lexicon no longer decides fillability.
   - **An example slide that copies its layout replaces it** (same role-bearing placeholders, nothing else drawn, not excluded): the slide is the pattern (duplicate + fill) and the layout pattern leaves the inventory, so one design is one catalogue entry and it carries the slide's sample text (calibration), notes `kind:`/`label:` lines, shape names and position. A later copy of the same layout is dropped; an excluded copy leaves the layout. Rejected: merging the slide's signals into the layout pattern (two sources per pattern, and instantiating the layout loses the sample's paragraph formatting). Slide 1 with a title-capable slot and no body content is a `cover` unless the template states another kind. An `OBJECT` placeholder named as an image is an image slot; a title-less `quote` takes its quote in the top body (role `title`) and its attribution in the next (`subtitle`). Measuring a slide placeholder, its padding and wrap come from its layout's and master's `bodyPr` when its own is empty, and inherited font and spacing from the layout placeholder of the same idx first (the first of the same type matched the wrong one).
   - **Rows of same-size text shapes are a repeat group**, like grouped shapes: non-grouped text shapes (placeholders or boxes, never title/subtitle) of near-equal size (±10 %), same font size and weight, on one band without overlap. One row is a group from 3 shapes; 2 shapes need a second row aligned under them (number above label, step title above body), and the chained rows give each item its fields; further aligned rows of the same class make a grid. A shape wider than 35 % or taller than 40 % of the slide is a column body, never an item, so two/three-column bodies stay columns. These items are filled, counted (`items max N`), removed and recentred like grouped ones; a non-grouped item is removed shape by shape.
2. **Vision pass (new, `labelling.py`).** Example slides are rendered once (patterns deck → LibreOffice PDF → per-page PNG via `pypdfium2`), each slot's box is overlaid with its number (set-of-mark), and a vision model returns, per slide, a typed JSON: `kind`, `label`, per-slot `purpose`, `max_items`, `reusable`. Calls run with bounded concurrency. Layouts are not sent (placeholders already say what they are).
3. **Merge.** Vision decides `kind`, `reusable` and slot purposes; geometry and capacity stay deterministic. A vision `kind` is accepted only when the slide's detected slots can carry it, otherwise the heuristic kind stays (the vision label, purposes and reusable flag are still taken), the rejection is logged, counted and added to the pattern's warnings. Compatibility: `cover`, `section`, `quote` need a title-capable slot (title or heading); `bullets` a body slot (body or caption); `image_text` an image slot and a text slot besides the title; `two_columns`, `comparison` two body slots; `cards`, `process`, `timeline`, `agenda`, `team` a repeat group of ≥ 2 items; `figures` a repeat group with a number slot; `closing`, `other` anything. A slide whose vision answer is missing or invalid keeps its heuristic label and `labelled_by="heuristic"`, shown in the review panel — analysis never fails because the model did. A kind the template declares — a `kind:` note, or a shape name stating a kind (`Roadmap`, `Agenda`…) — is never replaced by the vision kind; a `label:` note keeps its label.

**One closed vocabulary**, `SlideKind`: `cover, agenda, section, bullets, two_columns, comparison, cards, figures, process, timeline, team, quote, image_text, table, closing, other` (`table` added by D14). It replaces `Intent` in the inventory, the overrides and the plan.

### D3. Model access outside a turn

Add a turn-free port to the SDK: `CapabilityModelPort` (optional field appended to `RuntimeServices`), `async ainvoke(messages, *, profile_id: str | None, require_vision: bool) -> AIMessage`, implemented in fred-runtime over `RoutedChatModelFactory.select`/`build_for_chat` (`model_routing/provider.py`), which resolves **the model the agent uses by default**: platform binding, then `resolve_effective_chat_profile` (`fred_sdk/contracts/context.py` ~600: agent override → team `chat_default_profile_id` → catalogue default), checked against `usable_model_ids`.

Gap found: the save binding (`_build_capability_save_services`) has no team routing policy, no `usable_model_ids` and no platform binding; control-plane sends those only at prepare-execution. So the validate-config call gains the same routing fields control-plane already computes for prepare-execution (WP10), the save binding carries them, and the background job keeps that binding. No agent-tuning model field exists; routing is keyed by `agent_id`, so the port uses the saved agent's id.

Override: optional `PptBuilderConfig.labelling_model` (profile id), rendered as a selector inside the capability's own form widget (`ppt_builder_template`, no stock widget id), fed by the existing `GET /teams/{team_id}/routing-policy/available-models`; save checks only that the profile is known; usability and vision are enforced by the port. Unset → agent default.

**Vision toggle.** `PptBuilderConfig.use_vision: bool = True`. Off → the job makes no model call and labels by rules only. The selector shows only while the toggle is on and lists only vision-capable profiles. The form knows whether vision is possible from the existing `available-models` endpoint plus `effective-chat-model`, both extended with `supports_vision` (WP10). If neither the agent's resolved model nor any selectable profile has vision, the toggle is shown disabled and forced off, with "No vision-capable model is available for this agent; slides are labelled by rules". The job applies the same rule when the port is absent or refuses. `ModelProfile` gains optional `supports_vision`; capable profiles are flagged in `models_catalog.yaml`; the port fails closed when the resolved profile lacks it (→ heuristic labels, D2.3). Images go as LangChain `image_url` content parts. This touches the frozen runtime contract: dated entry in `RUNTIME-EXECUTION-CONTRACT.md` §8, and ships as its own PR (consolidation scope rule). Alternative — the capability reading the process-global runtime context directly — rejected: it bypasses the `RuntimeServices` boundary every capability is held to.

### D4. Background analysis with an owned table

- **Save** (`validate_config`): read the upload with python-pptx (an unreadable or oversized file still fails the save), after an archive pre-check that refuses a zip bomb before anything is inflated (`pptx_archive.open_presentation`: total uncompressed ≤ 512 MB, one member ≤ 256 MB, a member over 10 MB inflating > 100×; python-pptx inflates every member up front and the 50 MB limit bounds only the compressed size; every `.pptx` either capability opens from bytes goes through it), store the bytes via `agent_assets`, compute `template_sha256`, upsert a `pending` row, `spawn` the job with the bytes in memory and the save's `CapabilityModelPort`, return at once. Re-uploading the same file (same sha and labelling key) keeps a succeeded, current analysis instead of resetting it to pending; rebuilding a lost row from the stored asset returns that file's sha, not the client's. The stored config holds `template_sha256`, `use_vision`, `labelling_model` and the overrides — the inventory and `patterns_path` leave the config.
- **Store** `cap_ppt_builder_analysis`, one row per agent instance (replaced by the next save that needs a new analysis) matched on `(template_sha256, labelling_key)`, where `labelling_key` is `rules` or `vision:<profile id or agent-default>`, so toggling vision or changing the model re-runs the analysis: `status` (`pending|running|succeeded|failed`), `job_id` (a superseded job's writes match nothing), `attempts`, `lease_until`, `template_pptx` (so a re-run needs no user token), `inventory_json`, `patterns_pdf` (thumbnails), `error`, `team_id`, `saved_by`, timestamps. The job heartbeats the lease and writes the result in one transaction; it needs no Knowledge Flow token after the request.
- **Reads:** the middleware loads the row by `(instance, sha)`; a `succeeded` row is immutable, so a per-process cache keyed by the hash is replica-safe and costs one DB read per template per pod. The build renders the template bytes **from the row**, filtered on the config's sha, never the asset: a save stores the new asset before its config commits, so a turn on the old config would otherwise render bytes its inventory was not made from (it refuses instead). Template bytes are cached per pod by sha (4 entries; immutable, replica-safe). `GET /analysis/{instance_id}` (status + summary + inventory) and `GET /analysis/{instance_id}/patterns.pdf` serve the form; authorised for users who can **edit** the agent: there is no `agent_instance` FGA type; control-plane checks `TeamPermission.CAN_UPDATE_AGENTS` (`team.can_update_agents: team_editor`, `schema.fga`) on the instance's team (`product/api.py`). Capability routers are mounted with authentication only (`agent_app.py` ~4741), so the router checks the same permission on the row's `team_id` through the pod's `rebac_engine` (`runtime_context.py`, used as `check_user_permission_or_raise` in `agent_app.py`), exposed to capabilities as a small dependency (WP1).
- **Recovery:** a row whose lease expired is `interrupted`; the next readiness check, save or turn on any replica claims it atomically and re-runs it from the row's template, at most 3 attempts, then it is failed. The form shows "analysis interrupted" with the re-run action. A re-run started on a replica that did not take the save labels by rules (the model port is only remembered per pod), and the row then records the labelling it really used (`rules`), not the requested vision key. A `rules` row serves a vision config (readiness and turns accept it), and the next save that carries a model port re-runs it with vision; a save without one leaves it.
- **Re-analysis on rule change (refresh):** a `succeeded` row older than `ANALYSIS_VERSION` stays in use (the agent is never blocked by a rule change) and is refreshed in place: the first readiness check, turn (an outdated inventory is cached per pod and re-read every 60 s, since its refresh may land on another pod or never; a refresh finishing on this pod drops the instance's entries) or save that sees it claims the row atomically (`claim_refresh`: still succeeded and outdated, lease expired, attempts left), which sets a new `job_id` and a lease but keeps `status`, inventory and thumbnails; the job runs from the row's template as any re-run, its heartbeats keep the row `succeeded`, and its `finish` writes the new inventory with the current version. A failed refresh keeps the old result, records the error and spends every attempt, so it is not retried automatically; an interrupted one is claimed again while attempts remain. The form's re-run action and a save force a new refresh (attempts reset) unless one holds the lease. While a refresh holds the lease, `GET /analysis` reports `current: true`, so the form offers no re-run over it. `refresh_outdated(store, record)` is the shared helper (a platform-default template can reuse it). A vision-labelled analysis (labelling key not `rules`) is refreshed automatically only on a replica holding the model port its last save remembered: elsewhere the re-run would label by rules, so the old analysis keeps serving (developer decision, 2026-10-07), `current` stays false and the form says that saving the agent re-reads it with its vision model. A save forces the refresh with the port it remembers (vision kept); the re-run action keeps its behaviour (forced, labelled by rules on a replica without the port).
- **Copy to another scope** (AUTHORING "Scope-private settings"): `template_key` is an `AssetKey` of the `template` slot, set only while `template_sha256` is (a validator derives it), so a copy re-submits an uploaded template to `validate_config` in the target, which stores it and starts a fresh analysis for the new instance; the built-in template has no file to copy. `labelling_model` and `PatternOverride.pattern_id` are `Public`: a catalogue profile the target team may not use falls back to rules, and pattern ids travel with the template. No analysis is reused across instances by hash.

- **Background CPU bound:** background python-pptx work holds at most 2 of the pod's 4 heavy-job slots, so a burst of refreshes (an `ANALYSIS_VERSION` bump) never leaves the turns' builds busy; a cancelled job (timeout, superseded) keeps its slot until its worker thread really ends.
- **Known gaps (deferred):** analysis rows are never deleted when an instance is deleted or the capability disabled (the SDK has no delete hook), so a deleted agent's row and template bytes stay in the table; the analysis routes answer 404 for an unknown instance before checking the caller's permission.

Alternatives: JSON result in the asset store (needs a valid user token when the job ends and a KF fetch per turn); Temporal worker in fred-agents (new worker deployment for a one-minute job); `fred_core.tasks` (closed union in a control-plane hotspot). The table is the smallest durable, replica-safe option that follows an existing capability pattern.

### D5. Agent unavailable until analysis succeeds

The agent itself is unavailable while its analysis is `pending`, `running`, `failed` or `stale`, reusing the existing suspension machinery: `AgentInstanceRow.suspension_reason` (`control_plane_backend/models/agent_instance_models.py`), closed enum `SuspensionReason` (`agent_instances/suspension.py`). Every guard already treats a non-null reason as unavailable: run → 409 (`product/service.py` ~3243), locked toggle (`AgentCard.tsx`), hidden from non-managers (`TeamAgentsPage.tsx`), chat picker / recents / search filter on `!suspension_reason`.

- Add `SuspensionReason.CAPABILITY_PENDING` (same column, no schema change) and an optional `suspension_detail` text so a failure can carry its message (`config_invalid` carries none today).
- Add one optional, generic SDK hook `AgentCapability.readiness(stored) -> Ready | Pending | Failed(message)` (`fred_sdk/contracts/capability/base.py`), served by the pod. Control-plane reads it after a save and in `run_capability_reconciliation_sweep` beside `reconcile_instance_config_health`, setting/clearing `capability_pending` / `capability_config_invalid`. No ppt-specific code in control-plane.
- ppt_builder's `readiness` reads its analysis row: pending/running/stale → Pending, failed → Failed(error), succeeded → Ready, including a succeeded row made by older rules, which it refreshes in the background (D4). Becoming available therefore waits for the next sweep or for the form's status poll, which asks control-plane to re-check the instance (WP10 picks one; no extra save needed).
- The reconciliation sweep has no production host, so listing a team's agents also re-checks its `capability_pending` instances (caller's token, ≤ 10 concurrently, 2 s bound, on the shared runtime HTTP client; no answer changes nothing); with the form's re-check poll, an agent becomes available on the next listing after its analysis completes. A failed preparation (`suspension_detail` set) is not re-checked there: it only changes on a save, a re-run or the form's re-check. Over 10, a random subset is checked (stateless, any replica). The hook therefore runs on listings: it must return quickly, starting background work (the outdated refresh, interrupted recovery) without waiting for it.
- Only readiness verdicts set or clear `capability_pending`. A save, enrol or copy that validated its capability slices ends in one suspension write: none when the pod answers ready (the save resolves any earlier reason), else `capability_pending`; no answer after such a save fails closed to `capability_pending` without detail, lifted by the next answer. An older pod without the route (404) reads as ready. Every readiness write is compare-and-set on the reason read before the pod call, so a slow check never clears a suspension written meanwhile. A capability whose hook raised is reported `pending`, never omitted (omitted reads as ready).
- A copy goes through `copy-config`, which re-runs the capability's save in the destination: control-plane sends the destination team's routing parameters there and asks readiness once the copy exists.
- The pod's capability routes check the team the request names before building team-scoped services (the model port grants that team's models): `CAN_UPDATE_AGENTS` for validate-config and for both teams of copy-config, `CAN_USE_TEAM_AGENTS` for readiness (the listing's permission), with the route authorizer's rules (personal space, ReBAC off, security off). The model port re-reads the team's usable models every 30 s, since background jobs keep it.
- Failed or interrupted keeps the agent unavailable; the form shows the error and a **"re-run analysis"** action (`POST /analysis/{instance_id}/rerun`). `build_presentation` still refuses unless succeeded (defence in depth).

Control-plane, SDK-hook and frontend-gating parts ship as their own work package (WP10).

### D6. Rendering (kept, fixed)

Duplicate + fill stays the only way an example slide reaches the deck; layouts are instantiated as today. Fixes: `_duplicate_slide` copies only image/media/external-hyperlink relationships (slide-to-slide links dropped, their `a:hlinkClick` removed), copies `p:clrMapOvr` and the notes slide; the template's sections (`p14:sectionLst`) are dropped with its slides, since they list only removed slides and none of the copies (PowerPoint offers a repair otherwise) and their names mean nothing in a generated deck; `_write_lines` reuses the template paragraph's `a:pPr` of the same level for every level. A subtitle on a slide with no subtitle zone leads the body as an unbulleted line (as a column heading without its zone does), and step numbers 1, 2, 3… need no number zone (the order shows them): neither is lost content. Fill by slot, overflow (`fontScale` floor then word-boundary cut, reported), repeat-group item removal and recentring, image zones, lost-content reporting — unchanged.

**After-render check (`checks.py`):** any original non-shared slide text still present on a duplicated slide is removed and reported; overflow and lost content are reported. The tool fails closed: a slide that ends with no filled slot is an error (D8), never a silent sample slide.

### D7. The code chooses the slide

The plan per slide: `title`, `subtitle`, `bullets`, `columns`, `items`, `image(s)`, `notes`, then `kind` — last, optional. `pattern` and pattern ids leave the schema; the catalogue in the tool description lists the kinds the template offers with, per variant, the measured capacity of each zone (`≈C chars × L lines`, `items max N`), never ids, so the model writes to size on the first call. The plan coercion in `plan.py` stays.

`assign.py` maps the whole deck at once. A slide's candidate kinds, cheapest first: the requested `kind`, then the kinds inferred from its content shape, then every other kind; a candidate pattern must pass the **fit check** (every non-empty field has a slot, item count ≤ capacity, text within the stored capacity at the shrink floor). **Soft fallback:** a requested kind the template does not offer, or cannot fill with this content, or that the position forbids (`cover` not first, `closing` not last), is not an error: the slide goes to the best fitting pattern of a close kind (D21), and the success message names each substitution. Example slides outrank layouts of the same kind. A pass over the slides minimises misfit cost plus a variety penalty (deck-wide since D12) under **deck rules**: cover exactly once, at position 1 (the first slide is assigned the cover archetype; no other slide may use it); closing at most once and only last; never three identical archetypes in a row when an alternative fits (otherwise allowed and reported). `DEGRADATION`, `resolve()`'s last-resort fallback and the id loose-matching are deleted.

### D8. No silent fallback: actionable repair

If a slide fits no pattern of any kind (or the first slide does not fit the cover, or a slide is empty), the tool builds nothing and returns `needs_revision`. Per slide it names the exact field and element that does not fit and the measured limit, measured against the closest pattern: "bullets[2] is 214 chars; this zone holds ≈40 chars × 3 lines", "items: 9 given, max 6", "subtitle: no place on this slide", with concrete options (shorten `bullets[2]` to ≈120 chars, trim to 6 items, split over two slides, a kind that holds the content). The tool remembers the previous `needs_revision` of the same call sequence: a slide with the same problem again is flagged as resent unchanged, or as changed with the problem still there, never repeated word for word. The success message no longer says "do not call again"; it lists substitutions and what the after-render check removed or truncated. The prompt fragment tells the model to fix and call again, with only the changes since D23.

### D9. Built-in Fred template

`builder/assets/fred_template.pptx` — a real deck designed by the developer, with example slides for every `SlideKind` except `team`/`other` — ships as package data with `fred_template.inventory.json` (the analysis plus the deck's sha256), regenerated by `make builtin-inventory`; a test fails when the stored JSON differs from what the pipeline now produces for the shipped deck (deck edited, `ANALYSIS_VERSION` bumped, heuristic changed). The stored analysis is rules only: regeneration stays deterministic and needs no model, and every example slide stands for its layout (D2.1), so vision would label all of them. No template configured → this pair is used through the exact customer render path. The `/theme` routes are replaced by `/builtin` (inventory) and `/builtin/patterns.pdf`; `theme.py` is deleted.

### D10. Review panel and overrides

Thumbnail + label + kind per pattern, example slides and layouts in separate sections (D13); the author may change label or kind and exclude/include. `PatternOverride` keeps `label`, `kind`, `included`; zone-role overrides and the zone-outline detail dialog are deleted. A kind change also sets `reusable` from the new kind: the author's choice wins over the analysis's one-off verdict (an `other` slide, or vision's `reusable: false`), as a `kind:` note does; re-kinding to `other` makes the slide unused, and an override repeating the analysed kind changes nothing. Nothing is mandatory. The form shows the D4 status while pending.

### D11. Evaluation harness

`eval/` in the package, run by an opt-in `make eval` (never in `make test`): N prompts × templates through the real analysis, the real `build_presentation` tool and the configured LLM in a minimal ReAct loop with in-memory ports. Metrics per deck: first-call success, distinct archetypes / slides, cover exactly once at 1, closing at most once at the end, no three in a row, leftover sample text, overflow, lost content, repairs. Templates: the local "PPT Corporate" agent's `config/ppt_builder_template.pptx` (path given by env var, never committed) and the built-in one. Results go into `verification.md`.

### D12. Deck-wide variety: each template slide once where possible

Found on the "Paintress" template (48 patterns, 12-slide deck alternating two `bullets` slides): the assigner only prices adjacency (`_REPEAT`, `_TRIPLE`, `assign.py:65-66`, `_viterbi` 454-457), so A B A B is free; the icon cards (`slide:272`, `slide:273`) lose because (1) every cards slide of that template has one text field per item, so the natural `heading` + `text` item fits none of them (`_unused_item_fields`, `render.py:797`) and falls to `process`; (2) an empty item image zone costs nothing (`assign.py:290-292` reads top-level zones only), so `slide:266` ties `slide:272` at 0 and wins by order, then renders with its pictures removed; (3) the catalogue quotes 4 variants per kind (`_MAX_VARIANTS`, `tools.py:129`), hiding `slide:273`; (4) layouts 10/11 stay beside the slides that copy them (D13), doubling identical designs. `Pattern.preferred` is computed (`analysis.py:690`, `labelling.py:301`) and read nowhere.

- **Reuse cost.** A pattern already used k times in the deck costs `_REUSE × k` more (anywhere, not only adjacent); it outweighs `_LAYOUT` and the fit costs, and stays below `_KIND_STEP` for the first reuse, so an unused pattern of the same kind tier wins, a second kind tier wins only from the second reuse. Deck rules stay hard. The second-order Viterbi is replaced by a beam search whose state carries the use counts and the last two choices (decks ≤ ~30 slides, bounded beam): same rules, global term.
- **Honest fit costs.** An empty item image zone costs `_IMAGE_HOLE` like a top-level one.
- **Item heading without a heading zone** leads the item's single text zone in bold (as a subtitle leads the body, D6), counted against its capacity; lost only when it does not fit.
- **Catalogue:** every distinct variant per kind, each with its label (`cards: Three icon cards: items max 3 [text ≈12 × 2] | …`), no cap; the description asks to vary content shapes (items, columns, figures) rather than bullets everywhere.
- **Variety note:** when a pattern is used ≥ 3 times, the success message names the slides and the unused variants with their sizes, so a correction pass can recast one.
- **Icons** stay the template's decoration (group members or small pictures, never slots); never swapped. A decoration that overlaps a removed item is removed with it.
- `Pattern.preferred` is deleted (consolidation: dead field).

Alternative — a hard "never reuse" rule — rejected: small templates must still build a long deck; the cost keeps reuse possible and reported.

### D13. Review dialog: example slides first, layouts apart

An example slide that **holds every slot of its layout** stands for it even when it also draws decoration (D2.1 required "nothing else drawn"): picture placeholders count as slots, not as drawn extras (`_copies_layout`, `analysis.py:1096`, made `layout:10/11` survive beside `slide:266/267`). On Paintress this removes 6 of 10 layouts. A slide whose placeholders share an `idx` (`slide:267`: two `ph:16`) gets distinct zone keys and a pattern warning.

The dialog shows three sections: **slides of the deck** (included example slides), **layouts** (collapsed, "used only when no slide of the deck fits"), **excluded**. CSS fixes: `.cardHeader` uses `minmax(0, 1fr) auto` (its `1fr` took the native input's min-content and pushed the switch out of the card), the label `TextInput` is `compact` (its empty hint row made the gap above the kind `Select`), the switch is `small`, the thumbnail page is sized to its box.

### D14. Tables: fill a table the template holds

Paintress slide 5 (`slide:300`) holds one `a:tbl`: 12 rows × 5 equal columns (173 pt), `firstRow="1" bandRow="1"`, table style "Medium Style 2 – Accent 2", empty cells (only `a:endParaRPr lang`), no merges, no cell fills, text 18 pt (presentation default); it is excluded `table` (`analysis.py:1054`). Slide 24 (`slide:278`, "Timeline 1 an") is a 6 × 13 Gantt grid whose bars are per-cell `solidFill`: a drawing, not data.

- **Analysis.** A table covering the slide's main area is a **table zone** (role `table`) when it is a data table: ≥ 2 columns, no `gridSpan`/`rowSpan`/`hMerge`/`vMerge`, body cells empty or sample text, no per-cell fill that varies across body cells. Otherwise the slide stays excluded (`table`). The zone stores the header flag (`firstRow`), per-column `chars_per_line` (column width − cell margins, cell font: run → `endParaRPr` → presentation `defaultTextStyle`), the line height and `max_lines` = the lines the template's rows show (here 11 body lines). Kind `table`; vision compatibility: a table zone.
- **Plan.** `table: {header: [str], rows: [[str]]}` on a slide; ragged rows are padded (coercion); `infer_kinds` → `table` first. Fewer columns than the template: trailing columns removed, the others widened to the same total width; more → misfit. A table on a template with no table slide is a misfit (D8), never turned into bullets.
- **Fit.** Each row takes the wrapped line count of its tallest cell; the body's lines must fit `max_lines` at full size or at the shrink floor (one font scale for the whole table). Cells are never cut: `table: 18 rows need ≈22 lines; this table holds ≈11 (≈14 at the smallest size); longest cell rows[3][2] 120 chars, its column holds ≈17 chars per line`.
- **Render.** Header and cells written with the cell's `endParaRPr` attributes, colours left to the table style, `**bold**` allowed; rows grown by cloning the last body row (cleared, fresh `a16:rowId`) or removed from the bottom; columns removed with their `gridCol`; frame height set to the rows' sum; shrink sets one `sz` on every run.
- **Checks / preview / eval.** No template cell text left; the frame stays on the slide; shrink reported. The patterns PDF shows the table (LibreOffice's rendering of built-in table styles to be checked). Eval prompts with tabular content (offers × criteria, a schedule); metrics: table used when given, shape kept, no overflow.

### D15. No dropped text; variety asked once, on the first deck

Found in a real session (`mistral-small`, Paintress): four slides sent `"columns": {"bullets": [...], "heading": "Espagne", "heading2": "Italie"}`. The column coercion read `heading`/`bullets` and dropped `heading2` without a word, the deck showed one column, and the only signal was the passive note "Slides 4, 7, 10, 13 all use the template slide '2 colonnes de texte'" (the plan repeated section → two_columns → table, the columns restating the table). The eval's `lost` metric read the renderer's report, which never saw the key.

- **No silent loss.** The plan coercion keeps every key it cannot map as an ignored field, on slides, columns and items alike (`heading2 'Italie'`); a field given twice (`bullets` and `text`) is merged, not first-wins; a bullet written as `{heading, text}` keeps both. The assigner turns ignored fields into a `needs_revision` problem naming the slide and the field, and so does an unbalanced group: in `columns` or `items`, when one entry has both a heading and a body, an entry with a heading and no body (or a body and no heading) is a problem (`columns[1] has heading 'Italie' but no bullets`); an item's `number` counts as its heading and its `text` as its body, and a number with its label is a whole entry, so figures and agendas (headings only) stay whole lists. The renderer's ignored-field warning is deleted (unreachable). The eval's `lost` counts every text string of the raw tool arguments absent from the delivered deck.
- **Variety as a revision, first deck only.** When the assignment uses a non-structural template slide (not `cover`, `section`, `agenda`, `closing`) three times or more and the template has an unused variant of its kind or an unused slide of another non-structural kind, the tool returns `needs_revision` once, naming the repeated slides and the alternatives with what each suits (figures for short numeric items, timeline for dated items, cards for parallel items…). It says a resend of the same plan is built as is, and the next call is accepted whatever it holds (one ask per tool instance, i.e. per turn). It applies only while the conversation has no deck yet, read from the conversation history: the middleware keeps the messages of the turn's last model call, and an earlier `build_presentation` tool message whose text is a delivery (`Delivered: '…'`, or `The presentation '…' … is ready` without a preview) means a deck was delivered, so a later turn, where the user may ask for specific slides, keeps the passive note. A `needs_revision` or an error delivers nothing, so a history holding only those is still a first deck. The history is read only when a revision would otherwise be returned (no added work on the usual call). Earlier turns' tool messages reach the model through the runtime's transcript (`react_message_codec` keeps the tool name and text); a history trimmed before the delivered deck makes the next deck count as a first one again (at most one more ask, a resend is built). This replaced listing the session's outputs folder (`workspace_fs.ls`), retired when the SDK `WorkspaceFsPort` became write-only upstream; with no listing the ask never fired in production. Rejected: a new per-session store (the history already records it).
- **Choice guide.** The tool description replaces its "vary the content shapes" sentence with a short guide built from the offered kinds: numbers → figures, dates → timeline, parallel items → cards, ordered steps → process, a comparison → table (not restated as columns before it); each slide should look different.

### D16. Variety by kind, with alternatives read from the content

Found in a real session (`mistral-medium-3.5`, reasoning off, Paintress, first deck, one call, no ask, no note): kinds `[cover, agenda, bullets, two_columns, bullets, two_columns, bullets, table, bullets, bullets, closing]`. The five `bullets` slides landed on five different template slides ('Message clé', 'Texte', 'Vide', '1_Blank', 'Titre et contenu'), so the D15 trigger (one template slide 3+ times) never fired, though the deck showed five near-identical lists. Their content had other shapes: slide 7 dated events ("Janvier 2025 : …") → timeline; slides 9 and 10 "Espagne :" + "- …" then "Italie :" + "- …" (nesting faked with sub-bullets) → two_columns or cards; slide 5 "direction / objective / challenges" → cards.

- **Kind-level trigger.** Repeats are grouped by kind for non-structural kinds (by template slide for `cover`, `section`, `agenda`, `closing`, as before): a kind on 3+ slides is a repeat even across different template slides. A template slide used 3+ times is still one (it is a kind used 3+ times). Everything else of D15 stays: asked once, first deck only, resend built, structural kinds exempt. The passive note on later decks names the kind repetition too ("Slides 3, 5, 7, 9, 10 are all 'bullets' slides").
- **Alternatives from the content**, per slide of the repeat, pure text heuristics on its lines (bullets, column bullets, item texts): dated lines (a year, a month + year, a quarter at the start) → `timeline`; `Label :` header lines each followed by `- ` sub-lines, 2–4 groups → `two_columns` (2 groups) or `cards`; `Label : text` lines (2–6) → `cards`; short lines each holding a number → `figures`; numbered or "step/étape/phase" lines → `process`. A kind is suggested only when the template offers it and one of its slides could hold the entries (items max ≥ entries; two columns for exactly two groups). The ask and the note name the slides and the kind (`slide 7 → timeline (dated items)`, `slides 9, 10 → two_columns or cards (groups 'Label :' with '- ' lines)`). Deterministic, no LLM, computed only for the slides of a repeat.
- **Choice guide:** "at most 2 bullets slides per deck" when the template offers `bullets` and at least one other content kind of the guide.

Rejected: a hard cap on `bullets` in the assigner (the content is bullets as sent; recasting it is the model's job); an LLM call to classify the content (cost and latency per call for what a few patterns catch).

### D17. Variety asked on the first call only, with what each suggestion holds

Found by the WP17 eval (`mistral-small`, 78 like-for-like runs): the kind-level ask fired on most first decks (59 asks against 9), success fell 73 → 63, first-call 21 → 7, tool calls +39 %. 13 of the 15 failures had an ask, and in most the recast deck then failed the fit check: items sent to figures/process slides with no label or number zone, four columns on a two-column slide. The ask said which kind to use, not what that kind's slide holds, and it came after a fit repair, costing a round of its own.

- **Timing.** The ask is evaluated on the first `build_presentation` call of a turn only (first deck of the conversation, D15). When that call also has fit problems, the ask is **merged** into the same `needs_revision` (the problems, then the variety block): the model fixes and recasts in one round, so the ask never costs a round of its own, and a recast that brings new fit problems gets them back on the second call, as any repair. A later call of the turn is never asked, whatever it holds: no ask after a fit repair, and a resend is built (D15). The assigner therefore also computes repeats when some slides fit nothing. A slide with a fit problem counts on the template slide it would take once fixed: its closest fit (the pattern its problem names, `closest fit, a '<kind>' slide`) or a variant of that kind with no other problem, under the same caps, structural and revisable rules; so slides that repeat while each has a fit problem are asked in the same round (live Paintress call, `variety_max_uses` 1: a `label` on the items of two cards slides hid their repeat, and the repaired deck broke the max). An option or suggestion offered for such a slide never names a template slide that has the same fit problem. A slide with no closest fit (no slide takes its position, a table on a template without one) or whose text would be dropped is left out of the count. Rejected: asking only on a clean first call (a first call with a fit problem is the usual case on a weak model, so most decks would never be asked, and the ones asked would still pay a round); asking after the fit repair (the WP17 behaviour this replaces).
- **Fit hints.** Each content-based suggestion states what the suggested slide holds, read from the inventory: for a kind with items, `up to N items [number ≈C chars, text ≈C chars × L lines]` with the plan's item field names (so a figures slide says `number` and `label`, not `text`); for `two_columns`/`comparison`, `exactly 2 columns [heading ≈C chars, bullets ≈C chars × L lines]`. The variant quoted is the one the assigner would favour for that content: it holds the entries and the longest entry (a misfit is no candidate, an empty picture only a cost), then has no item picture to leave empty, is an example slide rather than a layout, then has the most room per entry; a field the analysis could not measure adds no room. When the slide's longest entry is longer than that room, the hint adds `shorten each entry to ≈N chars`. A kind no variant can hold (too few items, not exactly two body zones for two groups) is not suggested (D16). The hint reuses the catalogue's zone wording (`zone_summary`), so the description, the problems and the ask quote the same sizes.

### D18. Variety check as a setting; suggestions capped by the template

Found in two live sessions on Paintress (WP18 code). `mistral-small` (reasoning on): the first call had 2 `bullets` slides, yet got a merged ask for `slides [2, 4, 7]`, slide 2 being the agenda (asked `agenda`, too long for the agenda slide, built on a bullets slide by the soft fallback, so counted as `bullets`). The ask had no `suggested` line, only the generic options, `figures` first; the model recast slides 2, 4 and 7 to `figures` beside the two figures slides already there: 4 slides on Paintress's single figures slide (`Four KPI figures`), the agenda rendered by fallback, and, the ask being first-call-only, that deck was delivered. `mistral-medium` (reasoning off) ignored the ask and resent: its deck was the most varied (5 bullets of 16).

- **Structural slides are never in a repeat.** A slide is structural when its requested kind (or, with none, its first inferred kind) or its template slide's kind is `cover`, `section`, `agenda` or `closing`. It is grouped apart (by template slide, never revisable), so it neither counts towards a content repeat nor is named in an ask. The small-model plan above then has 2 bullets slides and no ask.
- **Caps.** Each kind gets a budget: its distinct variants in the catalogue minus the deck's slides already of that kind (a slide with a fit problem counts by its closest fit's kind, D17). A content suggestion (`suggested`) and an option of another kind (`options`) are given only while that kind's budget is above zero, each suggestion using one, shared across the repeats of one answer; Paintress `figures` (1 variant) beside 2 figures slides is never offered. Each slide gets one suggested kind: among those its content suits, the one suggested least so far (spread across kinds), so `two_columns or cards` alternatives go.
- **Setting `variety_check`** on `PptBuilderConfig`, values `template_slide` (default: ask when one non-structural template slide is used 3+ times, the D15 trigger), `kind` (ask when one non-structural kind is on 3+ slides, D16), `off` (no ask). Timing (first call of the turn, merged with fit problems, first deck only: D15/D17), caps and structural exclusion apply to both asking modes. The passive note stays in every mode, grouped as the mode groups (`off` groups by kind). A generic `FieldSpec` (`type="select"`, `enum`), rendered by the agent form's `TuningFieldRenderer` beside the plugin widget, option labels under `capability.ppt_builder.fields.variety_check.options.*`. Not in `labelling_key`: read per turn by the tool, no re-analysis; a stored config without it validates to the default.

Rejected: changing the default to `kind` now (the head-to-head eval decides; the developer chooses); a per-turn chat control (an author's choice, not a user's).

### D19. Max uses as a setting; one variety row in the widget

The WP19 eval showed `template_slide` nearly inert (the fixed "3+ uses" trigger rarely fires, since D12 already spreads template slides) and `kind` effective but tied to the same threshold. The developer approved an author-set maximum.

- **Setting `variety_max_uses`** (int 1..5, default 2) on `PptBuilderConfig`. 2 is the D15–D18 threshold (asked from the 3rd use); 1 means every content slide unique. With `variety_check: off` it does nothing (switch off = no enforcement). Not in `labelling_key`; a stored config without it validates to 2.
- **Realistic cap.** The max never applies below what the whole deck forces: one deck-wide cap per mode, `max(max_uses, ceil(n / v))` for every template slide, `n` the non-structural slides that fit (a slide with a fit problem counted on its closest fit, D17), `v` the non-structural template slides of the pool; in `kind` mode the kind cap is `max(max_uses, ceil(n / k))`, `k` the distinct non-structural kinds of the pool. Computed once per `assign` (`_caps`), before the beam, and reused by the ask, so the cost and the ask agree. Structural slides (D18) are exempt everywhere. Not per kind: a cap raised to a kind's own slides over its own variants (five bullets slides on a template with one bullets variant → five) would silence the very ask that recasts those slides into other kinds; reuse is forced only once the deck has more content slides than the template has content slides (or kinds). (An earlier draft of this paragraph described the per-kind cap; the code was always deck-wide, benchmarked in WP20–WP22, and is kept.)
- **Assigner.** The D12 `_REUSE × k` cost stays; when the check is on, each content use of a template slide beyond its cap adds `_OVER_MAX` (100), above `_KIND_STEP` and the fit costs, below `_TRIPLE`: another variant of the same tier wins while one fits; a requested kind is still its slide's only tier (D7), so the cost never switches it. The assigner prices template slides in both modes (the one thing it chooses); `kind` mode counts kinds for the ask.
- **Ask threshold.** A group (template slide or kind, per mode) is a repeat when its slides exceed its cap; timing, merge with fit problems, first deck only, resend built and suggestion caps (D15–D18) unchanged. Each variety entry carries `at_most` (the cap), so the model knows how many slides to recast. `off` keeps the passive note at 3+ slides of one kind.
- **Choice guide.** The "each slide should look different, at most 2 bullets slides" sentence goes; when the check is on: max 1 → "Each slide of the deck must look different."; otherwise "Use any variant below at most N times per deck" (`template_slide`) or "Use any kind below on at most N slides per deck, cover, agenda, section and closing aside" (`kind`). The bullets cap goes (the max covers it).
- **UI.** Both fields carry `ui=UIHints(widget="ppt_builder_template")`: the plugin widget renders one row, "Enforce variety [By slide name ▾] at most [2 ▾] times each", switch at the end (the vision row's pattern; a `div`, not a `label`, so the selects never toggle it). Switch off writes `variety_check: "off"` and disables the selects (stable layout); switch on restores the last mode seen while the form is open (default `template_slide`). The generic select field and its option labels are deleted.

Rejected: a per-kind max (one number is what an author can reason about); hiding the selects when off (the row would jump).

### D20. Limits where the model writes, build directly, no empty picture frame

Found by the WP20 eval and a live deck. Fit problems are the first cause of failed first calls: in WP20 cell 2 (`mistral-small`, `template_slide` max 1), 5 cover subtitles over the cover's ≈32 chars and 5 figure labels over ≈12 chars; the sizes were only in the description's catalogue, far from the fields. `mistral-medium` answered 2 of 14 first requests with a plan and a question (`no_tool_call`), as the fragment told it to "settle the outline" when the request looked vague. On Paintress, 'Nos quatre priorités stratégiques' (3 items heading + text, `kind: cards`, no images) landed on `slide:266` "3 colonnes d'image + texte": its three picture placeholders were removed, but its layout draws a full-width grey `Rectangle 2` behind them (y 25–49 % of the slide), which no slide can remove, so a grey band stayed between the title and the texts. `_IMAGE_HOLE` could not prevent it: a requested kind is the only tier (D7), and `slide:266` was the only `cards` variant holding that text.

- **Field limits in the schema.** Each text field of the tool schema (`title`, `subtitle`, `bullets`, `columns[].heading`, `columns[].bullets`, `items[].number|heading|text|label`) carries the template's room in its JSON-schema `description`, from the same zone mapping and measurement as the catalogue (`zone_summary`). Per kind, the room is the largest of its variants' (each variant quoting its tightest zone for that field, as the catalogue does), so a text within it always has a slide of that kind; the hint states the most common room across the kinds and lists the kinds that differ: `Room: ≈71 chars; cover ≈32 chars × 2 lines, figures ≈12 chars`. The cover is one fixed slide, so its room is exact. An item heading written atop the text (no heading zone) shares the text's room. Descriptive only, never `maxLength`: a schema violation would make the provider reject the call instead of the tool returning `needs_revision`. The schema stays cached, keyed by the offered kinds and the hints (identical inventories share it).
- **Build directly.** The fragment tells the agent to write the plan and call the tool in the same answer, asking to validate an outline only when the user asked for it or the request does not say what the presentation is about.
- **A picture zone framed by its layout needs a picture.** The analysis flags an image zone `framed` when a shape of the layout or master that no slide can remove (not a placeholder, no text, under half the slide's area, so never a background) covers at least half of it. The fit check treats a framed picture left empty (no slide image for a slide zone, no item image for a used item) as a misfit; the build tool fetches the plan's pictures before assigning and counts only those that open as an image (an invalid id is dropped and reported), so the slide goes to another variant or kind (soft fallback, D7) and only a plan with pictures gets that slide; the catalogue quotes such pictures as `image (required)` / `images×N (required)`. Unused items' pictures are removed with their items as before. On Paintress (and corporate) this flags `slide:266` and `slide:267` (layout bands behind their picture rows) and no other picture zone; on the built-in deck, "Pairing text with a visual" (its layout draws a panel exactly under the picture). `ANALYSIS_VERSION` 11 (stored analyses are refreshed in the background when first seen, the agent staying available; a vision-labelled one only where its model port is, otherwise at the next save, D4). Rejected: raising `_IMAGE_HOLE` (a requested kind is the only tier, so the cost never switches it); hiding the layout's shapes on the slide (`showMasterSp="0"` also hides the logo and footer); removing slide-level decoration over an emptied picture (no such case in the three templates: not added).
- **Eval agent prompt.** `eval/run_eval.py --agent-prompt <file>` replaces the short stand-in agent prompt with an author's prompt; `eval/agent_prompts/agent_prompt_fr.txt` holds a candidate prompt for agent authors, measured against the stand-in: no gain on the measured path, not suggested as is (verification.md, WP21). A short prompt (`agent_prompt_short_fr.txt`: stand-in + no invented figures + one- or two-sentence answer) was measured next (WP22): replies get short, but mistral-small then rebuilds the deck after delivery on most turns and neither model stops inventing figures without documents; not suggested either. No author prompt is suggested; the eval keeps the stand-in.
- **Variety default kept.** `template_slide`, `variety_max_uses` 2 (the code default). Max 1 scored slightly better in the WP20–WP21 benchmark; the developer validated max 2 in real sessions with mistral-small and mistral-medium and keeps it (2026-10-07).

### D21. Fallback only to a close kind; every message actionable

Found live (Paintress, `mistral-small`): an `agenda` slide with 9 items, where the agenda slide (SOMMAIRE) holds 8 [number, heading ≈19 chars × 2 lines]. The D7 fallback went on to the content-inferred kinds and built it on a `team` slide (15–22 items); the note said only "built as 'team' instead of 'agenda' (no 'agenda' slide holds this content)". The model resent the same 9 items three times.

- **Close kinds.** A requested kind falls back only to the kinds of `CLOSE_KINDS` (`assign.py`), in preference order; the inferred and "any kind" tiers apply only when no kind is requested (or `other`):

  | Requested | Close kinds, in order |
  |---|---|
  | cover | section |
  | agenda | bullets, process, timeline |
  | section | quote |
  | bullets | two_columns, cards, image_text |
  | two_columns | comparison, table |
  | comparison | two_columns, table |
  | table | comparison, two_columns |
  | cards | bullets, two_columns, comparison, process |
  | figures | cards, bullets |
  | process | timeline, bullets |
  | timeline | process, bullets |
  | team | cards |
  | quote | section, bullets |
  | image_text | bullets, two_columns |
  | closing | section, bullets |

  A list stays a list (agenda, process, timeline, bullets); grouped content stays grouped (two_columns, comparison, table); title slides stay title slides (cover, section, quote, closing). `quote → bullets` and `closing → bullets` keep the same structure (a title and one text block), so a statement or contact lines still build. `cards → process`: the same item shape (heading + text blocks), the mildest shift on offer (numbering suggests an order); without it, a cards slide whose only variant frames empty pictures (D20) fails instead of building. Item kinds cannot take bullets or columns and the reverse: such a close kind is never a candidate for that content, only an option in the revision. Never: agenda → team/figures/cards, or any kind to an unrelated one.
- **No absurd substitution.** When neither the requested kind nor a close kind fits, the slide is a `needs_revision` problem measured on the requested kind's closest slide (when that kind is absent or forbidden at this position, on the closest close kind's, led by `<why>; closest close kind, a '<kind>' slide: …`; otherwise `closest fit, a '<kind>' slide: …`; a first slide forced onto the cover takes only the cover prefix, never the close-kind lead). The item count names that kind's largest slide, not the template's: `items: 9 given; the largest 'agenda' slide holds 8`, options `trim to 8 items`, `split the items over two slides`, what the slide takes, then up to three close kinds with what each takes. It is counted for variety on its closest fit and merged with the first call's ask (D17): never a round of its own. A kind with neither its own slides nor a close kind in the template: "leave `kind` out".
- **Substitution note.** What, why, how to get the requested kind: `Slide 2: built as 'process' instead of 'agenda': the 'agenda' slide does not fit (items: 9 given, max 8). To get the 'agenda' slide, call again and trim to 8 items or split them over two slides; otherwise nothing to do.` A kind unavailable there: `…: this template has no 'timeline' slide. Nothing to do.`
- **Message rule.** Every text `build_presentation` and `list_images_in_folder` return states what happened, why, and one concrete remedy, or "nothing to do". Results that build nothing start "No deck was built"; a render error says whether to resend the plan or have the owner save the template again (it changed since its analysis); review notes give a remedy per element (`not placed: subtitle (move it to a field this slide shows, or drop it)`); misfit options name an edit that fits (`give the bullets as items (at most 8)` on an items-only slide, not `drop bullets`; a fixed slide: `send only the title '<label>'`). Kept: the `Delivered: '` / `The presentation '` prefixes (`deck_delivered`) and `Ignored:`. **Renderer findings** the after-check report does not carry go to `DeckReport.notes` and join the review notes, phrased by the same rule: the agenda gap (`Slide 2: the agenda announces 6 parts but only 2 slide(s) follow it. Add the missing slides or remove those parts from the agenda; otherwise nothing to do.`), a one-line heading or label running into the text below (shorten to under N characters), an items slide given no items (give that content as `items`), content sent to a fixed slide, a table the render cannot fit (its measured cause and remedy, instead of `not placed: table`). The last three are defensive (the fit check stops them first). `RenderResult.warnings` keeps every finding for the logs only (one info line per build): truncations, removed example text, dropped items, lost content, unusable images, a table off the slide and skipped entries already reach the model through the report or the plan.

Rejected: keeping the inferred tier after the close kinds (that is where `team` came from); refusing every substitution (loses the D7 first-call gain on templates that lack a kind); converting items to bullets for a bullets fallback (a renderer change; the revision option asks the model instead).

### D22. Limits phrased in words

Found by the WP21 eval: with the figure-label room in the schema ("figures ≈12 chars"), `mistral-small` still wrote 18–40-char labels (6 too-long labels in cell A, first-call success 3/14). Small models do not count characters; they follow a word count.

- **One rule, every template.** Wherever the model reads a room (catalogue, schema hints, `needs_revision` reasons and options, the kind advice), `capacity_text` quotes a word budget first, then the measured characters: `≤4 words (≈32 chars)`, `≤20 words (≈71 chars × 2 lines)`, `1 word (≈12 chars)`. Words per line = `floor((chars per line + 1) / 7)` (the last word needs no space), times the lines, since a word never spans two lines; at least one, "1 short word" under 6 chars per line. Nothing is tuned per template: the only input is the room the analysis already measures.
- **Ratio 7 chars per word, space included.** French prose averages about 5 letters per word (6 with the space), business vocabulary runs longer ("stratégique", "déploiement"): 7 errs on the short side, so the budget never promises more room than the characters allow on typical text. The characters stay quoted next to it.
- **Unchanged.** The rooms, the fit check (characters), the targets of the options (the same `per_line × lines`), the schema (no `maxLength`) and the reason's leading `<field> is N chars` measure.
- **No example from the template's sample text.** Considered (`label: 1 word, like 'Clients'`) and dropped: on Paintress every sample that fits its zone and is not placeholder text is either a slide name describing the layout ("3 colonnes d'image + texte", "Planche à puces") or a number ("01", "2022"); the label samples are "KPI #1", "Nom", "Changer ce texte". An example would be template-dependent, mostly absent, and misleading where present.

Rejected: per-kind or per-template ratios (template-dependent); words only, without chars (the fit check counts chars, and the model needs the target it is judged by).

### D23. Changes against the previous plan, whole deck re-rendered

Two needs, one mechanism. (a) A `needs_revision` naming two slides of twelve made the model resend all twelve, and weak models reworded or dropped slides they were not asked to touch. (b) A later-turn request ("add a key-figures slide per country", "put this phone number on the last slide") had the same cost and risk. Developer constraint: render quality must not change, so a change never patches the generated file — the tool applies the changes to the stored plan and the **whole resulting plan** goes through the normal path (assignment, fit check, variety rules, render), exactly as a full `slides` call.

- **Schema.** `build_presentation` takes `slides` (the whole deck, unchanged) **or** `changes`, a list of operations whose slide numbers are the **previous plan's** (1-based, never shifted by earlier operations of the same list):
  - `{op: "replace", slide: N, slides: [slide, …]}` — slide N becomes these slides;
  - `{op: "insert", after: N, slides: [slide, …]}` — after slide N, `0` = at the start;
  - `{op: "remove", slide: N}`;
  - `{op: "edit", slide: N, field: "items[2].label", value: …}` — one field of slide N: a slide field (`title`, `bullets`…), an element (`bullets[1]`, `columns[0].heading`, `items[2].text`, `table.rows[3][1]`); indexes from 0 as in the tool's messages; `value` null removes a list element, an index equal to the list's length appends one. The edited slide is re-coerced as any slide.
  Operations are applied all at once on the base: untouched slides are the base's own objects (byte-identical in the plan); inserts after the same N keep their order. `file_name` left out keeps the base's.
- **Actionable errors, nothing built**, all bad operations listed at once (`changes[2] (remove): slide 14 does not exist; the previous deck has 12 slides. Use a number from 1 to 12.`): unknown `op` (the four listed), a number out of range, `insert` without `after`, `replace`/`insert` without slides, `edit` without `field` or with a path the slide does not have (`items has 3 entries, items[0] to items[2]`) or a field that is not a slide field, two operations replacing/removing the same slide, an edit on a replaced or removed slide, `slides` and `changes` both non-empty. **No base plan** → `No deck was built: there is no previous deck in this conversation to change. Send the whole deck in slides.`
- **Base plan = the last plan the tool evaluated** in this conversation and agent: the full plan of the last call that ended in `needs_revision` (fit problems or a variety ask) or in a delivery, so a fix after `needs_revision` and an edit in a later turn work alike. An error before evaluation (unreadable or empty plan, bad changes) or after it (busy, template load, render or upload failure) does not replace it, so a retry of the same call applies to the same base. Pictures that did not load are dropped from the stored plan, as from the evaluated one.
- **Where it lives.** A capability-owned table `cap_ppt_builder_deck_plan` (same Alembic tree as the analysis), primary key `(session_id, agent_instance_id)`, holding `plan_json` and `updated_at`: one small upsert per evaluated call, read only when a call sends `changes` and the tool instance has not already evaluated a plan this turn (the turn's own last plan is kept in memory). Replica-safe (any pod reads it) and independent of history trimming. No session id (a test or eval context without one) → memory only. A failed write is logged, never fatal: the deck is still delivered; the next turn's base is then the previous stored plan (the risk is a stale base only after a database failure). Rejected: rebuilding the base from the conversation history (tool-call arguments are trimmed with history, and a `changes` call would require replaying every earlier call); patching the generated `.pptx` (a second render path, and the assignment and variety rules could no longer see the whole deck).
- **Resend of the same changes.** When a call sends exactly the `changes` of this turn's previous evaluated call, its result is the base already (it was stored): it is rebuilt as is, never applied twice (an insert would double). This keeps "send the same call again: it will be built as is" (variety ask, D15) true for a `changes` call.
- **Everything else unchanged on the resulting plan**: first call of the turn (D17), `deck_delivered` from history (D15), misfit closest-fit counting (D17), the duplicate-parallel-call guard keyed on the arguments (WP27), the repeated-problem flag (D8, by the new plan's slide numbers), success prefixes. Messages use the resulting plan's numbering; `needs_revision` ends "call build_presentation again with only `changes` for these slides (numbers as listed), or the whole deck in `slides`"; a delivery says to change it later with `changes`.
- **Description and working rules.** Both modes in a few lines: a new deck → `slides`; a fix after `needs_revision` or a change the user asks for → `changes`, which keeps the other slides exactly as they are. The fragment's "regenerate the whole deck" goes.
- **Known gap.** Rows are never deleted (no session-deletion hook reaches a capability); one row per conversation with this agent, a few KB.

## Risks / Trade-offs

- [Vision model mislabels] → the author relabels in the panel; deterministic geometry still bounds what can be filled; eval measures the effect.
- [Vision cost/latency at upload, ~40 calls] → bounded concurrency, background, once per template hash.
- [Job lost on pod restart] → lease + recovery on next save/turn; the form says so.
- [Strict fit check yields repair loops on weak models] → capacities in the description, soft fallback across kinds, errors that name the element and its limit; first-call success and repairs are eval metrics.
- [New SDK port widens the contract] → optional field, appended; ships alone with a contract entry.

## Migration Plan

Unreleased feature: no `upgrade_config`; local agents re-upload or re-save. New owned table via the package's Alembic tree (`python -m fred_runtime migrate`). The SDK port and the `supports_vision` flag are additive, but an older fred-agents rejects `supports_vision` in its catalogue (profiles forbid unknown keys), so the image rolls before overlays add it. Rollback downgrades the control-plane schema first: the `b8e1f4a2c6d9` downgrade lifts `capability_pending` suspensions, which an older control plane cannot parse. Migration note: operations impact (the table migration, flagging vision models in the catalogue, the readiness field if WP10 is needed) → minor. The control-plane validate-config timeout is out of scope.
