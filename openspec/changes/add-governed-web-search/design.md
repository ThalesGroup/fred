## Context

The attached V1 uses `ddgs`, `httpx` and `trafilatura`; it offers SafeSearch, region and freshness filters, extraction/focus, retries and size bounds. It logs full arguments and queries, permits per-call headers, and checks DNS before `httpx` connects. Those choices are unsuitable as the only security or privacy boundary in a shared Fred deployment. Fred already has capability packages, `RuntimeServices`, shared tool invocation audit/KPIs, and a three-stream observability model that excludes tool arguments from ordinary logs and audit.

## Decisions

1. **Capability boundary.** Implement `web-research` as a Fred SDK capability package with tools on the shared ReAct/Deep/Graph execution path. The package receives identity and a typed web-research port through context; the LLM sees only bounded search/page arguments. Keep transport credentials, user identity and deployment configuration out of tool schemas. Reuse capability enablement and tool authorization rather than creating a separate MCP registration or control-plane runtime.
2. **Single egress contract.** Fred's adapter calls a deployment-configured HTTPS egress endpoint. The endpoint performs the search and page fetch, including extraction, and is the only component permitted to reach public websites. Web research public egress is confined to the egress process. The existing agent runtime binds the SDK port and calls the DMZ endpoint via HTTPS; knowledge-flow needs no new runtime path. Container/Kubernetes installations deploy the same endpoint and policy locally or remotely.
3. **Transport security.** Use service authentication and TLS certificate validation (mTLS where supported by platform operations), bounded timeouts, concurrency, retries and request/response limits. The egress endpoint accepts a fixed JSON operation schema, not a proxy URL chosen by the model. Secrets come from deployment secret stores and never enter model-visible arguments or search activity records.
4. **Egress safety.** Validate HTTP(S) destinations, reject userinfo and private/non-global destinations, pin the resolved address through connection, and revalidate every redirect. Enforce public DNS/address policy at the egress service and network layer, including IPv4/IPv6 and DNS rebinding resistance. Strip sensitive headers across hosts, prohibit model-provided headers, cap redirects/bytes/chars/results and reject non-textual content. Retrieved text is explicitly untrusted; it cannot override agent/system instructions.
5. **Provider portability.** Keep a provider adapter behind the egress protocol. The first adapter uses DuckDuckGo HTML search through the same pinned HTTP transport as fetch, including the documented SafeSearch parameter. It does not use the V1 DDGS client, which bypassed the transport and ignored SafeSearch in some backends. HTML layout changes and captchas fail closed; availability has no SLA. The Fred API does not expose provider-specific fields. An operator can disable the feature when a provider or DMZ route is unavailable; failures return a bounded tool error.
6. **Activity, audit and monitoring.** The shared tool boundary emits existing structured invocation audits and metrics without content. A dedicated access-restricted search activity sink stores opaque user/team/agent/session identifiers, correlation ID, timestamp, operation, query text for search operations, requested/final public URL for fetch, status/error code, duration and result count; never page bodies, snippets, headers, tokens or raw exceptions. Search activity is written once per logical tool request, including rejection/failure, with a clear outcome and correlation across Fred and DMZ. Egress logs use only correlation and bounded status, avoiding duplicate query copies.
7. **Retention and deletion.** Set a configurable default of 30 days for the dedicated activity sink, with automatic purge and an operator-verifiable policy. Restrict reads to approved security/operations roles, audit access to these records, and erase records tied to a deleted user under Fred's account-erasure process. Deployment must specify the sink and purge mechanism; absence of a compliant sink blocks capability enablement. The implementation extends the observability contract; operators must approve raw-query collection before deployment activation. Durable hashed-subject fences prevent late writes across replicas after erasure.

## Data Flow

`Agent tool -> Fred capability -> typed port -> HTTPS egress endpoint -> search provider/public page -> bounded result -> agent`. In parallel, Fred writes one restricted activity record and existing content-free tool audit/metrics. The DMZ sees only service identity and correlation metadata; it must not receive Fred's user identifiers unless required by a separately approved contract.

## Risks and Open Decisions

- **Privacy:** Query text may contain personal/confidential data. Confirm that storing raw queries for 30 days is acceptable; otherwise use redaction or metadata-only activity before shipping.
- **Provider terms/availability:** Confirm DuckDuckGo HTML provider suitability for production and any rate limits. Preserve the adapter boundary if a contracted provider is needed.
- **Topology:** The Fred caller is the existing runtime; confirm DMZ deployment ownership for each platform. The HTTPS protocol is fixed; physical placement remains deployment-specific.
- **Existing policy:** Update `OBSERVABILITY-AND-AUDIT.md` and the relevant product/retention contract as part of implementation; do not silently place query text in the current audit stream.
