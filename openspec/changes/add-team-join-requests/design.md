## Context

Full rationale and catalogue: `docs/swift/rfc/NOTIFICATIONS-RFC.md` (types 3 and 4). This change builds on the notification framework of `add-in-app-notifications` (same branch) without changing its store or API.

What exists today (audit of `origin/swift` and `feat/notifications`, 2026-10-22):

- `JoiningMode` (`libs/fred-core/fred_core/teams/metadata_store.py`): `open`, `invite_only`, stored in `teammetadata.joining_mode` as `String(20)`, so a new value needs no DDL. `TeamVisibility` is independent; a private team has no `public` relation, so a non-member cannot read it at all. `update_team` downgrades `open` to `invite_only` when the result would be private.
- Self-service join: `join_team` (`POST /teams/{team_id}/join`), checks `joining_mode == OPEN`, grants `team_member` to the caller only. Admin add: `add_team_member` (gated by the permission matching the role, `can_administer_members` for `team_member`). Team invite link (#3116, `platform_access/service.py` `enroll`) grants `team_member` through a link.
- Discovery: `MarketplaceTeams` lists public non-member teams under "Other teams"; `TeamCard` shows "Join" for `open` and the static label "Invite only" otherwise. A non-member card is not a link. The access-denied pages (#3085) are about platform access, not about a team, and a private team is invisible to non-members, so neither offers a better entry point.
- Mode chooser: `TeamSettingsParameters` (ButtonGroup `open` / `invite_only` for public teams, a locked "manual only" button for private ones).
- `can_administer_members` = `team_admin` (`schema.fga`); `pending_team_admin` (charter not accepted) does not hold it.
- No request-like table exists. `platform_access_links` is about links, not requests.
- Notifications: `ACTION_PERMISSION` (`notifications/schemas.py`) maps each type to a `TeamPermission`; `_allowed_recipients` skips drafts without `team_id`; `forget_lost_access` iterates `ACTION_PERMISSION.values()`; `resolve` deletes the actor's own open rows and marks the others handled. The frontend registry (`rework/features/notifications/notificationTypes.ts`) already has `kind: "call"` actions, unused until now.

## Goals / Non-Goals

**Goals:** a person can ask to join a public `on_request` team from its card; its current admins get an actionable notification; the first decision wins; the requester gets the answer; nothing changes for teams that do not opt in.

**Non-Goals:** requests to private teams, email, a request history screen, a role other than `team_member`, request rate limiting beyond decision 5.

## Decisions

1. **Wire value `on_request`, not a revived `request_only`.** Legacy bundles carry `request_only` as the old default of every team (migration `a4b5c6d7e8f9` moved all teams there). Reusing it would make an old import turn requests on for teams whose admins never chose them, against the owner's "opt-in" rule. The importer keeps `request_only → invite_only` and passes `on_request` through. Labels: "On request" / "Sur demande".
2. **Public teams only.** Same rule as `open`: the ButtonGroup offers Open / On request / Invite only for a public team; a private team keeps the locked "manual only" button, and `update_team` turns `on_request` into `invite_only` when the result is private. A non-member cannot see a private team, so a request mode there would have no entry point; the team invite link already covers it.
3. **Requester entry point: the existing `TeamCard` in "Other teams".** It is where the person already learns the mode. States: no request, or a refusal older than 24 hours → "Ask to join" (opens the shared `Dialog` with an optional message, `TextArea` with its guidance in `description`); pending → label "Request sent" and a text button "Cancel request"; refused less than 24 hours ago → label "Request declined" (`can_ask_again_at` in the `mine` row says until when). The caller's own requests come from `GET /teams/join-requests/mine`, fetched once by `MarketplaceTeams` and passed down, so the hot team listing (`_list_teams`) is untouched.
4. **Record: one row per (team, requester), only while it matters.** Table `team_join_requests`: `id`, `team_id`, `requester_id`, `requester_name` (display snapshot), `message` (nullable, at most 280 characters, plain text), `status` (`pending` | `refused`), `created_at`, `expires_at`, `decided_at`, `decided_by`. `expires_at` is `created_at` + 30 days (the notification expiry) while pending, and becomes `decided_at` + 7 days on refusal: the refused row is what the admins' "Accept anyway" acts on. Unique `(team_id, requester_id)`; indexes on `requester_id` and `expires_at`. Accept and cancel delete the row (the audit log keeps the trail). Every read ignores expired rows; a new request replaces an expired one; the lifecycle notification step also deletes expired requests in the same budget.
5. **Duplicates and abuse.** A second ask while pending answers 200 with the existing request and emits nothing new (the open notification group stays as is). An ask less than 24 hours after a refusal answers 409 `join_request_refused`; after 24 hours the new request replaces the refused row (new id, so the old notification groups stay closed). Cancel deletes the request and the admins' open notification rows for it (new store method `delete_groups`), so a cancelled request leaves nothing to act on. No other rate limit (owner, 2026-10-22: the 24-hour wait is the cooldown): the remaining loop (cancel, ask again) is one person badging one team's admins, visible in the audit log, and an admin can switch the mode off.
6. **Recipients: current `team_admin` holders, filtered by `can_administer_members`.** The service lists the team's `team_admin` users and calls `notify` with `team_id` set and type `team.join_requested`, whose `ACTION_PERMISSION` is `CAN_ADMINISTER_MEMBERS`; slice 1's send-time filter, member removal, role loss (`forget_lost_access`) and team deletion then apply unchanged. Group `join_request:<request_id>`. Payload: `team_id`, `team_name`, `request_id`, `requester_id`, `requester_name`, `message`.
7. **Decision endpoints are the buttons' targets.** `POST /teams/{team_id}/join-requests/{request_id}/accept` and `/refuse`, gated by `can_administer_members` (re-checked server-side, never trusting the tile). Accept takes a pending or a refused row ("Accept anyway" is the same route on a refused row, no second endpoint): it claims the row with a conditional delete, grants `team_member` through `_add_team_member_relation` (a no-op if the person became a member meanwhile) and resolves the group with outcome `accepted`; on a refused row it also deletes the requester's refusal notification before telling them they were accepted. Refuse takes a pending row only (a conditional update; refusing a refused row is a no-op), sets `status = refused`, `decided_*`, `expires_at = decided_at + 7 days`, and resolves with `refused`. The deciding admin's row disappears; the others show "Handled by <name>". A decision on a request that is gone (decided, cancelled, expired, requester deleted) answers 404 `join_request_not_found`; the tile then deletes its notification and the list refetches.
8. **Leaving the mode refuses every pending request (owner, 2026-10-22).** When `update_team` stores a mode other than `on_request` for a team that was `on_request` (including the downgrade a private result forces), it refuses all the team's pending requests in one statement, as the updating admin, then resolves their groups and sends each requester the refusal notification. They then behave like any refused request: listed for 7 days with "Accept anyway". Accepting needs nothing the admin could not already do through Add members, so it does not depend on the current mode.
9. **Answer to the requester: type `team.join_request_answered`, no permission.** `ACTION_PERMISSION` becomes `TeamPermission | None`; `None` is never filtered by permission and `forget_lost_access` skips it. An acceptance carries `team_id` (only its "Open the team" tile acts on the team), so member removal/leave (`delete_for_member`) and team deletion (`delete_for_team`) drop it with the rest: a notification stays only for someone who can still act on it. A refusal carries none. Payload: `team_id`, `team_name`, `outcome` (`accepted` | `refused`); it never names the deciding admin. Group `join_request_outcome:<request_id>`. Accepted: tile link and button "Open the team" to `/team/<team_id>/agents`; refused: no link, no button. A refusal survives the team's deletion (no `team_id`); both expire normally.
10. **Admin list: a "Pending requests" section at the top of the Members tab**, rendered only for `can_administer_members` holders and only while `GET /teams/{team_id}/join-requests` returns rows: name, message, date; Accept and Refuse on a pending row, "Accept anyway" on a row refused in the last 7 days, all calling the same endpoints. It covers an admin promoted after the request was sent (notifications are addressed at send time). The notification stays the main surface.
11. **Audit.** `team.join_request.created`, `.cancelled`, `.accepted`, `.refused` through `emit_audit_log` with `actor_uid`, `team_id`, `request_id` (and `requester_uid` on decisions); never the message text. Notification counters are slice 1's.
12. **Platform access.** Every new route sits behind the same authenticated platform-access gate as `POST /teams/{team_id}/join`, so a requester is admitted when asking; accept adds no admission source beyond what Add members already does. Implementation confirms the gate (task 3.1) rather than adding a second check.
13. **Cleanup.** `delete_team` deletes the team's requests (its notification rows already go by `team_id`); `delete_user` deletes the user's requests and the admins' open rows for them (`delete_groups`).

## Risks / Trade-offs

- [A promoted admin misses older requests in the bell] → the Members section lists them.
- [Cancel and ask again re-badges admins] → accepted (decision 5); a refusal already imposes 24 hours.
- [Accept anyway after a refusal] → the group is resolved again with outcome `accepted` (`resolve(include_handled=True)`), so every admin tile shows the final outcome, and the requester's own refusal is replaced.
- [The requester's answer is lost if emission fails] → best effort as in slice 1; the card's state (`mine`) still shows the truth: the team appears under "Your teams" once accepted, "Request declined" once refused.
- [Three-way ButtonGroup on narrow screens] → checked in the live check; the group already wraps at small widths.

## Migration Plan

One linear Alembic revision whose `down_revision` is `fe166447f3d5` (slice 1's revision, the branch head; re-parent if `swift` moves, never `alembic merge`): create `team_join_requests` with its unique constraint and indexes. No existing row changes and no backfill: every team keeps its mode. Downgrade drops the table; a team left on `on_request` would then fail the older enum, so the downgrade also rewrites `on_request` to `invite_only`. The PR's migration note gains the second revision; impact stays minor.

## Owner answers (2026-10-22)

1. **Optional message:** kept, at most 280 characters, admins only.
2. **Re-asking after a refusal:** allowed 24 hours after the refusal; refused requests stay visible to admins for 7 days with "Accept anyway" (decisions 4, 5, 7).
3. **Pending requests when the team leaves `on_request` or becomes private:** all refused automatically, each requester notified (decision 8).
4. **"Pending requests" section in the Members tab:** kept (decision 10).
