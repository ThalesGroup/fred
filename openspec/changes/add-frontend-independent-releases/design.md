## Context

The three initial `@fred-oss` packages are published at `0.1.0-alpha.1`. The retained [release workflow](../../../.github/workflows/Publish-frontend-packages.yml) is preparation-only after retirement of bootstrap/recovery incident operations. [RELEASE.md](../../../libs/frontend/RELEASE.md) and the [frontend packaging RFC](../../../docs/swift/FRED-FRONTEND-PACKAGING-RFC.md) distinguish release readiness, publication, and adoption. Current tooling still requires exactly `designTokens`, `ui`, and `iframeSdk` in `libs/frontend/release/proposed-release-contract.json`, its schema, candidate/evidence/transfer code, and registry verification. That contract repeats manifest coordinates and metadata, so a normal version PR would require error-prone edits in multiple places. The UI manifest declares a design-token peer; the SDK is otherwise independently consumable.

The synchronized main `frontend-package-archives` specification already carries design-token, UI, SDK, and first-release guarantees. Its release-coordinate, candidate/evidence, exact-toolchain, fixture-transfer, isolated-consumer, and registry-verifier requirements still describe the initial alpha.1 three-package release. `add-frontend-package-release-foundations` remains active with task 12.7 unchecked; `retire-frontend-bootstrap-recovery` is implemented but not yet synchronized/archived. This delta explicitly modifies the six existing requirements where that historical scope would contradict selected future versions, and extends retirement's preparation-only replacement requirement. It must be verified against a post-retirement main specification and synchronized only after the predecessor/retirement close-out order is safe. Neither an unchecked trust/revocation task nor successful preparation proves routine OIDC publication.

Official npm guidance requires an existing package and an exact trusted-publisher relationship for GitHub's organization, repository, workflow filename, and environment. The publishing job needs `id-token: write`; direct `npm publish` must be permitted by the trust configuration, not inferred from a staged-only default or `npm whoami`. See [Trusted publishing](https://docs.npmjs.com/trusted-publishers/) and [npm trust](https://docs.npmjs.com/cli/v11/commands/npm-trust/). Repository code cannot establish npm ownership, change those settings, or inspect private package settings credential-free. Maintainers review the npm settings as a release prerequisite; CI validates only repository-owned policy and execution context, and actual npm OIDC authorization happens in the protected publish job.

## Goals / Non-Goals

Goals:

- Make the committed member manifests the sole maintained source of package coordinates, dependencies, peers, and exports, with a separate reviewed central policy and extensible registration.
- Prepare, publish, and verify a duplicate-free selected package set from one generated logical release record and retained, byte-identical archives; distinguish publication selection from compatibility-only exact prior versions.
- Permit normal direct-OIDC releases of existing packages behind one protected approval, with read-only, independently rerunnable verification and truthful per-package execution/provenance identity.
- Preserve existing archive, signature, browser, isolated-consumer, host, toolchain, CI, and source-isolation guarantees; make fourth-package registration possible without rewriting a three-role release schema.

Non-goals:

- Publishing or configuring npm/GitHub in this planning change; automatic version bumps, push-triggered releases, FRED/RAGS adoption, SDK protocol ownership transfer, registry fallback, or changes to historical first-release evidence.
- Reinstating `publish-bootstrap`, `recover-bootstrap`, `verify-existing`, incident JSON, or a bootstrap token. A genuinely new npm package still needs separately authorized initial creation before direct Trusted Publishing can be configured.
- Eliminating specialized package builders, validators, or consumers. Extensibility means shared identity/record orchestration is inventory-driven, not that all package-specific contracts become generic.

## Decisions

### 1. Manifest authority and a small registered inventory

Introduce a reviewed, schema-checked registration such as `libs/frontend/release/package-inventory.json` containing a stable selection ID, contained producer-workspace directory, build/pack/validator profile, and applicable consumer/host profile for each member. The private root's `workspaces` and registration must agree exactly; unknown, duplicate, escaping, or nonpublishable members fail before build. Member `package.json` values supply name, exact version, dependency/peer ranges, exports, `repository`, and `publishConfig`; the registration does not duplicate them. Existing CSS/asset/license and runtime/declaration validators remain profile-specific. Shared `release-contract.mjs`, `release-candidate.mjs`, `release-evidence.mjs`, `fixture-transfer.mjs`, and `registry-verifier.mjs` iterate the registration instead of a required three-role schema. A fourth member adds an explicit profile and tests, not a schema-required fourth field.

Keep a distinct centrally reviewed release-policy input/schema for allowed `@fred-oss` scope, `https://registry.npmjs.org/`, public access, `next` tag, `ThalesGroup/fred`, committed `swift`, the retained workflow filename, `npm-publish` environment, approved provenance issuer, authorized owners, and exact producer Node 24.21.0/npm 11.19.0. Compare manifest and packed metadata to this *expected* policy; never derive approval from the archive or downloaded attestation. Application/host tests remain on their separately pinned Node 22.13.0/npm 10.9.2 toolchain. Replace the live manifest-copy fields in `proposed-release-contract.json` and schema only when equivalent fixture/negative tests are updated; keep fixtures explicitly nonapproved and historical release evidence untouched. A selected release PR manually changes the member version, compatible peer/dependency ranges where needed, and matching per-package `CHANGELOG.md` entry; regenerate the private producer lockfile under the producer pins. Normal merges do not publish.

Alternative considered: retaining a full expectedManifest copy per package makes version changes a multi-file identity edit; using archive metadata as policy removes an independent acceptance boundary. Both are rejected.

### 2. Selection is not compatibility resolution

The shared CLI and workflow parse selected stable IDs deterministically, reject empty/duplicate/unknown selections, and generate candidate archives only for selected members. Producer quality and existing source regressions may still exercise all three packages; that is a regression gate, not an instruction to pack or publish unselected coordinates. Build order follows registered dependency edges, with selected design tokens before selected UI. UI's actual manifest peer range is checked against the selected token candidate or an explicitly reviewed exact prior token baseline. Recommend a source-reviewed compatibility-baseline file or ledger entry that names the exact prior coordinate, prior approved record/registry integrity, and provenance policy without copying UI's peer range. For the already published alpha.1 baseline, import a reference to validated historical evidence into the new ledger once, verify it read-only against npm, and never rewrite the original appendix/artifact. If that evidence cannot be obtained, fail UI-only approval rather than using a tag, workspace link, or arbitrary registry version. SDK-only skips UI/token publication and UI-specific consumers; all SDK archive/browser/neutral-consumer/host checks remain.

The prior-token baseline is a compact, source-reviewed, self-contained ledger entry, not a live dependency on an old CI artifact. Its required fields are stable package ID, exact name/version and approved registry URL, SHA-512 of the published tarball, expected attested artifact digest, independently expected source repository and publication commit, authorized workflow/certificate URI and OIDC issuer, and a verification trace (completed gate classification, verifier commit/run/attempt, evidence digest, date, and historical links as references only). Import alpha.1 once by comparing immutable historical evidence with freshly downloaded exact-version registry bytes and cryptographically verified provenance; record those independently checked facts without modifying the historical appendix. Thereafter a UI-only release retrieves the exact token registry version and repeats byte/provenance checks against this durable entry even if the original candidate ZIP has expired. An absent or altered required baseline field fails closed. The baseline does not authorize continuing a publication whose *selected candidate or attempt* archive is unavailable.

Offline compatibility tests may install integrity-verified candidate tarball `file:` references from a prepared cache in disposable source-isolated consumers; an exact prior registry token version may be provisioned into the pinned npm cache and installed offline against its ledger integrity. Published manifests still forbid local dependencies. Genuine registry verification installs exact selected and compatibility-only registry versions with no local-tarball or checkout fallback; the production host uses its own application dependencies while the SDK under test comes from the verified archive/registry installation.

### 3. One generated record, immutable candidate fields, separate outcomes

Generate a schema-versioned logical release record from reviewed committed source, central policy digest, selected manifest snapshots, durable compatibility-baseline digest, observed producer/application toolchains, gate results, and actual selected archive names/sizes/SHA-512. Retain the record with exact archives via the existing immutable transfer/evidence machinery; bind GitHub artifact ID, originating run/attempt, API metadata, ZIP SHA-256, and each archive digest when uploaded. The candidate portion is immutable. A new dispatch may publish original bytes under its actual `GITHUB_SHA`; provenance expectations for that version follow that actual approved publishing execution, not the candidate's earlier SHA. Never override GitHub environment variables to manufacture identity.

After protected approval, source/context authorization, original candidate retrieval, and immediate byte recheck—but **before the first publication command**—write a small publication-attempt record for that dispatch. It binds the original candidate-record digest/artifact identity, selected exact coordinates and archive SHA-512 values, approved policy digest, the actual current GitHub repository, workflow URI, `GITHUB_SHA`, run and attempt, expected OIDC issuer/certificate identity, and the selected commands/order. Upload it as a separate retained GitHub artifact (without credentials or dependency trees); verify the returned artifact ID/API identity, ZIP digest, and downloaded record digest against the locally computed values. Only then may `npm publish` start. If upload/readback or digest verification fails, no publication command runs. A fresh dispatch/attempt gets a new truthful attempt record; neither the original candidate record nor an older attempt is rewritten. This is shared ordinary publish evidence, not incident configuration.

Separate bound outcome documents record verified per-package npm coordinate/integrity and cryptographic provenance, referencing the particular pre-publication attempt; a later verifier document records its *own* commit/run/attempt. If npm accepts a version but the process dies before an outcome is saved/uploaded, the durable attempt already contains independent expected actual-publication identity. Later read-only exact-version reconciliation can establish success only by matching registry bytes and cryptographically verified digest/repository/commit/workflow/issuer to that attempt. A mere attempt is never reported as a success. Outcomes and verifier records refer to the immutable candidate/attempt digests and cannot alter original source, bytes, or policy.

Existing `fixture-transfer`, `release-evidence`, and `registry-verifier` interfaces should be parameterized rather than replaced. Controlled fixture records remain visibly nonapproved. A later publish or verify must retrieve the explicitly selected original artifact, verify GitHub API identity and ZIP digest, recheck record/archive consistency, then reject changed, missing, expired, incomplete, or mismatched material. Do not infer source artifact names from the current `github.run_attempt` or rebuild for a retry. Preserve exact immutable archives through application compatibility and publication.

The existing transfer-metadata JSON schema accepts selected inventory IDs and only their package records; it does not hard-code the initial three roles. The shared metadata validator applies that schema before independently checking registered IDs, dependency order, exact selected package set, identity, and integrity. Older all-member transfers may omit `selectedIds`; that omission means the complete registered member set, never permission to accept a partial package set.

### 4. Three ordinary dispatch operations in the retained workflow

Keep `.github/workflows/Publish-frontend-packages.yml` manual-only and `swift`-only. `prepare-only` is the default and executes selected candidate preparation plus applicable application/consumer checks; it never invokes publication. `publish` executes the same preparation/compatibility path for new records, or an explicit verified prior-record continuation, before one separately approved protected `npm-publish` job. Only that job has `id-token: write`; no npm secret or bootstrap-token fallback exists. Maintainers review exact package trust settings out of band, including direct-publish permission. Repository-controlled checks validate approved policy, workflow filename/environment and current GitHub execution; they do not authenticate to npm to inspect settings. Use direct `npm publish <exact-retained-tarball> --tag next --access public --provenance` only after manifest/record/byte checks and successful attempt-artifact retention. If npm rejects OIDC authorization (including a missing or staged-only trust setting), stop without an npm token or interactive-login fallback. Run published-token verification before selected UI, and fail closed for ambiguous results. The publish command is never automatically retried. Bounded post-command registry visibility polling retries only read-only 404s; auth failures, malformed metadata, mismatched integrity/identity/provenance are immediate failures.

`verify` takes explicit record/artifact identity (at least originating run/attempt, artifact ID, independently expected ZIP SHA-256, and record digest), retrieves retained materials without candidate creation, and runs generic public-registry/consumer/browser/host verification. Workflow conditions must make publishing unreachable in that mode. Verification receives GitHub read permissions needed for artifact retrieval only, neither `npm-publish` nor `id-token: write` nor a publishing credential. Its result is bound to the historical package publication identities and records actual verifier execution independently. Repeat verification must work even if all selected versions already exist.

The workflow should validate all manual inputs at source authorization. Do not make operators edit source incident IDs or relabel evidence; an input selects a retained record, and that record supplies its origin identity. GitHub candidate and attempt artifact retention must be sufficient for intended publication retry windows; if either required retained artifact is gone, require a new reviewed release version rather than reconstructing the same version. This does not limit a previously imported, self-contained compatibility baseline for an already-published dependency. Trust configuration review is a maintainer prerequisite for each existing package, including direct-publish permission. `npm whoami`, configuration review, and a dry run are not trusted-publisher success tests; a real approved publication and independent provenance verification are the first conclusive evidence.

Alternative considered: one workflow per package or a new release framework would duplicate source authorization, toolchains, archive transfer, registry verifier, and CI policy. The existing filename and mechanisms are retained.

### 5. Reconciliation and selected public gates

For each selected exact coordinate, preflight exact-version metadata and expected integrity/provenance before mutation. Classify it as absent, matching published, or unsafe/ambiguous. Skip a matching version only when its SHA-512 and verified authorized publication identity equal a bound verified outcome **or** a durable pre-publication attempt whose registry result has now been independently established. Publish only absent versions after fresh protected approval and successful retention of the *new* attempt record. Never overwrite a version or interpret a temporary 404 as definite absence without bounded readiness checks. Where a package has already published during a partial attempt, the continuation must validate its original outcome/attempt and all predecessor dependency gates before moving on. An attempt with no matching registry evidence remains unresolved, not successful; an ambiguous accepted publish command is not automatically rerun. Package-wide metadata visibility may lag an exact-version lookup; bounded read-only retries address that alone.

Parameterized `registry-verifier.mjs` uses exact registry coordinates/approved evidence, validates the installed, nonlinked dependency graph and `npm audit signatures`, independently verifies Sigstore certificate/provenance and expected digest/repository/publishing commit/workflow/issuer, then executes selected clean consumers. UI includes exact token baseline, React peers, assets, Geist opt-in, light/dark and browser checks; SDK includes neutral consumer, cross-origin messaging, and production-host compatibility; token-only includes its own archive/consumer/browser guarantees. Separate network-capable lockfile/browser provisioning from offline installation/build/smoke. No test fixture is presented as a public-registry success.

### 6. CI and specifications remain ordered

Extend existing `package-inputs.mjs`, `Check-pending-requests.yml`, and workflow-contract tests for registered manifests/changelogs, policy/inventory, compatibility baselines, record/publisher/verifier tooling, canonical sources/assets/notices, React and host inputs, and the retained workflow. Each selected job provisions its own caches/browser before consumer-dependent tests. Preserve unrelated-application skip behavior and normal app checks.

Do not falsely complete predecessor task 12.7. The predecessor main-spec sync is already reflected in the current main document, but its final close-out remains separate from this implementation. Follow `openspec-sync-specs` semantically: settle and archive the predecessor without re-syncing stale incident requirements over cleanup; then sync/verify/archive the implemented retirement delta; then, after this change is implemented, sync this delta against that post-retirement main and archive it. Until then, validate the new delta both normally and in a disposable post-retirement specification copy. Old requirements must never be reintroduced by later archival order.

## Risks / Trade-offs

- **Registry/trust prerequisites:** existing package ownership does not prove exact direct Trusted Publishing settings. Maintainers review package settings; CI cannot credential-free inspect them. Actual OIDC rejection blocks mutation/continuation without credential fallback; initial fourth-package creation remains separately authorized.
- **Historical baseline retention:** a UI-only release needs a verified self-contained prior token baseline and exact registry bytes/provenance, not the old CI ZIP. Missing/altered baseline fields block approval; accepting a tag would weaken reproducibility. Expired *selected candidate or attempt* artifacts still block publication continuation.
- **Partial publication:** a new dispatch has a different execution identity, while candidate bytes came from an earlier commit. The pre-command attempt artifact survives a lost final outcome and preserves expected identity; upload/readback failure blocks the publish. Ambiguous npm results fail closed and only registry reads retry.
- **Selection complexity:** specialized consumer gates differ by package. Registration profiles retain reviewable explicit mappings and negative coverage; generic record logic cannot silently skip a package's archive/license/browser/host guarantees.
- **Version-review discipline:** manifest/changelog authority eliminates duplicated coordinates but requires a reviewed explicit release PR and lockfile update. Preparation does not itself approve publication.

## Migration Plan

1. Add inventory, policy, schemas, changelogs, a self-contained reviewed compatibility baseline and record model using fixture coordinates first. Verify alpha.1 token registry bytes/provenance once against historical evidence, then retain its exact expectations in the ledger without changing published versions, public exports or historical appendix; keep development/fixture commands.
2. Parameterize candidate pack/validation, evidence transfer, registry verification, selected consumers, and positive/negative tests. Keep producer-wide regression commands green and prove SDK-only, UI-only and combined selected candidate sets plus fourth-registration fixture behavior. Preserve existing token/UI/SDK guarantees.
3. Add `prepare-only` selection, then protected `publish` and read-only `verify` conditions in the retained workflow. Add source authorization, artifact retrieval/recheck, durable pre-command attempt upload/readback, actual-execution outcome binding (including lost outcomes), immutable-byte publication, bounded read-only reconciliation, maintainer trust-review gate and actual OIDC failure handling, and no-publication-path regressions. Provision caches/browser separately; document exact manual dispatch fields and direct-trust setup without changing npm/GitHub settings.
4. Verify package quality, controlled release tests, archive and offline consumers, browser, host regressions, workflow selection, exact toolchains, strict OpenSpec, and independent implementation review when implementation is authorized. A fixture rehearsal is not actual OIDC or registry evidence. Maintainers separately review version/changelog PR and trust configuration; actual publication remains a manual approved operation.
5. Close out specs in predecessor → retirement → this-change order, verifying each semantic synchronization and archive. Do not mark predecessor 12.7 complete without its required trust/token-revocation evidence, and do not resync old incident requirements after retirement.

Rollback expectations: a preparation or pre-approval failure leaves npm unchanged and the record available. A publication failure cannot unpublish/overwrite an immutable version; stop, retain artifacts/outcomes, read-only reconcile, and continue only missing exact versions under new approval with the same verified bytes. Changed bytes or irretrievable evidence require a new reviewed version and fresh record. Verification can be rerun read-only from retained evidence; a failure is not repaired by local fallback.

## Open Questions

No package coordinates or registry changes are proposed here. Before a *real* ordinary publication, maintainers must review each package's direct trusted-publisher settings and protected environment, document evidence for the predecessor's still-open token-revocation/trust task, and approve the reviewed version/changelog source. The implementation default is a self-contained, source-reviewed compatibility-baseline ledger plus retained candidate/attempt GitHub artifacts. The runbook must state the repository's actual artifact-retention setting and retry window; if a publication candidate or attempt artifact expires, retry fails rather than choosing another storage or reconstructing bytes. This does not invalidate an already imported prior-dependency baseline. These are execution prerequisites, not architectural choices or assumptions that the published alpha.1 packages or preparation-only run fulfilled them.
