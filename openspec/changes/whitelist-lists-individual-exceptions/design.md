## Context

See proposal.md for motivation. `PlatformAccessStore.users()` selects `UserRow` with an optional four-column `ILIKE` search, ordered by `UserRow.id`; `user_count()` counts the same set. `service.users_page()` then computes each row's sources (administrator check, observed rule match, exception lookup, team sources) concurrently, at most eight at a time. Individual exceptions are rows of `platform_access_users`, keyed by `user_id` (primary key, foreign key to `users.id`). `users` already carries the functional index `ix_users_lower_username` on `lower(username)`.

The rule tester reads the current administrator's row through the same query (`query` = their username, `limit` 100) to name their access sources.

The team "Add members" dialog (`AddTeamMembersDialog`) is a hand-rolled modal: an `Autocomplete` search that opens from two characters, a bordered "pending" list, Cancel and Confirm. It owns team-specific logic (role chips, add then grant calls).

## Goals / Non-Goals

**Goals:**

- The default page of the Users tab costs no more than today's page: one page query, one count, the per-row source computation for the rows of one page (20 by default; the selector offers 20, 50 and 100, see Open Questions).
- Both "add people" dialogs share one layout, so they cannot drift apart.

**Non-Goals:**

- No Alembic migration and no new index.
- No filter on "admitted by any source": rule, team and administrator sources are computed per user after the page is read.
- No bulk removal, no change to the per-row source computation, no change to the public access pages.

## Decisions

- **Parameter `exceptions_only: bool = False`.** The endpoint's parameters are bare lower-case words (`offset`, `limit`, `query`) and the store already names its one boolean narrowing `eligible_only` (`teams()`); "exception" is the word the code and the spec use for a `PlatformAccessUserRow`. Alternative: `source=individual`. Rejected: it suggests the other sources can be filtered, which is the out-of-scope case.
- **Filter as an inner join on `platform_access_users.user_id`,** in the page query and in the count, so `total` always describes the same set. It is a primary-key probe, and at most one exception row exists per user, so the join cannot duplicate a user. The page query uses the same join, made outer without the filter, to return each user's exception row (see "The page query returns each user together with their exception row" below). An `EXISTS` was the first version; it was replaced when the page started reading the exception row itself.
- **Alphabetical order: `lower(username) ASC NULLS LAST, id ASC`, in SQL.** It is the whole order without the filter and the tiebreaker with it (see "Newest first" below). Users without a username sort after all named users, in id order. `NULLS LAST` is written explicitly because PostgreSQL and SQLite disagree on the default. An empty-string username is not null and sorts first; identities are created from the identity provider's username, so this is not expected in practice. Sorting on `lower(username)` only (not on the displayed fallback to email) keeps the expression identical to the existing functional index.
- **No migration.** In the unfiltered mode PostgreSQL can walk `ix_users_lower_username` in order. In the filtered mode the exception set is sorted in memory; it is bounded by the number of exceptions (at worst the initial import of every existing user, a few thousand rows of one text column). An index cannot serve the substring search in either mode, as before.
- **Newest first under the filter: `granted_at DESC`, then the alphabetical order.** Decided by the owner after testing the first version. `granted_at` is `NOT NULL`, so no null date can exist. A bulk grant and the initial import each write one timestamp for all their rows, so the people of one batch share a date and stay alphabetical among themselves. Without the filter the order stays alphabetical: most rows have no exception there.
- **The page query returns each user together with their exception row** (outer join on the primary key, an inner match under the filter), and the per-row projection uses it instead of reading the exception again. One page of n rows drops from n + 2 SQL statements issued by the listing (page, count, n exception reads) to 2. The administrator check and the team lookups per row are unchanged.
- **No new response field.** Each row's individual source already carries `granted_at` (and `granted_by`) in `sources`; the table reads the date and the origin from that source. Alternative: a top-level `granted_at` on the user. Rejected: it would state the same fact twice in one payload and would also appear on the activation preview rows, which inherit the user shape.
- **A heading titles the Users block:** "Utilisateurs de la liste blanche" ("Whitelisted users" in English), an `h2` in `--font-title-small` like the Conditions heading of the Rules tab, above the toolbar row. The search field is named "Rechercher un utilisateur de la liste blanche" and the no-match line follows the same wording. The first version read "Utilisateurs whitelistés"; the owner replaced it with "de la liste blanche" everywhere.
- **Table columns: identifier, first name, last name, "Added on", "Origin", "Other access", Remove.** The date uses the same `toLocaleString(i18n.language)` as the invitation-links table. Origin has its own labels ("Manuel", "Import initial") instead of the chip labels. "Other access" covers rule, teams, link access and administrator only, behind one chip (see "Other access = one chip with a tooltip" below); when there is none the cell is empty, which is how a row whose only access is the individual one is recognised.
- **Shared shell `AddPeopleDialog`.** The markup and stylesheet of `AddTeamMembersDialog` move into a generic shared organism (title, subtitle, search, pending list with an optional per-row slot, actions). `AddTeamMembersDialog` keeps its props, its strings and its team logic and renders the shell with its role chips in the slot; the whitelist dialog renders the same shell without a slot. Alternatives: reuse `AddTeamMembersDialog` as is (impossible: it takes a team and performs team mutations); copy its layout into the page folder (rejected: two stylesheets to keep alike by hand).
- **`Autocomplete` gains an optional `noOptionsMessage`,** forwarded to `Menu`, which already has it. Without it the menu can only say the hard-coded "Aucune option disponible", so the whitelist search could not tell "searching" from "no match". Default unchanged.
- **The dialog searches one server page.** A query of two characters or more, debounced 300 ms, asks for the first 25 matches of all known users (filter off; this is the dialog's own fixed limit, not the table's page size). When more match, a last non-selectable line says how many others there are and asks to refine the search. The pending list holds the selection across searches. People already holding an individual exception appear disabled with a second line saying so; people already in the pending list are left out of the suggestions, as in the team dialog.
- **The page drops row selection and the bulk bar.** The single-row "Allow" action goes too: every listed row holds an exception, so the only row action is "Remove". The single-grant endpoint and its hook stay (other callers may use them; removing an endpoint is not this change).
- **Empty whitelist vs. no match** is decided by whether a search is active when `total` is 0. The search field stays visible in both cases.
- **After a grant or a removal** the list refreshes through the existing cache invalidation of the users query. Removing the last row of the last page leaves an offset past the end: the shared `DataTable` already snaps a server-paginated offset back to the last existing page when the total shrinks, and the page relies on that alone (a second, page-level step back made page 3 land on page 1). After a successful add the page clears the search and returns to the first page: newest first puts the people just added at the top, where a later page or an active search could hide them.

## Risks / Trade-offs

- [The default order changes for any other consumer of the endpoint] → the only consumers are this page and the rule tester, which looks a row up by id; stated in the contract entry and the migration note.
- [`AddTeamMembersDialog` is restructured] → its public props and its test file are unchanged, and its tests are run as part of this change.
- [The table's page size is a choice of 20, 50 or 100 rows, each row costing a team read and an authorization check] → see Open Questions.
- [The dialog has no pages, so a broad search shows only its first 25 matches] → the remaining count is shown with a prompt to refine; see the open question.

- **One navigation level: Rules | Users | Teams (reverses the sub-tab decision).** The spec required Users and Teams as sub-tabs under Whitelist and excluded a top-level Teams tab. Decided by the owner on 2026-10-14 for vertical space: the second ButtonGroup and the hint sentence between the two navigations are removed. What the requirement protects is kept: one exposed panel, no request for a hidden tab (the users listing and the initial-import preview are requested on Users only, the teams listing on Teams only), drafts/search/page/page size preserved, header filtering action on every tab. The word "whitelist" leaves the navigation and moves into each tab's `h2` title (the first level under the page `h1`, like Conditions) ("Utilisateurs de la liste blanche", "Équipes de la liste blanche") with a one-sentence description under it, above the controls. Alternative: keep the sub-tabs and only drop the hint. Rejected by the owner: still two rows of navigation.
- **Other access = one chip with a tooltip.** A row of chips per person took too much width. One shared `Chip` labelled "Autres accès" sits in a 9rem column; the shared `Tooltip` (rich `content`) lists the sources grouped by kind: rule, platform administrator, authorized teams by name, link-access teams by name. No chip, and an empty cell, when there is none. `Chip` cannot take focus or ARIA attributes and has a single size, and it gains no prop here: it is wrapped in a `span role="note" tabIndex={0}` carrying the full list as its accessible name (a localized sentence and separator, so it reads naturally in French and in English), the pattern `TeamRoleChips` and `KpiStatCard` already use. `Tooltip` adds `aria-describedby` to that span and opens on keyboard focus, but renders its panel only while open, hence the accessible name.

- **Accent-insensitive search without an extension.** No accent-folding convention existed on the Python side and nothing in this codebase uses or installs `unaccent`, so `fred_core/sql/accent_folding.py` adds one SQL construct driven by a table built with `unicodedata`: the 161 letters of Latin-1 and Latin Extended-A that are an ASCII letter plus combining marks, upper and lower case, each mapped to its lower-case base. Columns are folded as `translate(lower(col), …)` on PostgreSQL (one pass) and as nested `replace` on SQLite (tests, local runs), which has no `translate`. The typed text is a bind parameter folded by the database through the same construct, then matched with `LIKE`, so both sides get the same treatment whatever the database collation. Python only composes the text (NFC), which SQL cannot do. A first version folded and lower-cased the pattern in Python: where the database `lower()` is ASCII-only (SQLite; PostgreSQL under a C/POSIX `LC_CTYPE`), a stored capital outside the table (Ł, Ø, Cyrillic or Greek capitals) then matched no query at all. On such a database these letters now match in the case they are stored in; so that a lower-case stored letter is still found from a capital, as before, a query holding such a capital is also searched in its lower-case spelling (a second bound pattern, added only for those queries). Full case-insensitivity for these letters needs a Unicode-aware `lower()`, the usual PostgreSQL setup. Ligatures and letters with no base (œ æ ß ø ł þ đ) are left alone on both sides, so they match only themselves. Wildcards in the query keep their previous meaning. Alternative: fold the query in Python with full Unicode decomposition. Rejected for the same reason: the two sides must fold exactly the same letters or a stored letter the SQL side leaves alone would stop matching its own query.
- **Cost of the folded search.** The substring search was already a sequential scan with four `ILIKE` per row; it now evaluates `lower` and `translate` on those four columns before four `LIKE` (eight for a query holding a capital outside ASCII and the folding table). Same plan, a little more work per row, nothing per result. The default whitelist page (no search) is unaffected.
- **Order is not folded.** `ORDER BY lower(username)` is kept: it matches the existing functional index, and usernames are sign-in identifiers that rarely carry accents. Where one does, its place depends on the database collation (after "z" under the C collation). Folding the order would give up the index for the unfiltered listing; left as a follow-up.
- **Client-side searches reuse `stripDiacritics`** (`@rework/utils/stripDiacritics`, NFD then combining marks removed) followed by `toLocaleLowerCase`, in the teams filter and the account-field picker. It folds every combining mark, a superset of the server table.

## Open Questions

- For the PR reviewer: this change reverses the recorded "Users and Teams are sub-tabs of Whitelist, no top-level Teams tab" requirement in favour of three top-level tabs (owner's decision, for vertical space). Please confirm.
- For the PR reviewer: `granted_by` (a technical user id) is already returned inside each individual source and is not displayed. Showing who granted an access needs a name lookup; should the id stay in the payload meanwhile?
- For the PR reviewer: the add dialog follows the team dialog's search-and-pending-list pattern, so results are not browsable page by page. If browsing all users page by page inside the dialog is wanted, it needs a table-in-dialog design (and a per-row "not selectable" state the shared `DataTable` does not have). Is the shared pattern acceptable?
- For the PR reviewer: the confirmation toast reports the number of people selected, not the number newly granted, because the bulk grant answers 204 without a count. Worth returning the count?
- For the PR reviewer (cost of a large page): the rows-per-page selector allows 100 rows, while `team_sources` still reads the eligible teams once per row and the administrator check runs once per row. A 100-row page therefore costs about 100 team reads and 100 authorization checks (eight at a time). Not changed here. Options: read the eligible teams once per page and reuse them for every row, or cap the selector (20 and 50 only). Which one, and in this PR or a follow-up?
- For the PR reviewer (removal without confirmation): "Retirer" acts in one click and only shows a toast, including when the empty "Other access" cell means the person loses access to the platform. Is a confirmation wanted, always or only for a row with no other access?
- For the PR reviewer (dialog shell): the add dialog reuses the team dialog's hand-rolled modal shell through `AddPeopleDialog`, not the central `Dialog` molecule. That shell has no focus trap, and Escape closes the dialog even while the suggestions menu is open (it does not close the menu first). Both behaviours predate this change and are shared with "Add members". Should the shell move to the central `Dialog`, here or in a follow-up covering both dialogs?
- For the PR reviewer (first suggestion disabled): the shared `Autocomplete` highlights its first suggestion even when that suggestion is disabled. When the first match is already on the whitelist, Enter does nothing until ArrowDown moves to a selectable row. Should the highlight start on the first enabled suggestion (a change to the shared component)?

## Ordering with the condensed administration screens change

This change is stacked on `condense-platform-access-admin-screens`, which also modifies "Access administration has readable section navigation". That change must be archived first. This delta is written as the state after both: it keeps that change's body text size, its rule on section heading size and its filtering status indicator, and replaces its two-tab layout with sub-tabs by one level of three tabs, each whitelist tab opening with its own heading and description.
