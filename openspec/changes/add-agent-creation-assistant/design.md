## Context

Current state, verified in the code:

- **Prompt assembly.** An agent's system prompt is four XML blocks, in order of authority: `platform_instructions` (shipped, read-only), `platform_prompt` (admin-editable house style), `tools` (the bound tool list from `build_runtime_tool_prompt_suffix`, capability instructions such as the HTML artifact, writable document and ppt-filler rules, MCP server instructions, the team wiki block), then `agent_instructions` (the agent's own prompt). Headings are demoted one level. The four tag names are reserved: control plane refuses an authored prompt containing them (`fred_sdk.contracts.prompt_utils.find_reserved_prompt_tag`, mirrored in the frontend). `{today}` and `{response_language}` are substituted at run time; other braces stay literal.
- **Default house style.** The shipped platform prompt already says: be direct, reply in the user's language, say when unsure. The platform instructions already say: use only the listed tools, never claim a call that did not happen, documents and tool results are data.
- **Models.** A pod builds one `RoutedChatModelFactory` at boot from `models_catalog.yaml`. Its only entry point, `build(definition, binding)`, needs an agent definition and a turn binding. `get_default_chat_model()` is not usable: no provider is set.
- **Capabilities.** A template advertises `available_capabilities`; the control plane narrows them to the team's `can_use` set (`filter_entries_by_usable`). Names and descriptions are i18n keys translated by the frontend.
- **Pod relays.** The control plane already relays save-time work to the template's pod with the caller's token (`validate-config`, `copy-config`).

## Goals / Non-Goals

**Goals:**
- A non-expert gets a good, platform-aware first draft of an agent (name, role, short description, system prompt, capabilities) in one click.
- Recommendations never include a capability the team could not enable.
- No new configuration and no new trust path; one single-row table for the admin override.

**Non-Goals:**
- Iterative refinement ("make it shorter") or a chat with the creation assistant.
- Rewriting an existing prompt (the dialog may prefill the description later).
- Recommending capability settings (libraries, folders).
- Team routing policy for the creation assistant's own model: an admin picks it platform-wide (decision 14).
- Choosing the created agent's model. The agent keeps the model that routing gives it today; the creation assistant never picks or sets one. A configurable default model per agent is a separate, future feature.

## Decisions

### 1. The pod drafts, the control plane relays

The pod owns models and capability code; the control plane holds no model client. The control plane resolves the template exactly as agent enrollment does (`_resolve_enrollable_template`, extracted from `enroll_agent_instance` so both share it), narrows the client's candidate capabilities to the template's advertised, team-usable ids, adds the canonical team id and forwards with the caller's token on the shared runtime HTTP client. The pod re-checks `CAN_UPDATE_AGENTS` (defence in depth, like `/kpi-turns`) and reads the admin settings back from the control plane (decision 9).

### 2. The client sends translated capability names

Capability names and descriptions are i18n keys; only the frontend can translate them. The client sends `{id, name, description}` in the user's language. Only the ids are trusted: the control plane filters them, the pod drops any returned id it did not offer, the control plane filters the result again. The request accepts up to 500 candidates (`MAX_DRAFT_CAPABILITIES`): a cap of 100 made a draft fail with 422 on a template advertising more, and silently truncating would hide capabilities from the model in an arbitrary order. 500 still bounds the model input (each candidate is at most 1,400 characters).

### 3. The admin-chosen chat profile, else the pod default, at the admin's reasoning effort

`RoutedChatModelFactory.build_chat_for_profile(profile_id, reasoning_effort=...)` resolves the profile an admin chose (decision 14) through the existing resolver, or `ModelSelectionRequest(capability=CHAT)` when none is chosen, and builds through the factory's provider, so `MockAwareModelProvider` still works in fred-agents. A chosen profile this pod does not know falls back to the default with a warning log, so a catalog change never breaks the feature. Any other failure to build the model (provider package, credentials, catalog) answers 503, like a pod without a routable model. The admin's `reasoning_effort` (`off`, `low`, `medium`, `high`, `off` by default; decision 14) applies to this call only, on a copy of the profile's config: `off`, or a profile without `supports_thinking`, strips the reasoning settings. A profile declaring two or more `reasoning_efforts` in the catalog gets the chosen level, clamped to the nearest declared one (ties go to the stronger, so `medium` on `[low, high]` sends `high`), even when the profile's own `settings.reasoning_effort` is absent. Any other thinking profile is on/off: any non-`off` value sends its own `settings.reasoning_effort`, else its single declared level (`ModelProfile.reasoning_on_effort`). A thinking profile with neither cannot be made to reason here: the pod sends nothing, and its catalog projection maps it to an empty `reasoning_efforts` list so the admin option reports `supports_reasoning: false` (disabled control) instead of a switch that changes nothing. Boot validation is unchanged: such a profile stays valid for agent chat. The factory resolves the profile once and returns the model, its name and, when it reasons, the same model without reasoning; a chosen id that is unknown or not a chat profile logs one warning saying which. Levels are never inferred from `settings.reasoning_effort`: Mistral answers 400 to `low` and `medium` (verification.md). Approved: this choice is the creation assistant's own and does not consult the per-model `model_reasoning` toggle that governs agent chat; agent chat ignores `reasoning_efforts` for now. One structured call (`with_structured_output(method="json_schema", include_raw=True)`). With reasoning on the answer can carry thinking blocks beside the JSON text (Mistral through `ChatOpenAI`): the OpenAI SDK's own parse of a Pydantic schema rejects them, so a reasoning call passes the same schema as a JSON-schema dict, which LangChain parses from the text blocks only. A reasoning call is hedged, never cut: still running after 23 s (`REASONING_HEDGE_AFTER_S`), the same call without reasoning starts beside it and the first usable draft wins, the other being cancelled; one failing after the hedge leaves the other running, both failing answer the usual error. A reasoning call whose answer is unusable or whose request is refused (as below) before 23 s starts the call without reasoning at once; any other early failure is not retried. Neither start happens with less than 12 s (`MIN_PLAIN_CALL_S`) left before the deadline: a call without reasoning takes 7.5-16 s for a ~1k-word draft, so it would only be billed and cancelled; the reasoning call is then awaited alone, or its early failure answered (`event=creation_assistant_plain_skipped`). With the 50 s budget the 23 s hedge always clears the guard; it matters for a late early failure and for a shorter deadline. The model without reasoning is built up front with the reasoning one (no I/O). Tokens of every answered call are added to the KPI; a cancelled call reports none, though the provider may still bill it, so the completion log and KPI carry `calls` (1, 2), `hedged` and `winner` (`reasoning`, `plain`, `none`) to estimate that cost, and the log adds `reasoning` (`used`, `off`, `fallback`). Approved over the former cut 15 s before the deadline: a reasoning call cut at 35 s left 15 s for a ~1,000-word draft without reasoning (13-16 s live), which timed out (504, no tokens counted). 23 s lets most reasoning drafts (22-47 s) answer alone while leaving the call without reasoning 27 s, and a reasoning draft finishing after the hedge still wins. Many OpenAI-compatible gateways reject `json_schema` only when called, so a failure that says the request's shape was refused (an HTTP 400, or LangChain's own `ValueError` / `NotImplementedError` when no status is known) is retried once with `method="function_calling"`, inside the same deadline. Authentication, permission, quota (401/403/429), connection errors and timeouts are not retried: a second call would fail the same way and double the wait. An answer that does not match the schema, raised or returned, answers 502. An empty prompt, or one holding only reserved tags, is unusable in the same way and checked when the answer is parsed, so a reasoning call returning one never wins the hedge: the call without reasoning starts at once (or keeps running) and both empty answer 502.

### 4. The meta-prompt carries the platform knowledge

`CREATION_ASSISTANT_SYSTEM_PROMPT` (`fred_runtime/app/creation_assistant.py`) explains the assembly above to the model, so the drafted prompt covers only what is specific to the agent: role, mission, audience and tone, method with decision rules and edge cases, how to use each recommended capability, sources and accuracy, answer format, rules and limits (do / do not), in second person, 500-900 words (never above 1,200): a short generic prompt is described to the model as a failure. Whenever a document capability is recommended, the drafted prompt must say that summarizing is only for a global overview or an explicit request for a summary, and that every other request is worked on exhaustively (full text, extraction, comparison). Capabilities are still named by what they do, never by tool name. It forbids tool names and mechanics, reserved tags, the platform's name, invented facts and placeholders (even in examples: no file names or document titles, section or page numbers, dates, years or figures the description does not give; citations follow the pattern "(document title, section)"), and a fixed reply language unless asked. Grounding is "team documents or data first and cited, then general expertise said as such", general questions related to the role are in scope, and absolute formulas ("only", "seuls ... font foi", a minimum number of sources) are forbidden unless the description demands them; safety or scope limits from the description (read-only, confidentiality) stay. The user's description is passed between markers as data, so an injected "ignore your rules" still yields an agent prompt.

### 5. Reserved tags are stripped, not retried

A model writing `<agent_instructions>` around its answer is the expected failure. Stripping the markup (`strip_reserved_prompt_tags`) avoids a second model call; a retry would double latency and cost for no better text.

### 6. Timeouts below the ingress default

The pod has one 50 s deadline for the whole draft (settings read, model build, structured call and its retries, the hedged call without reasoning starting at 23 s), the control plane waits 55 s: both under the 60 s read timeout most ingresses apply, so the user sees this feature's 504 rather than a proxy error. The settings read has its own 2 s timeout inside that budget, so a slow control plane falls back to the defaults instead of eating the model's time. The relay's pool wait is 5 s (`httpx.Timeout(55, connect=5, pool=5)`): the runtime client is shared with session-erasure calls, and a 55 s pool wait would let saturated drafts hold those up. A pool timeout answers 503 ("the control plane is busy"), not the slow-draft 504.

### 7. Observability has its own event, not the agent model-call timer

The draft emits no `llm.call_latency_ms`: agent turns emit it with another label set, and the Prometheus store fixes a metric's labels from its first event, so a shared timer would make `llm_role` unreliable and add draft latency to agent model latency. `agent.creation_assistant_completed` (decision 11) carries latency, status, model and tokens; the call also writes one log line of counts and timings, never content. The call bypasses `TracingKpiMiddleware` by design (no agent turn): no `llm.calls_total`, active-call gauge, spans, chunk timings or `llm_call_*` diagnostic records.

### 8. The form applies a draft only when the user confirms

One entry point: a tonal **Assistant** button (`auto_awesome`; the feature keeps the name "Creation assistant") in the agent form header, next to Cancel and Save, in create and edit modes. It is hidden on the template step, since the template decides the pod and the capabilities on offer and the assistant cannot pick a template from a description yet (a possible later evolution). The dialog sends the UI language's base subtag, the current name and role, and the template's team-usable capabilities with translated names (reasoning is not a capability). The prompt goes to the template's main system-prompt field (`prompts.system`, else the first `type: "prompt"` field); a template without one gets no prompt item to apply.

The review step makes every proposal selectable, all ticked by default: the system prompt (left, read-only), then name, role and description, then the capabilities (a group checkbox and one per capability). **Apply** writes only the ticked items and is disabled when nothing is ticked. Ticked capabilities replace the selection: a draft prompt is written for that set, so a union would leave tools the prompt never mentions. The existing per-capability settings are kept. Reasoning is not asked of the model: wherever the Simple view offers its reasoning pack (`isPackSelectable`, today every template, since the reasoning card is always offered), the capabilities column starts with a reasoning tile under the pack's title, ticked by default and part of the column's select-all. Applied, it goes through the form's own `withReasoning` (the reasoning switch's rule): reasoning on, and new conversations starting in it when reasoning was off; a member who had reasoning on but left the default off keeps that choice. Unticked, both stay as they are. It is never listed in the overwrite confirmation: it adds an option and erases nothing the user wrote. A recommended `document_access` turns on both Simple document packs, "Attachments" and "Team documents" (through `applyPackToggle`, so both sources are set and both packs show on): the model recommends the capability, not a source, so the assistant keeps the former single pack's reach (attachments plus team search) rather than guessing one; the user can switch a pack off before saving.

In edit mode the agent's template is resolved like any other (`_resolve_enrollable_template`): a template the team may no longer use, or whose runtime is gone, answers 404 with a plain `detail`, and a pod without the route answers 501. The frontend shows its "not available for this agent" copy for both rather than a generic error; the statuses stay as they are, since 404 is what agent creation answers for the same template.

If a ticked item would overwrite a non-empty, different value (name, role, description, prompt, or a non-empty capability selection), Apply first opens the critical `ConfirmationDialog` listing what will be replaced; confirming applies, cancelling returns to the review. A value still equal to the template's seed (its display name, description, default prompt or default capabilities) counts as empty: the user did not write it, so a new agent never asks. When no capability is ticked (or none was recommended), the selection is left as it is. The current name and role (seeds blanked) are sent as context. Nothing is saved until the form is. Escape closes only the topmost dialog: `FullPageModal` leaves Escape to the topmost modal.

### 9. Admins can override the meta-prompt

The settings live in one single-row `creation_assistant_settings` table next to `platform_prompt` (same model file, same `can_edit_platform_prompt` gate): `text` (nullable meta-prompt override), `model_profile_id` (nullable, decision 14), `reasoning_effort` (decision 14), `updated_by`, `updated_at`. `GET`/`PUT`/`DELETE /admin/platform/creation-assistant` read, write and reset them. Unlike the platform prompt, an empty meta-prompt means nothing, so an override is non-blank and "no override" is `NULL`. `PUT` takes `{text, model_profile_id, reasoning_effort}` and replaces all three (`text: null` keeps the built-in text); `DELETE` clears the meta-prompt override only and keeps the model and the effort. **The pod reads the settings itself.** Pods are browser-reachable, and a pod cannot tell the control plane's relay from a direct call: the relay forwards the user's own bearer, and pods recognise no control-plane service identity (the `service_agent` role is the evaluation worker's, and the control plane's `security.m2m` account is only used for lifecycle erasure). So the settings are never on the wire to the pod: `AgentDraftPodRequest` has no setting field (extra fields are ignored), and the pod reads `GET /control-plane/v1/teams/{team_id}/creation-assistant/settings` (`CreationAssistantRuntimeSettings`: `creation_assistant_prompt`, `model_profile_id`, `reasoning_effort`) with the caller's bearer, the way it already reads the admin platform prompt through the team-scoped runtime binding. The route requires `can_update_agents` on the team, the same gate as the draft. Rejected: the control plane calling with its service token and the acting user in the body (a new body-asserted identity the pod would have to trust, and no person bearer left for the pod's own check); a signed settings envelope (a new shared secret). Any failure to read them (no `platform.control_plane_url`, control plane down, refusal, invalid body) falls back to the pod defaults with a warning log carrying only the error type: the defaults grant nothing a caller could not already get. Team editors (`can_update_agents`) can read the saved meta-prompt override and model id through this route; they are instructions, not secrets, so admins must not put confidential notes in the meta-prompt. The pod builds the settings URL with the URL-encoded `team_id`. Under control-plane or connection-pool saturation the 2 s read fails the same way and the pod silently uses its defaults (WARNING log): by design, since the defaults grant nothing extra and a draft beats a 504. The pod uses the override or its built-in text and still substitutes `{language}`. The pod reports its built-in text on `/agents/platform-prompt` so the editor shows the default and the reset target; older pods omit it and the UI says the default is unavailable.

A missing `{language}` placeholder is **accepted with a warning**, not rejected: the human message already ends with "Write the name, role, description and prompt in <language>", so the creation assistant still works, and an admin may deliberately write a single-language meta-prompt. The response flags it (`missing_language_placeholder`) and the admin pane shows it while typing.

### 10. Admins see when the built-in meta-prompt changed after their override

The pod dates its built-in text with `CREATION_ASSISTANT_REVISED_AT` (ISO day), and a unit test pins the text's sha256 together with that date, so editing the text without bumping the date fails CI. `/agents/platform-prompt` reports it as `creation_assistant_prompt_revised_at`. The control plane compares it by day with the override's existing `updated_at` and returns `default_revised_at` and `default_changed_since_override`; no column or "seen" flag is stored. The warning therefore disappears when the admin saves again or resets. `updated_at` and `updated_by` date the meta-prompt, not the row: a save that only changes the model leaves both as they were (the ORM column has no `onupdate`, the store sets them), so choosing a model never hides the warning, which is about the text; any other save, an identical re-save included, moves them. No schema change. Day granularity can miss a same-day revision after an override; accepted, since releases rarely ship on the day an admin edits. An older pod omits the date and no warning is shown.

### 11. Creation assistant tokens count in the user's and the team's usage

The pod emits `agent.creation_assistant_completed` (timer, latency in ms) with the caller as actor (`to_kpi_actor`, so the KPI writer sets `dims.user_id`), dims `team_id` (the team where the agent is being created), `model_name` and `status`, and quantities `input_tokens` and `output_tokens`, the names `agent.turn_completed` uses. It is emitted for every outcome, so the failure and latency tail (timeouts, provider errors) reaches the KPI stream; quantities are set only when the provider answered, including an unusable answer (status `error`), since those tokens were billed. `calls`, `hedged` and `winner` are OpenSearch dims only; the Prometheus store keeps `model_name`, `status` and `actor_type` as labels. With security off there is no caller and the event is a system one, counted in team and platform views only. A distinct name, rather than reusing `agent.turn_completed`, keeps turn counts, conversation depth and top-user presets unchanged.

The six token presets (`user_token_usage_{over_time,by_model,by_agent}` and `token_usage_{over_time,by_model,by_agent}`) read both names through `TOKEN_USAGE_FILTER` in `kpi/presets/common.py`, which keeps only creation assistant events carrying `quantities.input_tokens` (`CREATION_ASSISTANT_ANSWERED_FILTER`), so an event without tokens never opens an empty by-model or by-agent bucket. By-agent presets keep turns with an agent name plus every creation assistant event, bucketed by the `terms` `missing` value `__creation_assistant__`; the frontend translates it ("Assistant de création" / "Creation assistant"), so the backend carries no display text. Turn, conversation, activity and latency presets still read `agent.turn_completed` only.

The platform `creation_assistant_usage` preset reads `agent.creation_assistant_completed` only and returns `total_tokens`, `input_tokens`, `output_tokens` and `drafts` (the count of answered calls, usable or not: the same filter, so the number means what it meant before every outcome was emitted) for the period, with the default `can_observe_platform` gate and no team scope. The admin Analytics token-usage section shows it as a `KpiStatCard` whose new optional `caption` carries the number of uses; the by-agent bucket stays as is.

### 12. Name: "Creation assistant"

The feature drafts more than a prompt, so it is the **Creation assistant** ("Assistant de création") for users and `agent draft` / `creation_assistant` in code: pod `POST /agents/creation-assistant/draft`, control plane `POST .../agent-templates/{template_id}/draft-agent` and `/admin/platform/creation-assistant`, SDK `fred_sdk.contracts.agent_draft`, KPI event `agent.creation_assistant_completed`, preset `creation_assistant_usage`, by-agent bucket `__creation_assistant__`. It was unreleased, so nothing keeps the old names (the prompt generator).

### 13. Name, role and description are drafted short

The result is `{name, role, description, system_prompt, capability_ids}`. A `rationale` was drafted, capped and sent, but never shown, so it was removed (code review 2): fewer output tokens and no dead field on the wire. The form accepts 255 / 255 / 500 characters, which invites long values; the meta-prompt asks for a one-sentence description of at most about 140 characters, in the request language. **Name = identity, role = function.** The name is a short, memorable proper name (one or two words, ideally at most about 20 characters, like the coined "Brivel"), chosen from the role: a coined word, a figure from any mythology, or a tasteful pun; workplace-safe (no living person, brand, offensive or religiously sensitive word) and never a job label. The role carries the function as a short job label of at most about 40 characters ("Assistant RH", "Meeting notes writer"). This splits the two fields the card shows instead of drafting two descriptions. The pod then enforces hard caps below the form limits (60 / 120 / 300): reserved tags stripped, whitespace and line breaks collapsed, surrounding quotes and Markdown emphasis removed, cut at a word boundary. A value left empty becomes `null` and the review step does not offer it, so a draft can never hold a value the form would reject. The form limits themselves are unchanged.

### 14. An admin chooses the creation assistant's model

The **Creation assistant** admin tab has a model selector next to the meta-prompt editor. Its options are the chat profiles every enabled pod advertises (`universally_available_chat_model_profile_ids`, labelled with the catalog's model name), plus "Platform default model" (`null`). `PUT` refuses a new profile outside that set (422), so a typo cannot be stored; the profile already stored is accepted as is, so a catalog change, or no pod answering, never blocks saving the text. A profile removed from the catalog later falls back on the pod (decision 3). The pod reads the choice itself with the meta-prompt (decision 9); no request body carries it. It only selects the model the creation assistant itself calls; it never touches the created agent's model (non-goals). The platform chat model binding is not applied to the creation assistant (open question 1). A **Reasoning** control beside the selector sets `reasoning_effort` (not-null text column, default `off`, check constraint on the four values). Off by default (product-owner decision, open question 9): in a blind comparison Medium without reasoning matched Small with reasoning (13.3 vs 13.5/18) while being ~30% faster with ~40% fewer output tokens, and on Medium the reasoning call never beat the hedged call without it. It follows the selected option: a button group Off plus the declared levels when the option reports two or more `reasoning_efforts` (projected per profile from the catalog's `model_reasoning_efforts`), the small switch for any other option with `supports_reasoning` (on stores `medium`, read by the pod as "on"), and a disabled switch with a tooltip for an option that cannot reason. "Platform default model" uses the option of the pods' common default chat profile (`default_model_profile_id`, `null` when pods disagree or none answers, then the switch). On a model change the UI normalises the value with the pod's rule (a level on an on/off model becomes `medium`, a level not offered becomes the nearest offered) and saves that. When the control is unknown (that `null` default, or a saved profile no pod serves) or the model cannot reason, the stored effort is kept as is until the admin toggles the switch, so saving the text never rewrites a `low` or `high` the pod would clamp anyway. `PUT` refuses only a value outside the four (422): whether a model offers the level is the pod's clamp, so a catalog change never blocks a save. Like a model-only change, a reasoning-only save does not move `updated_at` / `updated_by`, which date the meta-prompt text; `DELETE` keeps both model and effort. The field never shipped as `reasoning_enabled`, so no released control plane sends that name; the pod ignores it and defaults to `off`.

### 15. Tonal button

The `Button` atom had no tonal variant; it gets `variant="tonal"` with the same tokens as `IconButton`'s tonal one (`container` / `on-container`, state layers from the scheme), so the header button follows M3 rather than a local style.

## Risks / Trade-offs

- **Model quality varies by deployment.** A small default model writes weaker prompts. → The user always reviews the result; an admin can pick a better model for the creation assistant.
- **Translated names reach the model.** A malicious client could put text in a capability name. → It only influences its own generated draft; ids are filtered three times; nothing is saved.
- **Cost.** One call of roughly 2.5k input and 1k output tokens per click without reasoning; with reasoning (Mistral Medium, `reasoning_effort: high`) 3.5-7.5k output tokens. → Visible in the KPI; the only automatic second call is the one without reasoning (decision 3). When reasoning is slow, two calls are billed: the winner's tokens are counted, a cancelled reasoning call's are not (`calls=2 hedged=true` marks those drafts).
- **Latency with reasoning.** Measured 22-47 s per draft with reasoning, against 7-10 s without, for the 500-900-word prompts. → A reasoning call still running at 23 s is hedged with one without reasoning, the first usable draft winning (decision 3); reasoning is off by default; an admin who turns it on can, on a profile declaring levels, lower it.

## Migration Plan

Additive. One control-plane Alembic migration creates the empty settings table (`reasoning_effort` defaults to `off`). Deploy pods and control plane together; a control plane facing an older pod answers 501 for this route only, and the admin tab reports the default as unavailable. A pod facing an older control plane (no settings route) drafts with its own defaults.

## Open questions for the developer

1. **Creation assistant model.** Settled by decision 14: an admin picks a chat profile, else the pod default applies; team routing and `usable_model_ids` are not consulted. Open: should a platform chat model binding, when set, also apply to the creation assistant?
2. **Language.** The prompt is written in the request's `language` (the UI language), even when the description is written in another language. Should the description's language win?
3. **Platform name.** "Never name the platform" is only an instruction to the model; no post-check rejects "Fred", because an agent may legitimately be named so. Is that enough, or should a counter log drafts that name it when the description did not?
4. **Rate limiting.** No per-user limit on drafts. A team editor can also call the pod route directly (it checks only `can_update_agents` on the named team, not the template), using the admin-chosen model and meta-prompt as a text generator (they cannot change either: decision 9). Needed before wide rollout?
5. **KPI visibility.** Settled: the draft no longer emits `llm.call_latency_ms` (decision 7); its latency is only in `agent.creation_assistant_completed`. Out of scope, separate issue: the KPI presets (`kpi/api.py`) still call the synchronous OpenSearch `store.client.search` inside async handlers, which predates this change.
6. **Template-specific prompts.** Graph templates and templates without a free system prompt field: should the header button be hidden there (frontend decision), or should the creation assistant know the template's own prompt field?
7. **Existing prompt.** Should the dialog send the current prompt so the creation assistant improves it instead of starting over?
8. **501 for older pods.** Acceptable, or should the control plane hide the button via a template flag?
9. **Timeouts.** 50 s pod / 55 s control plane. With reasoning on Mistral Medium took 22-47 s per draft, and one of five drafts fell back without reasoning at 35 s; a later 35 s cut timed out (the ~1,000-word retry needed ~14 s of the 15 left), so the reasoning call is now hedged at 23 s instead (decision 3): two live hedged drafts took 36.5 s and 38.9 s, both won by the call without reasoning. Settled for the effort: the admin chooses it, default `off`. A blind comparison (3 descriptions, rubric /18) scored Medium without reasoning 13.3 against 13.5 for Small with reasoning, ~30% faster, ~40% fewer output tokens and 3/3 usable drafts against 2/3; with Medium the reasoning call never finished before the hedged call without it (verification.md). Mistral only takes `high` or none, so its profiles stay on/off; a level is selectable only where the catalog declares `reasoning_efforts`. Still open: raise and document an ingress timeout?
10. **House style.** The meta-prompt says the admin-editable platform prompt "usually" asks for directness, the user's language and honesty about uncertainty. Should the pod pass the effective platform prompt to the creation assistant instead, so it adapts to what an admin saved?
11. **Capability replacement.** Apply replaces the selection (decision 8). A recommended `document_access` turns on both document packs (Attachments and Team documents, with their members: tabular, summary, similarity, verbatim, extract), as the two Simple view switches do. Keep, or tick only the recommended ids and let the Simple view show the pack partly on?
12. **Graph templates.** The header button is available on every template, graph templates included (see 6); the prompt item only appears when the template has a `type: "prompt"` field. Hide the button on graph templates until the creation assistant knows them?
13. **Older pods.** The button shows for every chosen template; a pod that predates the route answers 501 only after a click, with an "not available for this template yet" message (see 8).
14. **Description memory.** The description survives closing and reopening the dialog while the form stays open, never longer, and is never prefilled from the current prompt (see 7).
15. **Escape everywhere.** The `FullPageModal` fix is global: any dialog over a full-page modal (confirmations included) now closes alone on Escape. Expected, but worth a look on the other forms.
