## Context

The pod loads discovery once at startup and retains one routable catalog snapshot. Control-plane reads that snapshot through `/agents/models-catalog`; managed turns already request a fresh runtime binding from control-plane. The pod holds the discovery bearer credential, while control-plane owns administrator settings. See proposal.md for the requested behavior.

## Goals / Non-Goals

**Goals:** Refresh and compare verified inventories when Models opens, apply an administrator's URL without a restart, preserve static profiles, and route a confirmed removed choice to a distinct platform fallback.

**Non-Goals:** Parse arbitrary vendor response formats, move credentials to control-plane, refresh on a timer, or substitute a model after an endpoint outage or authorization failure.

## Decisions

1. Store one override URL and the last successful model inventory per `source_id` in the existing PR's single Alembic revision. The pod YAML remains the fallback. Source state has a different lifecycle from per-model display names; keep the existing forced binding and store a separate platform fallback binding.
2. Accept absolute HTTP(S) URLs ending in `/models`, without userinfo, query, fragment, or redirects. The parent URL is the inference base, so the listed model IDs are sent to the endpoint that listed them. The pod uses its existing `OPENAI_API_KEY` for discovery and inference; control-plane never receives it.
3. Opening Features > Models requests a refresh. Control-plane passes the last successfully applied URL in each managed runtime binding. Each pod prepares a candidate using asynchronous HTTP; control-plane validates all candidates before asking pods to activate them. Activation failure triggers a best-effort rollback on every prepared pod. The active router and advertisement swap together. A failed refresh leaves the last successful source inventory intact; an unchanged URL does not trigger a discovery request on every turn.
4. Compare only successful inventories. Persist removed entries with their prior metadata and expose them as unavailable; a failed endpoint or pod fetch cannot create removals. New entries start without a platform default-on grant. Multi-pod removals require successful checks from all relevant enabled pods.
5. Send a separately configured platform fallback in the trusted per-turn binding. Apply it only when a selected profile is in the confirmed removed set. Keep the stored choice, log the actual model, and fail explicitly if the fallback cannot be used. The forced platform binding retains its absolute precedence.
6. The admin API lists source IDs with YAML defaults, saved overrides, last success, refresh error, new and removed IDs. Writes require `can_manage_capabilities`; an override can be saved only for an advertised source and commits only after a successful refresh. The Models tab shows the refresh summary before rows and states the OpenAI format limitation.
7. The pod's catalog reports the profile IDs appended by the successful discovery resolution, then projects their model IDs and source ID. Control-plane carries this provenance and every advertising runtime ID onto each model capability, including across the multi-pod union. Features > Models uses the home-page pill tabs for manual and discovered models, a shared text filter, and the existing model identity style for pod provenance. The Discovery tab has a compact refresh control; source URL editing and removed-model details remain available on demand. It does not infer origin from profile prefixes, names, or wire IDs.
8. Persist a manual chat profile ID for the disappearance fallback. The admin picker offers manual chat profiles available across the known agent pods. The runtime resolves that profile against its current policy when a confirmed removed choice needs fallback, so settings stay pod-local and current. A missing fallback profile fails explicitly. Keep the forced concrete binding independent.
9. Treat explicit `capabilities.completion_chat: false` in a compatible `/models` entry as non-chat and skip it; entries without that vendor extension remain eligible for OpenAI compatibility. Read `max_context_length` when provided and show it as a compact context badge. The standard OpenAI list and single-model APIs do not expose context or modality; omit unknown limits and do not show a model type badge for discovered models. Reasoning effort levels come from declared catalog profile metadata; `/models` does not provide a portable list of supported levels, so do not infer them from a model name or a generic reasoning flag.
10. Add a `discoveries` list to the YAML alongside the existing single `discovery` form; reject a catalog that mixes both or repeats a source ID. One chat default may be declared across all sources and the manual catalog. Keep source ownership in the resolved catalog rather than inferring it from profile IDs. Refresh one named source against the current verified snapshot, preserving the other sources' inventories and effective URLs. Fence revisions, activation rollback, and failed URL backoff per source so activity on one endpoint cannot suppress another. Pod responses list every source and retain the single-source fields for older consumers. Control-plane groups sources from that list and sends the source ID on prepare and refresh. A failed source leaves its last verified inventory in place.
11. Put a small information control beside each discovered model. Its click calls the same source's `GET /models/{id}` through the runtime pod, with the pod's credential and a bounded response. Render the returned object as nested key/value fields in an interactive tooltip. Do not request one detail per row during list refresh: this keeps source latency and rate limits out of the catalog load. Keep context values from `/models` visible on the row.
12. If control-plane cannot verify a configured agent pod catalog, return its runtime ID and URL as a transient warning, along with source IDs advertised by pods that did respond. Keep stored source errors and inventories unchanged: an unverified pod cannot prove that an upstream discovery source failed or a model disappeared. URL edits still fail while their target pods cannot be checked. The Discovered models tab renders a warning rather than a refresh error, while still identifying unregistered sources advertised by verified pods.
13. Restrict URL overrides to `platform_admin`: a changed URL receives the pod's provider bearer key. The pod refresh route independently requires `can_manage_platform` for any `models_url` different from that source's active URL, including direct calls that bypass control-plane. A feature manager may refresh the currently active URL and view source status, but cannot edit the URL in the admin UI.
14. A prepared catalog token or in-flight direct refresh may outlive a source URL change. At activation, rollback and refresh publication, compare its source URL with the current one under the factory lock; a feature manager cannot restore a previously active URL. After a pod restart, the YAML URL is active until a managed turn restores a saved override or a platform administrator refreshes it.

## Risks / Trade-offs

- A changed URL may return different IDs. Stable IDs retain their identities; confirmed removed IDs route to the fallback only when selected. Admin grants for new IDs remain explicit.
- A malicious endpoint could receive the pod credential. Only platform administrators may save URLs, and the UI describes the credential scope. Production operators should allowlist reachable hosts at the network layer.
- A pod or endpoint outage leaves the last verified inventory visible with a failure status. It does not prove that a model disappeared. A changed URL that cannot be verified cannot replace the active router.
- A pod can boot with static profiles if its YAML discovery endpoint is unavailable. A managed turn then applies the last successfully saved URL. A discovery-only pod cannot serve direct local turns until one endpoint responds.
- Activation across pods has no distributed transaction. If an activation response or rollback is lost, a pod may briefly carry a different snapshot. Each prepared pod reports its active revision; the next refresh chooses a revision above every pod and the stored revision so it can reconcile the deployment. No removals are committed from the failed attempt.
- Several discovery sources can list the same wire ID. Their generated profile and model identities remain distinct by `source_id`, so a source-specific URL change cannot silently reassign a saved selection to another endpoint.

## Migration Plan

Deploy the migration and control-plane/pod/frontend together. Existing rows are absent, so YAML URLs and existing forced bindings remain effective. Rollback removes source state and fallback storage and returns to YAML-only discovery.
