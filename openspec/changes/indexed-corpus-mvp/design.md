## Context

See proposal.md - Why. FRED's only prior pull-mode attempt (a Sphere connector, still live in a different, older fork — not in this repository) is documented here as evidence, not as something this design extends: full remote rescan every cycle despite an incremental delta API existing but disabled, no stable revision id (diffed by a raw modified-timestamp string), a changed file minted a brand-new document id with the old one explicitly deleted to fake an update, no leader election across replicas (safe only because that deployment ran a single replica), in-memory-only sync status, and heavy business-logic coupling inside what should have been a generic sync engine. Every decision below closes one of these failure modes structurally, not by adding a check on top of the same shape.

FRED already has one relevant precedent to build on rather than reinvent: the agent-template/agent-instance split (`control_plane_backend/agent_instances/`) for "a platform-wide registered thing" vs. "a team's own instantiation of it," and the `capability` OpenFGA object (`fred_core/security/rebac/schema.fga`) for "admin enables this platform-wide thing per team." This design reuses both shapes rather than inventing new ones.

## Goals / Non-Goals

**Goals:**
- One narrow, provider-agnostic contract (`SourceConnector`) that structurally prevents the specific Sphere failure modes above, not just documents against them.
- Split "what can exist on the platform" (`CorpusType`) from "what a team actually has" (`Corpus` instance), reusing the agent-template/agent-instance precedent.
- A usage-enablement gate that is its own ReBAC object type, not a repeat of the `capability:app__<id>` namespacing mistake already being corrected elsewhere for `app`.
- Reuse FRED's existing push ingestion pipeline for pull-sourced documents rather than building a parallel one.
- Design the ingestion hand-off (D8) so a corpus can be hosted either in-process inside `knowledge-flow-backend` or, later, in a fully separate repository deployed as its own pod — without a rewrite when the second shape is actually needed (2026-09-07 revision, D8-D10).
- Prove push and pull are the same contract, not two code paths: retrofit the existing manual-upload path onto the same ingestion hand-off `sync_pull_corpus` uses (D9).
- Make the operational contract precise enough to build against without guessing: what "accepted"/"completed"/"queryable" mean, how a replayed submission and two racing workers are both closed by the same mechanism, how a crash mid-batch and a failed update both preserve rather than lose or duplicate work, and what the M2M/instance-authorization/document-rights boundary actually is — all reusing the existing `fred_core.tasks` durable lifecycle, not a parallel one (2026-09-07 review pass, D11-D19).

**Non-Goals:**
- Building the remote HTTP adapter or any external-pod hosting/deployment mechanism itself — D10 designs the wire contract this MVP's local adapter is shaped compatibly with, but does not implement a remote adapter or ship anything that runs outside `knowledge-flow-backend`.
- Any scheduler or trigger mechanism for running a corpus instance's synchronization — this change specifies that synchronizations for one instance must not overlap (see specs/indexed-corpus/spec.md), not how or when a synchronization is invoked.
- A second `CorpusType`, `graphrag`/`llm_wiki` kinds, or an admin/team-facing UI — later increments.
- Reconciling with the older, unrelated GitHub issue `#2240` (an external-pod processor/connector design) — a separate decision once this MVP has produced evidence. D10 mines #2240's shared-envelope thinking for the narrower ingestion hand-off this change needs; it does not perform that reconciliation.

## Decisions

**D1 — Two objects, not one (`CorpusType` + `Corpus`), not a bare connector.** A bare connector (discover/fetch only) says nothing on its own about what an agent gets from it — it is not a unit worth registering, enabling, or showing an admin. `CorpusType` (platform-wide: `kind` × `mode` × `connector_kind`) is what a developer contributes and an admin enables; `Corpus` (team-scoped: `scope` × `connector_ref`) is what a team creates once its type is enabled. Alternative considered and rejected: a single `Corpus` object carrying both platform-wide and team-scoped fields together (the MVP's first iteration) — rejected because `mode` and `connector_kind` are intrinsic to which type is being instantiated, not a per-instance choice, and conflating the two objects would force every instance-creation path to re-decide platform-wide facts.

**D2 — `SourceConnector` identity is two fields, not one.** `source_item_id` (stable, provider-defined) and `revision` (content-addressed where the provider offers it) are separate fields, never derived from a display path or a mutable timestamp — directly closing the Sphere failure mode of diffing by a raw timestamp string. A rename is representable as "same `source_item_id`, new `display_path`"; "nothing changed" is provable from `revision` alone, without re-fetching content. Alternative considered: deriving identity from a hash of the display path (what the dead, pre-existing `SphereContentLoader` in this codebase did) — rejected for the same reason it failed before: it cannot represent a rename and provides no real change detection.

**D3 — Deletion is a first-class change kind.** The connector reports `DELETE` explicitly rather than the caller inferring it by diffing two listings — removes an entire class of bugs where a partial or failed listing looks like "everything was deleted."

**D4 — Pull-sourced documents reuse the exact push ingestion primitives.** `sync_pull_corpus` calls `extract_metadata`/`save_input`, `push_input_process`, and `output_process` — the same functions a manual upload already calls — rather than a parallel pull-specific pipeline. A changed source item is handled as delete-then-recreate (a new document id), not update-in-place; this is an accepted limitation carried over from the evidence in Context, not a new gap introduced here.

**D5 — Usage enablement is its own OpenFGA type (`corpus_type`), not a namespaced `capability` id.** `capability` is reserved for "something an agent uses"; a corpus type's creation/operation permission is not that, any more than an application's is. This mirrors a parallel, in-progress move a teammate is making for `app` off the same `capability:app__<id>` namespacing pattern this design deliberately does not repeat. The new type omits `capability`'s personal-space overlay (`personal_on`/`personal_disabled`) — not needed yet; a personal team still inherits `default_on` like any other team through the same contextual edge.

**D6 — `CorpusType` is deployment configuration; `Corpus` is a database row.** Mirrors the existing `ApplicationSourceConfig` precedent exactly: a corpus type is contributed by a developer/operator, not created through a product API, so it needs no table — `CorpusTypeConfig` subclasses `fred_sdk.contracts.corpus.CorpusType` directly rather than redeclaring its fields. A `Corpus` instance is genuinely new, team-created runtime state, so it is a Postgres row (`corpus` table, mirroring `agent_instance`'s shape: plain string primary key, indexed `team_id`, JSON-serialized `tag_ids` in a `Text` column matching the codebase's existing convention for structured-but-flexible fields).

**D7 (open, tracked as a task) — Where `Corpus`/`CorpusType` config is read from during synchronization, and where sync state lives.** `Corpus`/`CorpusType` are owned by `control-plane-backend` (D6); the synchronization engine runs in `knowledge-flow-backend` (where the existing ingestion pipeline already lives). The decision already reached in design discussion: read `Corpus`/`CorpusType` from control-plane once per synchronization cycle (not once per file — a low-frequency read, mirroring `fred-runtime`'s existing `initialize_control_plane_client()` pattern), and keep the synchronization's own cursor/state (`{source_item_id: document_id}` plus the connector's opaque cursor) in a small `knowledge-flow-backend`-owned table next to `kf_task_run`/`kf_task_event_log`, never round-tripped through control-plane. Not yet implemented — see tasks.md.

**D8 (2026-09-07) — A new `DocumentIngestionPort` in `fred-sdk`, sibling to the existing `Document*Port` family.** `fred_sdk/contracts/runtime.py` already has an established pattern for decoupling code that must not import backend internals: `DocumentContentPort`, `DocumentFolderPort`, `DocumentTreePort`, `DocumentSummarizePort`, `DocumentMarkdownPort`, `DocumentExtractionPort`, `DocumentSearchPort`, `DocumentSimilarityPort` are abstract `ABC`s defined in `fred-sdk`; every concrete implementation lives in `fred_runtime/integrations/v2_runtime/adapters.py` as an `httpx`-backed adapter calling FRED's real API, and every adapter shares one `DocumentPortCallError` for transport failures. All eight are read-side. `DocumentIngestionPort` is the missing write side: `async def submit(item: SourceItem, artifact_path: Path, corpus_id: str) -> str` (returns the document id) and `async def delete(document_id: str) -> None`, raising `DocumentPortCallError` on transport failure — same shape, same shared exception, not a new error type. Matching the existing family's convention (see `DocumentContentPort`'s docstring: "auth and identity come from the adapter's privately-captured per-turn binding, never from the caller"), `submit`/`delete` take no user/team identity parameter; the adapter's own binding supplies it. **Amended (2026-09-07 review pass) — two precisions the original signature left open:** `submit` MUST be idempotent per `(corpus_id, item.source_item_id, item.revision)` — resubmitting an already-ingested identical revision returns the same document id rather than creating a duplicate (needed for D13's replay guarantee and D14's crash recovery). `delete` gains a required `corpus_id` keyword — `async def delete(document_id: str, *, corpus_id: str) -> None` — because the original `delete(document_id: str) -> None` gave an adapter no way to verify a delete request targets the corpus the caller believes it does; the adapter MUST verify the resolved document's own corpus/`source_tag` matches `corpus_id` before deleting, raising `DocumentPortCallError` on mismatch (D16). Alternative considered and rejected: extending `sync_pull_corpus` in place with an injectable interface instead of a `fred-sdk` port — rejected because the whole point (Goals) is that this contract must be callable from code that cannot import `knowledge_flow_backend` at all, which an injected-but-internally-typed interface does not guarantee.

**D9 (2026-09-07) — Both MVP corpus types are hosted in-process, and both call the same port's local adapter.** A local adapter implements `DocumentIngestionPort` inside `knowledge-flow-backend`, calling the existing pipeline exactly as `sync_pull_corpus` already does (`extract_metadata`/`save_input`, `push_input_process`, `output_process`, `delete_document_and_artifacts` — D4 is unchanged, just moved behind the port instead of called ad hoc). `sync_pull_corpus` (the `local_fs`/pull corpus) is refactored to call this adapter. The existing manual-upload path (`ingestion_controller.py`) — the de facto `rag_sql`/push corpus — is refactored to call the *same* adapter instance for its own document creation, rather than calling `push_input_process`/`output_process` directly as it does today. This is the concrete proof the developer asked for: push and pull become two callers of one contract, not two pipelines that happen to look similar. Alternative considered and rejected: leave the push path untouched and only route the new pull path through the port — rejected because it would leave the "one ingestion contract" claim unproven for the one corpus type every FRED deployment already has, and the retrofit is small (the push path already calls the same four underlying functions; only the call site moves).

**Correction (2026-09-07 review pass) — "in-process, no Temporal" was stated as if intrinsic to pull sync; it is not, and the mismatch matters.** `pull_corpus_sync.py`'s own docstring says this proof-of-concept runs "in-process (no Temporal)," and D13 below was first drafted assuming that. But the real push path this decision claims to share a contract with does **not** hard-code that choice: `ingestion_controller.py` already routes document creation through `IngestionTaskService` (`features/scheduler/scheduler_service.py`) against a real `SchedulerBackend` (`fred_core.scheduler.SchedulerBackend`) that can be `MEMORY` or `TEMPORAL` depending on deployment — `_scheduler_backend()` reads it from `ApplicationContext`, it is not fixed at build time. If push and pull are to share one contract (this decision's whole point), whether `corpus_sync` also goes through `IngestionTaskService`'s existing scheduler-backend abstraction (and inherits whatever Temporal-backed reconciliation already exists for `kind="ingestion"` tasks) — versus staying a bespoke `kind="corpus_sync"` island hard-wired to no Temporal — is a real, currently unresolved architecture choice, not a settled detail. It materially changes which crash-recovery mechanism D13 can rely on (see D13's correction below). Left open — see Open Questions; tasks.md's Group 8/10 acceptance criteria must state which way this went once decided, not assume "no Temporal" silently.

**D10 (2026-09-07) — The wire contract for a future remote adapter is designed now, not deferred, but not implemented now.** `DocumentIngestionPort` is meaningless as a decoupling boundary if its local adapter is shaped in a way an HTTP-backed remote adapter could not also satisfy later. The wire contract (`submit`: `SourceItem` fields + a corpus/team-scoped authorized upload target + the artifact bytes; `delete`: a document id + the same authorization) is deliberately narrower than `#2240`'s shared execution envelope: `#2240` externalizes document *processing* (OCR/chunking/entity extraction) itself, returning FRED a manifest; this port's remote shape only externalizes *discovery and fetch* (already `SourceConnector`'s job) plus handing FRED the raw artifact for FRED's own existing pipeline to process exactly as it does today — closer to "an M2M-authenticated upload" than to a processor pod. Reused from `#2240` without adopting its broader scope: authorize the exact scope before dispatch (mirrors this change's own `corpus_type`/`can_use` gate, D5), least-privilege/short-lived artifact access rather than passing raw credentials, and "the durable cursor advances only after the corresponding batch is durably accepted" (already `SourceConnector`'s own cursor contract, D2/D3 — restated here because a remote caller cannot assume anything stronger). The exact request/response field list is a task-level fixture (tasks.md), not enumerated in this document — this decision fixes the shape and its security properties, not a field-by-field schema.

**D11 (2026-09-07, corrected 2026-09-07 review pass) — Three distinct things, not one: what a corpus exposes, what an agent is authorized to use, and what a user selects.** The first draft of this decision collapsed all three into "the tag is the coupling point" and implicitly generalized rag_sql's own wiring to every future `CorpusKind`. Restated as three layers, none of which this change touches:
- **What a corpus instance exposes** — a property of its `CorpusKind`'s own pipeline, not of this change: `rag_sql` indexes into FRED's existing document/vector/SQL store, so its content is *capable of* being retrieved semantically and queried tabularly. A future `graphrag` corpus would expose a graph query surface instead — a completely different exposure shape, decided entirely by that kind's own indexation implementation, never by anything `CorpusType`/`Corpus` (this change's SDK contracts) define. No code branches on `CorpusKind` today, and this change adds none.
- **What an agent is authorized to use** — an existing, entirely separate configuration surface: an agent instance's `document_access` capability config (`DocumentAccessConfig.library_tag_ids`, RAG) and/or its MCP server list including the tabular server (SQL, scoped by `TabularService._resolve_scope_tag_ids`). Creating a `Corpus` never creates, edits, or implies either. For `rag_sql` specifically, both of these existing capabilities happen to key on a tag — and a corpus stamps its documents with one (`corpus.scope.tag_ids`, `source_tag=corpus_id`) — so an admin *can* point an agent's existing capability config at a corpus's tag. That is a fact about `document_access` and the tabular MCP server's own design, not a mechanism this change defines or a pattern a future `CorpusKind` is obligated to fit — a kind whose exposure shape is not tag-addressable (e.g. a graph query surface) would need its own, different capability-wiring convention, decided when that kind is built, not implied here.
- **What a user selects** — the chat-time picker (`RuntimeContext.selected_document_libraries_ids`) or an LLM-supplied scope argument on a per-turn MCP call; neither is aware a `Corpus` exists either, only tags and document ids.
Net: creating or operating a corpus instance never creates, modifies, or implies any agent capability or MCP server configuration, in any `CorpusKind` — that general claim stands. What does *not* stand is treating tag-based rag_sql wiring as the design's general answer to "how capabilities are exposed" for every future kind.

**D12 (2026-09-07) — Operation lifecycle states, reusing `fred_core.tasks`.** A corpus synchronization run is one `fred_core.tasks` row (`kf_task_run`/`kf_task_event_log` — the same durable task/event pair already backing `knowledge-flow-backend`'s ingestion/erasure tasks and control-plane's migrations, #2170), not a parallel table or in-memory status (reuse required — see Consolidation guidance). **Accepted**: `TaskService.start()` has durably created a `kf_task_run` row in a non-terminal state for this sync; the caller may stop watching. **Completed**: that row reached a terminal `state` (`succeeded`/`failed`/`cancelled`). **Queryable**: a per-document, incremental property independent of the task's own state — a pulled document is queryable the moment `output_process` durably lands it (already true for push, spec.md's "indistinguishable downstream" requirement), which happens item-by-item while the enclosing task is still `running`. A corpus is never all-or-nothing queryable at task completion.

**D13 (2026-09-07, corrected 2026-09-07 review pass) — A unique index closes replayed *submission*, but "one worker actually executing" needs three separate things: acquisition, crash resumption, and fencing.** The first draft conflated these. Restated precisely, and with the schema error fixed (`TaskTarget` is `{type, id, label}` — there is no `corpus_id` field to index on; a corpus-sync task's target is `TaskTarget(type="corpus", id=corpus.corpus_id, label=corpus.name)`, so any index or filter must read `target->>'id'` under `target->>'type' = 'corpus'`, never `target->>'corpus_id'`):
- **Replayed-submission dedup (what the index actually gives, unchanged from the first draft other than the field fix).** `TaskService.start()` (`store.py::new_task_id`) always mints a fresh `task_id` with no client-supplied idempotency key. `task_run_table_args` already solves the equivalent problem for `kind='migration'`: a partial unique index over non-terminal rows (`single_active_migration_index_name`) turns a second concurrent `create()` into a Postgres `IntegrityError`, translated to a 409 (`import_export/api.py`). Reused here as a partial unique index over non-terminal rows filtered to `kind='corpus_sync'`, keyed on `target->>'id'` where `target->>'type'='corpus'`. A caller whose `start()` raises the resulting 409 MUST treat it as "already accepted or in progress" and poll the existing `task_id`. This alone answers "no duplicate row is ever created for the same corpus" — it does **not** answer "exactly one worker is advancing that row," which is a different property the index cannot provide (two workers could both believe they own the *one* row that exists).
- **Acquisition.** Creating the row is *announcement*, not *acquisition*. A worker that successfully calls `start()` (or finds no colliding row) must additionally bind itself to that `task_id` as the one entitled to advance it — via `TaskService.bind_execution(task_id, execution_id=...)`, the existing hook `fred_core.tasks` already provides for exactly this purpose (`service.py::bind_execution`). Whether `execution_id` is a real Temporal workflow id (if D9's correction above resolves toward reusing `IngestionTaskService`'s `SchedulerBackend.TEMPORAL` path) or an in-process liveness handle (if it stays a bespoke `MEMORY`-only island) is the open question D9 now flags — this decision does not resolve it, but both paths require *some* `execution_id` binding for acquisition to mean anything.
- **Crash resumption.** `fred_core.tasks` already has a reconciliation sweeper (`TaskService.reconcile_stale`/`run_reconcile_sweeper`, `list_stale_non_terminal`), but by explicit design (`_reconciled_terminal`'s own docstring: "no fred-side timeouts/retries... never false-fail") it refuses to declare a task terminal from staleness (`updated_at` age) alone — it only reconciles when it can ask the bound execution's real status via `WorkflowControl` and get an authoritative non-running verdict. For a Temporal-backed `execution_id` this works out of the box (`TemporalWorkflowControl`). For an in-process, non-Temporal `corpus_sync` (the current `pull_corpus_sync.py` shape), there is no `WorkflowControl` implementation that can authoritatively say "that process is dead," so `reconcile_stale` would never resolve a crashed in-process sync's row — meaning the D13 exclusion index above would then block every future sync for that corpus **forever** after a crash. This is a genuine, unresolved gap, not a solved one: either corpus_sync must run under a scheduler backend `fred_core.tasks` can already reconcile (Temporal, per D9's correction), or a purpose-built `WorkflowControl` for the in-process case must exist (a heartbeat the execution host renews by calling `record_event` faster than a grace period, treated as "gone" only once that grace period has unambiguously elapsed) — this decision names the requirement, not the implementation; resolving it is a precondition for Task 11.1, tracked in Open Questions.
- **Fencing (excluding a presumed-dead worker that is actually still alive).** Even with a correct liveness check, a worker that is merely slow (GC pause, network partition) can be reconciled "failed" while still running, then keep calling `DocumentIngestionPort.submit`/`delete` after a second sync has legitimately started. `fred_core.tasks` already has the right instinct for this at the row level — `_emit_terminal_if_diverged` re-fetches "for a fresh terminal check... never overwrite a terminal state" immediately before writing, rather than trusting a stale read. The execution host must apply the same discipline one level up, *before* every mutating I/O call, not only at sync start: re-check its own `task_id`'s row is still non-terminal and still bound to its own `execution_id` immediately before each `submit`/`delete`, and stop calling either the moment that check fails. This is fencing-by-frequent-recheck, not a true monotonic fencing token compared-and-swapped at the storage layer — weaker, but consistent with D9's single-execution-host assumption for this MVP and with the existing `_emit_terminal_if_diverged` pattern; a real multi-replica-safe fencing token is not designed here and should not be assumed solved.

**D14 (2026-09-07) — Crash between indexing an item and persisting the cursor.** This is about `corpus_sync_state` (D7) — the sync's own per-item progress — a different layer from D13's `kf_task_run` row (which task is running at all, and who owns advancing it). `sync_pull_corpus` today persists `corpus_sync_state` exactly once, after the *entire* `discover_changes()` batch finishes — a crash after item N of M is durably ingested but before that single persist means item N is re-discovered and re-ingested next run, from state that does not yet know about it. Closing this (left to Task 10.2/10.3's implementation, specified here): (1) the per-item `{source_item_id: document_id}` entry MUST be durably updated after that item's `DocumentIngestionPort` call lands, not once per batch; (2) the connector's own opaque **cursor** (the second half of `corpus_sync_state`, D7) is a coarser-grained checkpoint than the per-item map and MUST NOT advance past a batch until every item in that batch is durably reflected in (1) — advancing it early would let a subsequent `discover_changes(cursor)` call skip an item whose per-item state write is still pending, which no per-item idempotency fixes (idempotency protects against re-processing the same item twice, not against never being asked to process it again). So: per-item state after every item; cursor only once the whole batch it belongs to is fully accounted for. (3) `DocumentIngestionPort.submit`'s idempotency (D8 amendment, above) makes a resubmission produced by the residual gap between an item landing and its own per-item state write a no-op instead of a duplicate — this is what makes (1)'s narrower window safe to leave unclosed rather than requiring a single atomic transaction across the ingestion call and the state write.

**D15 (2026-09-07) — A failed update must preserve the last usable version.** The merged `pull_corpus_sync.py` (changed-content branch) currently deletes the OLD document (`MetadataService().delete_document_and_artifacts`) *before* fetching and ingesting the new revision — so a failure anywhere in the subsequent fetch/extract/ingest sequence leaves that source item with **no** usable document at all, not merely a stale one, until the next successful sync. This is backwards: an update MUST ingest and durably confirm the replacement *before* the prior version is removed, so a failed update leaves the last-known-good version in place and the item is simply retried whole next cycle. This is a correction for Task 8.1's implementation, not a new task — tasks.md now states the required ordering as that task's acceptance criterion. **Scope, reconciled with D4/D9 (2026-09-07 review pass):** this ordering fix lives entirely in `sync_pull_corpus`'s own orchestration (the changed-content branch that decides to call `submit` then `delete`) — never in the shared adapter/port itself, and never triggered by the push path. Push (manual upload) has no "same source item, new revision" concept at all — every upload is a fresh document, so it never takes this branch; D9's "one shared adapter" claim is about the `submit`/`delete` *primitives* both paths call, not about pull's own delete-then-recreate orchestration, which is unique to pull and stays unique to pull.

**D16 (2026-09-07, corrected 2026-09-07 review pass) — A worker cannot write to the remote source, and cannot mutate another corpus; neither claim is fully closed by the Protocol shape alone.**
- **No write to the remote source.** `SourceConnector` defining only `discover_changes`/`fetch` (no write method in the Protocol) is necessary but not sufficient — a `Protocol` cannot stop an implementation from importing its provider's write API anyway, so this is a contract obligation on implementers, not a runtime guard. Closing the gap needs an operational control, not just an interface shape: whatever credential `connector_ref` resolves to (D18) MUST itself be provisioned read-only at the source (a read-only API token/scope, or a read-only filesystem mount for `LocalFilesystemConnector`) — this is a requirement on whoever configures a `CorpusType`'s credential, stated here so it is checked at registration/deployment review, not assumed from the Protocol's method list. Worth a one-line pointer to both halves (Protocol shape + credential scope) on `SourceConnector`'s own docstring.
- **Cannot mutate another corpus — corrected: a `corpus_id` parameter is not, by itself, an authorization.** The first draft's fix (`delete(document_id, *, corpus_id)`, D8 amendment) checked the document's own corpus against a caller-supplied `corpus_id` — but a bare parameter is only as trustworthy as whatever passed it in, and nothing stopped arbitrary code from calling `delete()` with any `corpus_id` it liked. The actual guarantee has to come from **where `corpus_id` is bound**, not from its presence as an argument: the execution host constructs one `DocumentIngestionPort` adapter instance per sync cycle, only after D17's authorization checks pass for one specific `corpus_id` — the adapter privately captures that `corpus_id` in its own binding at construction time, exactly the convention `DocumentContentPort`'s docstring already states for identity ("auth and identity come from the adapter's privately-captured per-turn binding, never from the caller"). `submit`/`delete`'s explicit `corpus_id` argument is then defense-in-depth against a bug in the caller's own bookkeeping (it MUST match the adapter's bound scope, or the call is rejected) — never the primary authorization, which is *which adapter instance you were handed*, not what you told it. This, together with the document's own recorded corpus/`source_tag` (checked before delete, unchanged from the first draft), gives two independent checks instead of one nominal one.
- **General rule for any internal mutation (submit/delete), stated once here rather than per-decision:** never trust a single caller-supplied identifier. Every mutating call must be backed by (a) an authorized identity for this execution (D17's M2M + instance-authorization checks, already passed before the adapter was constructed), (b) the corpus bound to *that* execution (the adapter's own captured scope, this decision), and (c) the target document's own recorded ownership (checked against (b) before the mutation proceeds). No single one of the three stands in for the others.

**D17 (2026-09-07, corrected 2026-09-07 review pass) — Runtime authorization is three distinct checks; here is what revocation of each produces. (a)'s "no mechanism exists" claim was wrong — the mechanism exists and is reusable; what's actually missing is narrower.**

(a) **M2M identity** — whether the caller reaching control-plane's M2M read endpoint (Task 10.1) really is `knowledge-flow-backend`'s runtime; transport-level, decided before any business logic. **Corrected inventory:** `fred_core.security.backend_to_backend_auth` already provides a generic, reusable client-credentials token minter — `M2MAuthConfig`/`M2MTokenProvider`/`M2MBearerAuth` (Keycloak `client_credentials` grant, cached/refreshing bearer token, `httpx.Auth` injector) — used twice today: control-plane's own `get_service_token_provider()`/`get_service_bearer()` (`app/context.py`) mints control-plane's *own* service-account token for its server-initiated erase-at-expiry path (CTRLP-12), and `knowledge-flow-backend` already builds its *own* `M2MTokenProvider` too (`application_state.py::_init_m2m_client`, from `configuration.security.m2m`) — but only for self-calls over an in-process ASGI transport (`make_m2m_asgi_client`), not for a real network call to another backend. What's actually missing, precisely: (1) no `httpx.AsyncClient` wiring exists yet for `knowledge-flow-backend` to call **control-plane**, over the network, using its own `M2MTokenProvider` and `M2MBearerAuth` — a small, low-risk addition following an established pattern, not an unknown mechanism; (2) authorization on the *receiving* side is the real open piece — `is_service_agent(user)` (`fred_core.security.structure`) is a generic role predicate (`SERVICE_AGENT_ROLE in user.roles`) any backend's JWT validation already recognizes, and `teams/service.py` already has a precedent for granting a service identity read-only bypass (`is_service_agent(user) and permissions_are_read_only`) — but that predicate alone would let *any* service-agent-role-holding caller (any backend's M2M principal, not specifically `knowledge-flow-backend`'s) read *any* team's `Corpus`/`CorpusType`. Task 10.1's endpoint needs a narrower check than "is a service agent" — either restricting by the caller's specific Keycloak `client_id`/`azp` claim, or scoping what a generic service-agent token is allowed to read for this endpoint specifically. No existing endpoint in this codebase authorizes one specific *cross-service* caller (as opposed to a self-call) this way, so this narrower check has no precedent to copy — it is the genuine open design item, not the M2M authentication machinery itself.

(b) **Instance authorization** (`corpus_type#can_use`, D5) — whether the team owning a `Corpus` may operate an instance of its type; already checked once at creation (spec.md) and, newly specified here, re-checked at the start of every sync cycle (the same low-frequency control-plane read, D7) rather than cached indefinitely from creation time.

(c) **Document-level rights** — the existing tag/team ReBAC scope on the documents themselves, governing agent query-time access; unaffected by (b) (spec.md's existing "authorization to use a corpus type governs creation only" requirement, now extended by (b)'s re-check).

Revocation of (b): the instance and its documents are not deleted; the next cycle's re-check observes `can_use=False` and does not run (fails closed, same as creation); already-ingested content stays queryable under (c) unchanged — revocation stops *future* synchronization, it is not retroactive erasure. Task 10.1 is not blocked on inventing a mechanism (one exists, per the corrected inventory above) — it is blocked on deciding the receiving-side authorization narrowing in (a)(2), a smaller and more precisely scoped open question than the first draft stated — see Open Questions.

**D18 (2026-09-07) — Ownership and cleanup of copies, index, state, and secrets.** Fetched artifact bytes: transient, owned by the execution host process, already cleaned up correctly today (`tempfile.TemporaryDirectory`'s `__exit__` runs on both success and exception) — confirmed, not a gap. The durable document copy and its vector/SQL index entries: owned by `knowledge-flow-backend`'s existing store, identically for pushed and pulled documents; cleaned up by the existing `delete_document_and_artifacts`, reused as-is. `corpus_sync_state`: owned by `knowledge-flow-backend` (D7). `Corpus`/`CorpusType` rows: owned by control-plane (D6). Secrets: `connector_ref` is specified (corpus.py's own docstring) as a *reference*, never the raw secret — it MUST stay a reference through every hop: the `corpus` table stores only the reference string, the M2M read endpoint (Task 10.1) returns it unresolved, `knowledge-flow-backend` resolves it itself close to use, and it MUST NOT appear in any `kf_task_event_log.detail`/`error`/`target` (nor, forward-looking, any frontend response — no such UI exists in this MVP's scope). **Flagged, not resolved**: no secret-resolution mechanism exists in this codebase yet (checked: no vault/secret-store abstraction in `fred-core` or either backend) — `connector_ref`'s "reference" property has never been exercised, since the only built connector (`LocalFilesystemConnector`) needs no credential; must be designed before a connector kind requiring a real secret (Sphere/GitHub/Minio) is built. **Also flagged**: this MVP has no `Corpus`-instance deletion operation at all (only `create_corpus`), so "who cleans up `corpus_sync_state` and ingested documents when an instance is retired" is presently unanswerable, not merely undecided — added to proposal.md's out-of-scope list and to Open Questions.

**D19 (2026-09-07, corrected 2026-09-07 review pass) — Portability proof must exercise the corpus implementation, not just `DocumentIngestionPort` in isolation.** The first draft's contract-test suite ("given any adapter satisfying `DocumentIngestionPort`...") proves the *port* is implementation-agnostic — it does not prove *this corpus* (`local_fs`/rag_sql: `LocalFilesystemConnector` acquiring, the existing pipeline indexing, `document_access`/tabular MCP exposing) is portable, because `DocumentIngestionPort` is only rag_sql's own indexation service (D11/matrix correction below), not the corpus's full boundary. A fake satisfying the ABC in isolation tells us nothing about whether the *real* connector's discovery/fetch behavior, the real ingestion pipeline, and the real end-to-end "discover → fetch → index → queryable" outcome hold up once the connector's process boundary moves — which is the actual claim D8-D10 make.

Corrected proof: one shared contract-test suite exercising the real `local_fs` corpus implementation end-to-end (real `LocalFilesystemConnector` against a real temp directory, real `extract_metadata`/`push_input_process`/`output_process`, real assertions that discovered changes become queryable documents with the expected content) — "given this corpus implementation wired up, discover→fetch→submit→query and discover→fetch→delete must hold these observable outcomes" — run twice: (1) **in-process**: connector and indexation adapter constructed in the same process as the test, the shape D9 ships for this MVP; (2) **separate-process**: the same `LocalFilesystemConnector` instance runs in a child OS process the test spawns, discovering/fetching against the same real temp directory, but handing what it fetched to the indexation service over D10's wire shape (a thin loopback `httpx` client in the child process talking to a real HTTP server in the parent, backed by the *same* local indexation adapter Task 8.1 builds — not a second implementation of it) — the shape D10 designs for later. No Kubernetes, no second deployable service; the process boundary is the only thing that differs between (1) and (2), and both must produce identical, real, queryable documents. Anchored on Task 9.1's wire-contract fixture (D10) but scoped to the corpus, not the port. New task-level deliverable for Group 9 (tasks.md), not yet listed there before this revision.

**Correction (2026-09-07 review pass): "corpus implementation" ≠ `SourceConnector`.** The first draft's "Corpus-type implementation" row equated a corpus implementation with its `SourceConnector` alone. A corpus implementation is three things together, for one `CorpusKind`: **acquisition** (a `SourceConnector`, if pull-mode — discover/fetch, D2/D3), **indexation** (whatever turns an acquired item into indexed, queryable content — for `rag_sql` specifically, `DocumentIngestionPort`'s local adapter calling FRED's existing pipeline; a future `graphrag` kind would index differently, through a different service, not necessarily `DocumentIngestionPort` at all), and **query capability** (what an already-indexed corpus's content can be retrieved through — for `rag_sql`, the existing `document_access`/tabular-MCP surfaces, per D11's corrected boundary). `DocumentIngestionPort` is `rag_sql`'s own indexation service, one possible implementation of the middle piece for one kind — not the universal corpus/execution-host boundary the first draft implied. ## Risks / Trade-offs

- **[Risk] The `corpus_type` ReBAC schema addition could diverge from Adrian's separate `app`-kind convention if his lands with a different shape.** → Mitigation: `libs/fred-core/fred_core/security/rebac/schema.fga` already carries `corpus_type` as a minimal, easily-adjusted type (six relations); reconciling means adjusting this one block, not a rewrite. Do not extend `corpus_type` further (e.g. a personal-space overlay) until his convention lands.
- **[Risk] Redundant synchronization cost when multiple corpus instances pull the same external source.** → Accepted trade, not mitigated: each instance runs its own independent connector, cursor, and cost, in exchange for zero cross-instance coordination. Documented as a deliberate simplicity choice, not an oversight.
- **[Risk] A changed source item is delete-then-recreate, not update-in-place, so a document id referenced elsewhere (a link, a citation) stops resolving after any content change.** → Accepted limitation carried over from evidence in Context; revisit only if a concrete downstream consumer needs stable document ids across content changes.
- **[Trade-off] No scheduler/trigger is specified in this change (Non-Goals), so nothing currently invokes `sync_pull_corpus` outside a test.** → The no-overlapping-synchronization requirement (specs/indexed-corpus/spec.md) is specified now, ahead of the trigger mechanism, precisely so whatever trigger is chosen next is designed against an already-fixed constraint rather than retrofitted around one.
- **[Risk] Retrofitting the existing manual-upload path (D9) touches a code path every FRED deployment already depends on, not just this MVP's new pull corpus.** → Mitigation: the retrofit changes only the call site (which function creates the document), not `extract_metadata`/`push_input_process`/`output_process`'s own behavior — the same functions run the same way, now invoked through one adapter instead of two call sites. Ship behind the existing test suite for the upload path, not just this change's own tests.
- **[Risk] Designing a wire contract now (D10) without building or testing a remote adapter risks the shape being wrong when one is actually built.** → Accepted, bounded risk, not eliminated: D10 fixes only the contract's shape and security properties (what a remote caller must prove, never raw credentials or unscoped access), not its exact fields — the field-level detail is deliberately left to when a real remote adapter is built and can be tested against, per D10.
- **[Risk, corrected 2026-09-07] The M2M *authentication* mechanism for Task 10.1 already exists and is reusable (`fred_core.security.backend_to_backend_auth`, D17) — the real risk is narrower: no precedent exists for authorizing one specific cross-service caller on the receiving side.** → `is_service_agent` alone would authorize any service-agent-role bearer, not specifically `knowledge-flow-backend`; a caller-specific check (client_id/`azp`, or a narrower per-endpoint scope) must be designed before Task 10.1 ships. Smaller and more precisely scoped than the first draft's "no mechanism exists" — see Open Questions.
- **[Risk] `connector_ref` is documented as "a reference, never a raw secret" (corpus.py) but no secret-resolution mechanism exists to back that claim (D18), and it has never been exercised by a connector that actually needs one.** → Accepted for this MVP (`LocalFilesystemConnector` needs no credential), but MUST be resolved before any credential-bearing connector kind (Sphere/GitHub/Minio) is built — see Open Questions.
- **[Risk, new 2026-09-07] `fred_core.tasks`' reconciliation sweeper cannot recover a crashed in-process (non-Temporal) `corpus_sync` task by design (D13) — it refuses to declare a task terminal from staleness alone, only from an authoritative executor verdict it has no way to obtain without a real `execution_id` binding.** → Unmitigated: if `corpus_sync` stays a `MEMORY`-only island (D9's open question), a crashed sync permanently blocks that corpus via D13's own exclusion index, with no existing sweeper able to clear it. Resolving D9's scheduler-backend question (reuse `IngestionTaskService`'s Temporal path, or build a bespoke in-process `WorkflowControl`) is a precondition, not an implementation detail — see Open Questions.
- **[Risk, new 2026-09-07] A worker correctly presumed dead by reconciliation can still be alive (GC pause, network partition) and keep mutating after a second sync starts (D13's fencing gap).** → Partially mitigated by design (frequent re-check before every mutating call, D13) but not by a true fencing token — accepted as adequate only under D9's single-execution-host assumption; revisit if this MVP ever runs multiple replicas of the execution host.

## Migration Plan

No migration of existing data: this is new capability, not a change to existing behavior. The one schema migration involved (`corpus` table, `apps/control-plane-backend/alembic/versions/57f8e7e05006_add_corpus.py`) is additive-only (`create_table`) with a verified symmetric `downgrade()`. `docs/swift/rfc/INDEXED-CORPUS-RFC.md` is left in place, not deleted, until this change is archived and its content is confirmed to have carried over completely (see tasks.md).

## Open Questions

- Final id/name for the `corpus_type` ReBAC object once Adrian's `app`-kind convention lands (tracked in tasks.md, does not change this change's specs or approach).
- Whether the admin Features-tab entry for a `CorpusType` reuses the existing capability-kind-filtered catalog UI (`CapabilitiesPage.tsx`) as an additional filter value, or gets its own page — a later increment's decision, not this one's.
- How a team's Resources tab represents multiple corpus instances, given it shows undifferentiated documents today with no corpus concept at all — a later increment's decision.
- **(D17, corrected 2026-09-07) How control-plane's Task 10.1 endpoint authorizes `knowledge-flow-backend` specifically, not any service-agent-role bearer.** The authentication mechanism itself is settled — reuse `fred_core.security.backend_to_backend_auth` (`M2MTokenProvider`/`M2MAuthConfig`/`M2MBearerAuth`), the same machinery control-plane already uses for its own service account (`get_service_token_provider()`) and knowledge-flow-backend already uses for self-calls (`application_state.py::_init_m2m_client`) — extended with a real network `httpx.AsyncClient` from KF to CP using KF's own provider. What remains open is the receiving-side check: `is_service_agent(user)` alone is too broad (any backend's service principal), and no existing endpoint authorizes one specific cross-service caller — the developer must decide the narrowing (client_id/`azp` allow-list, or a scoped permission) before Task 10.1 ships.
- **(D9/D13, new 2026-09-07) Whether `corpus_sync` reuses `IngestionTaskService`'s existing `SchedulerBackend` abstraction (inheriting Temporal-backed reconciliation where deployed) or stays a bespoke `kind="corpus_sync"`, `MEMORY`-only island.** Not cosmetic: D13's crash-resumption story depends entirely on this. Staying `MEMORY`-only requires a purpose-built `WorkflowControl` (heartbeat-based liveness) to be designed before Task 11.1's exclusion index is safe to ship; reusing `IngestionTaskService` may resolve most of D13's crash-resumption gap for free but changes Group 8/10's shape. Must be decided before Task 11.1, not discovered while implementing it.
- **(D18) What secret-resolution mechanism backs `connector_ref` when a connector kind needs a real credential.** No vault/secret-store abstraction exists in `fred-core` or either backend today; deferred safely for this MVP (`LocalFilesystemConnector` needs none) but blocking for the first credential-bearing `CorpusType`.
- **(D18) How a `Corpus` instance itself is deleted, and what cascades from that** (its `corpus_sync_state` row, its ingested documents and index entries). No such operation exists yet — only `create_corpus`. Out of scope for this MVP (added to proposal.md); must be designed before a real deployment can retire a corpus instance.
- **(D1, SDK weight) Whether `fred-sdk`'s hard dependency on `langchain`/`langchain-core`/`langgraph`/`httpx` (its agent-authoring surface) is acceptable for a minimal external connector that only wants `SourceConnector`/`CorpusType`/`DocumentIngestionPort`.** `test_sdk_purity.py` guards transitive *imports* of a few backend-only modules, not the package's actual installed footprint — a future standalone connector repo (D10's remote-hosting goal) would install the full agent-authoring stack for three contract modules. Not blocking this MVP (everything runs in-process); worth resolving (a narrower `fred-sdk-contracts` distribution, or accepting the weight) before a real external connector is built.
