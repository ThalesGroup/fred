## Context

The chart renders each application's `configuration` verbatim into its ConfigMap (`configmap-backend.yaml`), and its `env` and `extraEnvVars` verbatim into its Deployment. The Deployment already derives one frontend variable from another application's values: `FRONTEND_ENABLE_APPLICATIONS` comes from the control plane's `enableApplications`, and is emitted after `env`/`extraEnvVars` so that it stays authoritative. The values schema is generated by `scripts/generate_chart_schema.py`: the backends' configuration schemas are inlined into a hand-written chart-level schema.

The consumers do not change. The control plane validates `application_sources` (`ApplicationSourceConfig`, unique `app_id`) and `knowledge_bases.publishers` (`KnowledgeBasePublisher`, unique and non-covering prefixes) at startup. The frontend entrypoint validates `FRONTEND_APPLICATIONS_JSON` (keys, origin-only URLs) at container start.

## Goals / Non-Goals

**Goals:**
- Registrations computed once per render, and seen identically by the ConfigMap, the Deployment's configuration checksum and the frontend's environment.
- Refusal of the former values with an actionable message, rather than a schema error that does not say where an entry should go.

**Non-Goals:**
- Changing the control plane's configuration model, Docker Compose configuration or the frontend container's variable.
- Registering applications at runtime (an API or a CRD). Registration stays deployment configuration.

## Decisions

- **Top-level `registrations`, not under `applications`.** In this chart, `applications` already means the chart's own workloads. A separate root also keeps a registration readable by both the control plane's and the frontend's templates, without reaching into another workload's values.
- **Maps keyed by the identifier the consumers already make unique** (`app_id`, `client_id`). Helm deep-merges maps across values files, and a `null` key deletes an entry. Considered: keeping lists and concatenating them in a helmfile or a wrapper. That does not help a plain `helm install -f a.yaml -f b.yaml`, and it leaves the two halves of an application separate.
- **The gateway inside the application entry.** One entry yields both the catalog entry (the fields without `gateway`, plus `app_id`) and the gateway entry (`gateway`'s fields plus `app_id`). The two halves can no longer disagree on `app_id`, and an application cannot be half registered.
- **Derive in one place, before the per-application templates run.** `main.yaml` merges the derived `platform.application_sources` and `knowledge_bases.publishers` into the control plane's resolved application, so its ConfigMap and its checksum annotation both carry them. The frontend's Deployment appends `FRONTEND_APPLICATIONS_JSON` after `env`/`extraEnvVars`, alongside `FRONTEND_ENABLE_APPLICATIONS` (rendered by `toJson`, keys sorted). A helper template builds both, so the derivation exists once. Go templates range over maps in key order, which makes the rendering deterministic.
- **Former values refused by a guard template, not removed from the schema.** The inlined control-plane schema stays generated from the backend model as is, because Docker Compose and the backend still use those keys. A `fred.validate-registrations` template, included like `fred.validate-ingestion-worker-roles`, fails when the control plane's values set `application_sources` or `publishers`, or when the frontend's `env`/`extraEnvVars` sets `FRONTEND_APPLICATIONS_JSON`, naming the replacement key. The chart's default `FRONTEND_APPLICATIONS_JSON: "[]"` entry is removed: the derived variable is always emitted for the frontend.
- **Schema for `registrations` built from the backend schemas.** The generator takes `ApplicationSourceConfig` without `app_id` and `KnowledgeBasePublisher` without `client_id` from the control-plane schema. It adds a strict `gateway` object (`ui_upstream` required; `service_upstream`, `service_required` optional) and a key pattern taken from `app_id`'s. The rest stays with the existing validators: URL shapes at the frontend's start, prefix overlap at the control plane's start.

## Risks / Trade-offs

- [Operators upgrading with their former lists] -> The chart refuses to render, and names the key. The migration note gives the mechanical transformation, list item to map entry.
- [The worker or another workload needs these lists later] -> Today only the control-plane backend reads them. The derivation helper is the single place to extend.
- [A key in the map and an `app_id` disagree] -> Impossible by construction: the key is the `app_id`, and an entry carrying its own `app_id` is refused by the schema.

## Migration Plan

Before upgrading, an operator moves each `application_sources` item to `registrations.applications.<app_id>`, adds its gateway entry as `gateway`, and moves each publisher to `registrations.knowledgeBasePublishers.<client_id>`. They then remove `FRONTEND_APPLICATIONS_JSON` from the frontend's values. Rollback: the previous chart with the previous values. The rendered configuration is the same, so no data or state is involved.
